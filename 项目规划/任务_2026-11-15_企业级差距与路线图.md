# 企业级差距与路线图（2026-11-15）

> 依据：`任务_2026-11-12_T2_周任务闭环清单.md`（17 条剩余动作）、`任务_2026-11-13_T9_三验收.md`、`任务_2026-11-14_V_独立验收.md`（25 项）、`第10周/04_发布前检查表_2026-11-10.md`（64 项），以及 2026-11-15 现场核查的工程指标。

## 0. 一句话判断

**功能已经够一个企业级产品的骨架（41 表 / 137 接口 / 四端 / 768 个自动化测试），缺的是「工程化外壳」**：代码没有版本、没有流水线、没有监控告警、没有灰度与回滚、没有真实用户。这四样不补，功能再多也上不了生产。

## 2. 三步走（按依赖顺序，不可跳）

### 第一步：把「能交付」立起来 —— 1～2 天，AI 可做，不需要你

| 编号 | 动作 | 判据 |
|---|---|---|
| S1 | **把 207 条改动按主题拆成 5–8 个 commit 提交**，打 tag `v1.0.0-rc1` | `git status` 干净；`git tag` 有 rc1；每个 commit 只含一个主题 |
| S2 | 写 `ci.ps1`：**一条命令**跑 `mvn -B test` → `pytest` → `e2e_check` → 构建 jar → 记录 SHA | 干净目录执行一条命令，产出测试报告 + jar + SHA；任一失败退出码非 0 |
| S3 | 加 JaCoCo 覆盖率报告，阈值先设 40%（**不追求高，先有数**） | `target/site/jacoco/index.html` 可打开；CI 里有覆盖率数字 |
| S4 | `CHANGELOG.md`（按版本记变更）+ `VERSION` 文件 | 存在且与 tag 对应 |
| S5 | `deploy.ps1` / `rollback.ps1`：起服务、停服务、回滚到上一个 tag | 回滚演练一次留证（滚到 rc1 再滚回来） |

**这一步做完的意义**：任何人（包括未来的你）拿到仓库，一条命令能跑起来、能验证、能退回去。这是"企业级"的入场券。

## 3. 如果只做三件事

按"投入产出比"排序，**只做这三件也能把项目从"能跑"拉到"能交"**：

1. **提交代码 + 打 tag**（S1）——207 条改动没有版本，任何回滚、对比、交付都无从谈起。这是当前**最大的单点风险**。
2. **一条命令构建 + 测试 + 起服务**（S2）——现在靠 6 个手工 `.bat` 和记忆，换台机器就起不来。
3. **修 D07 分数口径**（Q1）——这是目前唯一一个**已定位到具体代码行**的功能缺陷，且它污染了拒答指标。

## 4. 不建议现在做（避免过度工程）

| 想法 | 为什么不建议 |
|---|---|
| 拆微服务 | 单体现在完全够（41 表、QPS 不高），拆了只会增加部署与调试成本 |
| 上 Kubernetes | 3 个 compose 已够本地/小规模；K8s 的运维成本远超收益 |
| 全链路 tracing（Jaeger/SkyWalking） | 已有 `TraceIdFilter`，先把手头日志用起来 |
| 追求 90%+ 覆盖率 | 先有覆盖率数字（40% 起步）比追高更有价值 |
| 多租户改造 | 没有第二个租户需求，属于提前优化 |
| 重写前端 | Swagger + 静态页够用，重写不解决任何当前阻断项 |
