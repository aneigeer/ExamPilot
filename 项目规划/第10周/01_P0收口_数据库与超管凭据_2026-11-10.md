### 2.2 配置文件 `D:/bigplan/tools/mysql-8.0.46/my.ini`

```ini
# 仅本机监听（第10周 P0-2：关闭全网卡监听；原值 0.0.0.0，回滚见
# 项目规划/第10周/evidence/credential_rollback_20261110.txt）

# 第10周 P0-2 实测 netstat 发现 0.0.0.0:33060 仍在监听，故显式收口
mysqlx-bind-address=127.0.0.1
```

```ini
# 日志
log-error=D:/bigplan/tools/mysql-8.0.46/data/mysql.err
# 第10周 P0-1：通用查询日志默认关闭。
# 原值 general_log=1 会把**每一条 SQL 原文**写到 380MB 的 mysql.log，
# 包括 `ALTER USER ... IDENTIFIED BY '<明文口令>'` —— 等于把口令抄了一份到磁盘。
# 排障需要时临时开：SET GLOBAL general_log=1; 用完 SET GLOBAL general_log=0; 并清空该文件。
general_log=0
general_log_file=D:/bigplan/tools/mysql-8.0.46/data/mysql.log
```

> 额外发现：原配置只改了 `bind-address` 时，**X Plugin 的 33060 端口仍会监听 `0.0.0.0` / `[::]`**（实测 `netstat` 可见）。因此补了 `mysqlx-bind-address=127.0.0.1`，避免"主端口收口了、旁路端口还开着"。
> 配置语法已用 `mysqld --defaults-file=<my.ini> --validate-config` 自检通过（无输出即合法）。

```yaml
mysql.host: 127.0.0.1
mysql.port: 3306
mysql.user: root
mysql.root.password: "<真实口令>"
admin.user: admin
admin.password: "<真实口令>"
```

这样写的理由：shell / batch / PowerShell 都能用一行 `sed`/`Select-String` 精确取到，
**不会因为 YAML 嵌套层级不同而误取到另一个 `password:`**（嵌套写法下"取第一个
`  password:`"很容易把 admin 的口令当成 MySQL 的用，属静默故障）。
`config/secrets.example.yml`（可提交）用的是同一套键名，只有占位符。

### 3.4 超管 admin 口令（BCrypt 校验实测）

用后端同一套实现（`spring-security-crypto-6.5.1` 的 `BCrypt`，与 `SecurityConfig#passwordEncoder()` 的 `new BCryptPasswordEncoder()` 同算法同强度 `$2a$10$`）对新哈希做校验。
校验用的 40 行 Java 小程序是一次性的（生成哈希 / `checkpw` 校验），**用后即删、未入库**，避免把"能生成超管哈希"的工具留在仓库里：

```console
$ java -cp spring-security-crypto-6.5.1.jar BcryptGen.java gen <新口令文件> <哈希文件>
GEN_OK pwdLen=24 hashLen=60 prefix=$2a$10$
SELF_VERIFY=MATCH
$ java -cp spring-security-crypto-6.5.1.jar BcryptGen.java check <新口令文件> <库中哈希文件>
MATCH
$ java -cp spring-security-crypto-6.5.1.jar BcryptGen.java check <旧口令文件，值见回滚点文件> <库中哈希文件>
MISMATCH
```
库内状态：

```console
$ mysql -uroot exam_prep -N -B -e "SELECT student_no, LEFT(password_hash,7), LENGTH(password_hash) FROM user WHERE student_no='admin';"
```

UPDATE 影响行数：`1`（`ROW_COUNT()`），且条件是 `WHERE student_no='admin'`，未触碰其他用户。

`backend/target/classes/application-local.yml` 是 mvn 的**资源副本**，11-08 构建时留的是旧口令；

比"资源副本旧"更坑的是**类副本旧**：自建输出目录与 `target/classes` 同时在 classpath、

> 测试/脚本里手动拼 classpath 时，同一份代码只允许出现一个目录；
> 否则让 `src/main/resources` + 新编译输出排在 `target/classes` 之前。

`scripts/qa/week10_p0_verify.sh` 的 B 段已加 `cmp -s src 与 target`，只能护住"资源副本"这一半，
类层面的规则靠上面这条人工纪律。

### 3.8 施工中新发现：通用查询日志把明文口令抄到了磁盘（已处置）

收尾自查"口令到底落在哪些文件里"时发现 `my.ini` 里有 `general_log=1`，
`D:/bigplan/tools/mysql-8.0.46/data/mysql.log` 已涨到 **380MB**，里面是**每条 SQL 的原文**，
包括本轮我执行的 `ALTER USER 'root'@'localhost' IDENTIFIED BY '<明文>'`：

```console
$ grep -c "IDENTIFIED BY" D:/bigplan/tools/mysql-8.0.46/data/mysql.log
112
$ ls -lh D:/bigplan/tools/mysql-8.0.46/data/mysql.log
-rw-r--r-- 1 ... 380M ... mysql.log
```

也就是说：**只改 my.ini + 改口令是不够的**，口令还会被 SQL 日志原样抄一份到磁盘（且该文件长期保留、

2. `my.ini` 里 `general_log=1` → `general_log=0`（含原因注释，重启后仍保持关闭）
3. 日志文件截断为 0 字节（380M → 0），复查 `grep -c "IDENTIFIED BY"` = 0
4. 因为"曾经写进日志"的口令不能算安全，又做了**第三次（最终）轮换**；这次 `general_log` 已关闭，
   实测执行 `ALTER USER` 后 `mysql.log` 仍为 **0 字节**——最终口令从未落过盘
5. 把这条检查固化进 `scripts/qa/week10_p0_verify.sh` 的 D2 段（`general_log` 必须 OFF、日志里不得有 `IDENTIFIED BY`）

### 3.10 同实例 3 个远程业务账户（dg_ctl / dg_ro / dg_rw）暴露面评估

**结论：本仓零引用；这三个账户属于同机另一个在用项目，本轮不锁定、不改 host，只定性 + 给方案。**

1) 全仓 grep（`--exclude-dir=.git --exclude-dir=target --exclude-dir=node_modules`）只在
   **本报告**与**回滚点文件**里命中（都是在描述这个风险本身），**没有任何代码/脚本/配置在用**。

2) 但顺着账户权限查下去发现它们不是本项目的：

```console

'dg_ro'@'%'   dg_lab      SELECT          / performance_schema SELECT
'dg_rw'@'%'   dg_lab      ALTER,CREATE,CREATE TEMPORARY TABLES,DELETE,DROP,INDEX,INSERT,LOCK TABLES,REFERENCES,SELECT,UPDATE

$ SELECT table_schema, COUNT(*), SUM(table_rows), MAX(create_time) ...
dg_lab      2 tables   ~240 rows    最新建表 2026-11-06
dg_system  18 tables  ~7945 rows    最新建表 2026-11-09   ← 昨天还在建表，属在用系统
```

3) 引用位置在**同机另一个项目** `D:/DBGuaredian`（DBGuardian，`dg_` = DataGuardian）：
   `.env`、`.env.example`（`DG_RO_DSN` / `DG_RW_DSN`，值是 `CHANGE_ME_*` 占位符，非真实口令）、
   `.github/workflows/ci.yml`、`adapters/mysql/adapter.py`、`apps/api/deps.py`、`benchmarks/faults/injector.py`。

4) 因此**没有执行 `ACCOUNT LOCK`**：锁定或 `RENAME USER ... TO 'localhost'` 都会跨项目生效，
   可能打断 DBGuardian 的运行与 CI（它的 DSN 走 `127.0.0.1`，但 CI/容器来源未知），
   这超出"第 10 周 P0 收口"的授权边界，也违背"不得打断未知调用方"的施工原则。

5) 即便如此，**本项目的口令暴露面并没有因此留着**：

   与是否锁定无关。所以 P0-2 的重启仍是关键动作，锁定只是纵深防御。
