## 1. 优化①：分数口径 —— 根因是靠诊断日志打出来的

### 1.1 现象（来自 `任务_2026-11-15_D07拒答闸门实测发现.md`）

同一批问题的 `bestScore` 出现 **79.39 / 114.24 / 72.50**（双通道）与 **0.8456**（纯向量），差两个数量级。

### 1.2 诊断过程

在 `VectorChunkMerger.java` 临时加一行 INFO 日志，编译新 jar、重启 8080、跑一次 `/internal/agent/tools/search`，日志原文（节选）：

```
id=17637  ft=0.687909  maxFt=167.0375  ftNorm=0.004118  score=0.03
id=82815  ft=151.7645  maxFt=167.0375  ftNorm=76.3365   dual=true  score=76.6
```

**根因两条**：
1. `maxFt` 取的是 ngram 的 **BM25 原始分（167）**，而向量块的 `ftScore` 是**余弦（0.68）**。旧代码 `min(1, ftScore/maxFt)` 拿同一个分母除两路 → 向量余弦被压到 **0.004**，向量通道等于白干。
2. `dualHit` 分支 `ftNorm = (ftNorm + ngramNorm)/2` 里，左边的 `ftNorm` 仍是**未归一化的原始 BM25 分（151.76）**，直接进 `finalScore` → 79/114 这类值。
3. 且 `maxOf(existing, ctx)` 在双通道命中时把向量版覆盖成 ngram 版，丢了余弦分。

### 1.3 最终修复（`VectorChunkMerger.java`）

在**合并阶段**就把两路分各自归一化到 [0,1]：
- 向量块：`clamp01(ftScore)`（余弦本身已归一）
- ngram 块：`clamp01(ftScore / maxFt)`
- 双通道命中：`normFt.merge(id, n, max)` 取两路较高值（保留「两路都相关应排前」的设计意图）
- 重排阶段直接用 `normFt`，双通道可信度仍由 `dualHitBoost` 提供

诊断日志已降级为 DEBUG，未留在 INFO。

### 1.4 一次失败的改动（如实记录，已回滚）

曾把 `HybridRetriever.java:160-166` 的 `lexicalHasEvidence` 旁路整个取消，想让语义闸门始终生效。**214 条评测误拒率飙到 55.7%**（域内题余弦偏低但词法证据很强，被语义闸门误拒），远超判据 ≤10% → **回滚为原设计**，并在源码注释里写明回滚理由。

> 结论：分数口径问题由 `VectorChunkMerger` 独立解决即可；`reject-threshold` 现在对归一化后的分有意义，不需要动语义闸门。

### 8.2 根因（直接抓真实 LLM 输出，不再靠猜）

`ai-service/.env`：`LLM_BASE_URL=http://127.0.0.1:11434/v1`、`LLM_MODEL=exam-prep-7b`、`LLM_GENERATOR_NAME=ollama` —— **本地 7B，非云端**。

用 `_chat(settings.llm, _build_prompt(cluster, []), strict_json=True)` 对真实簇（doc `1000636`，块 47448–47453）抓到的原始返回只有 342 字符、4 个字段：

```json
{"title":"专题九--公司落地篇","summary":"……汇集了20多家行业标杆企业的案例……",
 "content":"……汇集了20多家行业标杆企业的案例。这些企业涵盖了……",
 "key_points":["汇集了20多家行业标杆企业的案例。","涵盖了人工智能、医疗科技、金融科技等多个领域。","……"]}
```

- **完全漏掉 `source_chunk_ids` 与 `links`** → `_validate()` 的 `isinstance(raw_ids, list)` 直接抛 `source_chunk_ids 不是数组`（37 次的主因）。
- `content` 约 60 字 → 低于 80 字下限 → `正文过短`。
- `response_format: {"type":"json_object"}` 只保证「是合法 JSON」，**不保证字段齐全**；`SYSTEM_PROMPT` 里的字段示例对 7B 约束力不足。
- 第二次重试 prompt 只泛泛写「所有字段齐全」，没告诉模型具体漏了哪个字段、正文要 400–800 字 → 第二次照样漏 → 回退抽取式。
- 该簇标题「专题九--公司落地篇」属花名册类噪声，与 `EXCLUDED_DOC_IDS={20}` 想排除的内容同类，但灌库后 doc_id 已变为 `1000636`，**排除名单失效**（另记为待办，本轮不扩大范围）。

**补充实测（主 agent 独占 Ollama）**：在 prompt 末尾显式写「必须包含 `source_chunk_ids` 数组，只能从上面 chunk_id 里选；content 正文必须 400-800 字」后，同一台 `exam-prep-7b` **单次 6.8 s** 就返回了全部 6 个字段（`title/summary/content/key_points/source_chunk_ids/links`），且 ids 合法（`doc=1005071`，`[25275,25276,25277,25278]`）。这直接证明：字段缺失是**提示词约束不足**，不是模型不会输出；也验证了「重试 prompt 点名缺失字段」这条修复方向有效。

但同一实测里 `content` 仍只有 **83 字**，远达不到 400-800 字设计目标。→ **结论**：修复后能消除「整页回退兜底」，但**正文偏薄是本地 7B 的能力上限，不是脚本 bug**。本轮不改正文下限、不拼接原文冒充蒸馏，单列为待办（换更强生成模型 / 做结构化输出微调——正好对应 §6 里 7B QLoRA 训练血缘缺失的风险）。单次约 7 s，全量 500+ 页预计 1–2 h，低于首轮按「两次失败重试」估出的 2.6 h。
