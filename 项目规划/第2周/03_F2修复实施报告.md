## 1. 改了什么

### 1.1 `training/build_dataset.py`

| 位置 | 改动 |
|---|---|
| `:67` 新增 `PLANNER_FINAL_TEMPLATES` | **10 种**问法模板（`{title}`/`{topic}` 占位），最终模板分布每档 21–29 条，无单一句壳 |

| `:381` 新增 `build_planner_final()` | 方案 C 主体：COURSEWARE 块 → `【资料】[1] 标题：首1-2句` + `【问题】模板` → `{"action":"final","answer":"…[1]。"}`；meta 含 `source/chunk_id/title/subject_id/template/qid` |
| `:448` 改 `build_planner()` | **删除 final 随机配块分支**（原 `chunks[i % len]`）；只保留 `variant 0/1` 两种 tool；配额改为 `tool_quota = limit*2//3`，尾部 `out.extend(build_planner_final(chunks, 剩余))`；tool 样本补 `meta{qid, action:"tool"}`（修 D4 无溯源问题） |
| `:427` 改 `main()` 的 chunks 查询 | 增加 `source_type` 字段（final 生成器要按 COURSEWARE 过滤） |

`build_planner_final` 的选块闸门（比 01C 的 G 规则更严，因为只取 250 条，宁缺毋滥）：

1. `source_type == COURSEWARE`（排除 QUESTION 题库原文、KNOWLEDGE 知识点桩）
2. 过 `is_clean_chunk`；去空白后 ≥120 字；标题非空
3. **跳过块内第 1 句**（chunk 从文档中间切开，首句常是半句残片），正文取第 2 句起 `clip_sentences(content,200)`
4. 正文 ≥60 字；首句 ≥25 字且以「。」结尾；首句引号/括号/书名号必须配平（多出收尾符号＝上一句的尾巴）
5. 排除含 `•`、前 60 字含 `？`、含「相关题目：」的块（问答清单/题目列表型）
6. `chunk_id` 与 `title` 双重去重；可用上限实测 **489 条**（去重后），取 300 → 实际入集 300

**关于 `pick_definition`**：deviation——它**仍在被使用**（`build_citation:321`、`build_injection:349`），因此未加「暂不使用」注释（加了会误导）。planner 不再调用它（原调用点是已删除的 final 配块分支）。

### 1.2 新增 `training/compress_for_training.py`

- 渲染口径与训练一致：`apply_chat_template(tokenize=False, add_generation_prompt=False)` → `tokenizer(text, add_special_tokens=False)`
- 超预算时**只删 user 中【资料】块尾部的整句**（逐句删除并重算 token），直到 ≤ 预算
- **assistant 一个字符都不动**（实测：非 planner 样本 assistant 与旧版 100% 一致）
- 无法压缩（无【资料】段 / 资料删空仍超）→ 丢弃并在报告里记 `i/kind/qid/chunk_id/tokens/reason`
- 输出 `--out` jsonl + `--report` json（含 before/after 条数、逐条 before/after token、丢弃清单、按原因汇总）

### 1.3 顺带改的两个文件（不改就无法满足验收项）

**失败怎么办**（出现 `[FAIL]` / `无法解析 pins 行` / exit≠0）：

1. **立即停手**，不要跑训练、不要跑评测、不要「顺手」改数据文件；
2. 先 `ls -l --time-style=full-iso training/output/data_pins.txt` 看 pins 的 mtime，再 `cat` 内容——判断是「pins 被改」还是「数据文件被改」；
3. 把 `文件名 / 期望 sha / 实际 sha / 两侧 mtime` 贴给 team-lead，由 team-lead 指定 owner 处理；
4. 需要回滚时只从 `backup/2026-11-04/` 取，且**必须连带把 pins 的行一起改**，改完再跑一次本门禁，仍失败就继续停手。

**格式兼容**：pins 每行为 `文件名  N 条  [字节数 B]  sha256=<64 hex>`，**字节数列可省略**；脚本兼容「仅条数」与「条数+字节数」两种排版，任何解析不出来的行都会显式报 `[FAIL] 无法解析` 并计入失败（fail-closed），不会静默跳过。

**注意**：数据冻结期间任何人动手前，先读 pins 的 mtime 与内容，不要凭记忆；改动 `training/data/` 或 pins 需要 team-lead 明确指令。

### 10.4 答案不得超出资料（本轮真缺陷修复）

**这个约束怎么来的**：原实现里资料只截 120 字（`material = clip_sentences(body, 120)`），答案却用完整 `body`（最长 200 字）——等于教模型「给你 120 字资料，可以合理输出 200 字」，与「只依据资料、无据拒答」的策略直接冲突，也是本轮「拒答 −40pp / 引用 −52pp」在训练侧的可疑成因。这是 QA 在验收中实际测出来的（答案中位 166 字 > 资料中位 114 字、200/250 条答案比资料长），不是设计时预见的。修法就是把答案改成资料的同一段文本，让 `answer ⊆ material` 由**构造**保证，而不是靠事后校验。

`build_dataset.py:435` 由 `body` 改为 `material`（团队已改，本次未再动）：

```python
"answer": material.rstrip("。！？") + "[1]。"
```

> **切分口径补充（回应 data-audit 的 525/533）**：资料段必须用 `meta.title` 定位——`user = "【资料】
[1] {title}：{material}

【问题】..."`，标题里有 6 条自带「：」（如 `六大AI核心概念：从幻觉到Agent`、`从幻觉到Agent：`），若按「第一个全角冒号」朴素切分，会把这 6 条错切成 `…从幻觉到Agent：…`，于是逐字相等只剩 527/533。按 `meta.title` 精确切分后是 **533/533 逐字相等**（`chunk 15489`、`17926` 两条实测两次都相等）。
> 团队另一次复核报的是「531/533（99.6%）」，我按落地文件复算是 **533/533（100%）**（`evidence/answer_subset_qa_recount.log`）。差异只在度量定义：我先把 `[1]。` 剥掉再与资料做 `==`（并统一去掉句末标点）；若直接拿 `answer` 原文去比，则因为多了 `[1]。` 会 **0/533** 全部不通过。建议统一采用「剥掉引用标记后比较」这一口径，并写进 QA 脚本。

**一个口径提醒（给 QA）**：`answer` 末尾还带引用标记 `[1]。`，所以**按原样量长度**时每一条都比 `material` 多 3 个字符（去掉句末一个句号、加 4 字引用），250/250 都会「更长」。建议判据用「**去掉 `[1]。` 后的答案正文**」与资料比：此时正文中位 94 < 资料 95、且 100% 逐字相同。若坚持按原样比较长度，则必须改设计（例如答案只取资料首句），那样会丢信息，不建议。
