## 3. F2 修复的三个阶段（含两次返工）

### 阶段一：定位（不是"选块 bug"，是"没有语料"）
- `chunks[i % 9746]` 在 `i<3044` 时恒等于 `chunks[i]` → 题目与块各自打乱后**同序号随机挂接**；
- `pick_definition` 命中率 **0/158** → 全部落到 `clip(content,120)` + `…`；
- final 的 user **一条【资料】都没有**（0/158），却输出 `[1]。` → 直接教「凭空引用」；
- 干净语料仅 1,024 块（AI/架构/OS 课件），行测 3,027 个块全是「题干+解析」，不可用。

### 阶段二：方案 C + 首次返工（答案超资料）
改为材料驱动的合成任务：user 给 `【资料】[1] 标题：正文`，assistant 出 `{"action":"final","answer":"…[1]。"}`。
第一次实现时 `material` 截 120 字、`answer` 用完整 `body`（200 字）：

| 指标 | 首次实现 | 修复后 |
|---|---|---|
| 答案中位 / 资料中位 | 166 / 114 | **94 / 95** |
| 答案比资料长的条数 | 200/250 | **0** |
| `answer ⊆ material` | 保真度 ≥0.9 仅 20% | **250/250**（子串口径） |

> 口径说明：全集按**子串**判为 533/533；按「去 `[1]。` 后逐字相等」判为 525/533，差的 8 条是资料在 120 字边界截断时差 1–2 字（如 `2.1 链表` vs `表 2.1 链表`），仍满足 answer ⊂ material 且 0 条超长。

这条缺陷的性质：等于教模型「给 120 字资料可以合理编 200 字」，与「无据拒答」policy 直接冲突——很可能是本轮拒答 −40pp / 引用 −52pp 的**训练侧成因**。

### 阶段三：可复现性（F6）
三次"对不上"全部定性为**调用口径问题**，非数据缺陷：

| 现象 | 根因 |
|---|---|
| build 复跑 4,640 / 403 | chunks 查询漏 `source_type` → final 静默 0 条，少 300 |
| mix 复跑 2,113 | 用压缩后的源跑（顺序应为 build → mix → compress） |
| 配额 450 vs 产物 491 | 450 是单桶旧常量；现版分桶 `250 tool + 250 final`，去重丢 9 得 491 |

已加 fail-closed：缺 `source_type` 或 final < 50 条直接 `SystemExit`，不再「少 300 条却显示成功」。
