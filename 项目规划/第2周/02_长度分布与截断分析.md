## 2. 三档截断落点（核心）

| 档位 | 截断条数（占比） | 答案**整段丢失** | 答案尾部被截 | 引用 `[n]` 丢失 | 答案保留比例中位 | 压缩资料可救 | 无法挽救（按 kind） | 有效 token 占比 |
|---|---:|---:|---:|---:|---:|---:|---|---:|
| 512 | **936（44.4%）** | **504** | 432 | **584** | 23.7% | 845 | mcq 84 / injection 6 / grounded 1 | 91.4% |
| 640 | 268（12.7%） | 15 | 253 | 235 | 59.8% | 251 | mcq 17 | 98.5% |
| 768 | 17（0.8%） | 0 | 17 | 13 | 90.1% | 15 | mcq 2 | 100%（基准） |

读法：

- **512 档**：44.4% 的样本被截，其中 **504 条截断点落在 user 段内**——模型看到的是「完整资料 + 没有答案」，
  等于在教它「不要回答」。剩下 432 条截在 assistant 中段，答案只保留 23.7%（中位），
  584 条连带丢掉句末 `[n]` 引用 → 训练目标里「引用」信号被系统性削弱，评测上会表现为引用率假性下降。
- **640 档**：截断降到 12.7%，答案整段丢失只剩 15 条；但仍有 253 条答案尾部被截（保留 59.8% 中位），
  235 条丢引用。这一段对 `grounded/injection` 伤害最大（占 240/268）。
- **768 档**：只截 17 条（0.8%），**零答案整段丢失**，且这 17 条的答案还保留了 90.1%。

被截样本按 kind（@512）：injection 461 / refusal 267 / grounded 124 / mcq 84；@640：injection 193 /
grounded 47 / mcq 17 / refusal 11；@768：injection 12 / grounded 3 / mcq 2。

样例（来自 evidence JSON）：

| qid | kind | 总 token | 答案 token | @512 落点 | 后果 |
|---|---:|---:|---:|---|---|
| 1505 | injection | 659 | 165 | assistant 中段 | 答案只留 11.5%，引用丢失 |
| 2255 | grounded | 680 | 161 | user 段内 | **答案整段丢失**（模型只学到资料） |

## 3. 成本侧：三档差多少

- 全量未截断 token 总量：**1,034,258**
- 按档位截断后实际喂给模型的 token 总量：
  - 512 → 945,363（**91.4%**）
  - 640 → 1,019,248（**98.5%**）
  - 768 → 1,033,874（**100.0%**）
- 也就是说：**512 只省 8.6% 的 token，却让 44% 的样本失去完整答案**；640 比 768 只省 1.5%，却多截 251 条。

显存/步速（观测值，口径不完全可比，仅作量级参考）：

| 档位 | 显存 | 步速 | 来源 |
|---|---|---|---|
| 768 | 未记录 | `full_train.log` 100 步均值 **35.9 s/step**（该次 max-length 未写入日志） | 训练日志 |
| 640 | **7.8 / 8.2 GB** | **≈195 s/step** | 团队记录（与上行的 batch/后台负载不同，勿直接相减） |
| 512 | 未跑完 | — | — |

> 步速差异主要来自批内最长样本与显存压力，不能按 token 比例线性外推；但 token 总量差异（8.6% / 1.5%）
> 说明「降 max_length」省不下多少算力，砍掉的却是监督信号。

## 4. 若坚持 512：压缩资料能不能救

判据：把 user 里的 `【资料】…` 整段去掉、只留 `【系统前缀 + 问题】+ 完整答案`，重算 token 是否 ≤ 512。

- 936 条超长样本中，**845 条（90.3%）可通过压缩资料塞进 512**；
- 剩下 **91 条救不了**：mcq 84、injection 6、grounded 1。mcq 没有资料可压，超长来自题干 + 四个长选项；
  要进 512 只能按句压缩题干或直接丢弃（占全量 4.3%）。

可行性判断：**可以救，但代价是必须改数据构造**（`build_grounded` / `build_injection` 里对资料做按句截断，
并保证答案与引用完整），而不是把 `--max-length` 调小就算完。只调参数 = 504 条「无答案样本」。

640 档同理：251/268 可救，剩 17 条 mcq 需另处理。

## 5. 建议策略

1. **训练用 768（当前默认）**。截断 0.8%、零答案整段丢失，token 成本仅比 640 多 1.5%；
   P99 = 759 < 768，绝大多数样本天然装得下。
2. **若显存卡死在 640**：先做「资料按句压缩到预算内」的预处理（预算 = 640 − 答案 tokens − 固定前缀），
   预期把 268 条降到 ~17 条；再对这 17 条 mcq 长题按句压缩题干，压缩失败则丢弃（0.8%）。
3. **不要用 512**：即使压缩资料仍有 91 条不可救，且当前直接用 512 会让 504 条样本变成「只有资料没有答案」，
   与「拒答纪律」「引用纪律」两项验收目标直接冲突。
4. **与 F1 的关系**：F1（答案正文截断）是**数据构造期**截断；本报告是**训练期** `max_length` 截断，
   两者叠加会让「答案不完整」在数据与训练两头同时发生，建议一并修掉。

## 7. 口径限制

- 假设 SFTTrainer 使用 **右截断**（`tokenizer.truncation_side = right`，TRL 1.17.1 默认）；
  若后续启用 packing 或改成左侧截断，截断落点结论需重算。
- token 数按 `add_special_tokens=False` 计算，与训练时一致；不同 tokenizer 版本可能有个位数差异。
- 「压缩资料可救」只判断**长度是否装得下**，不判断压缩后语义是否仍足够作答；语义质量需另行抽检。
