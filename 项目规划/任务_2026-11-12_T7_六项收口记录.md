## 2. D05：限流 XFF 伪造绕过（PASS）

**代码事实**：`ClientIpResolver.java:24-30` 规则 —— 只有 `remoteAddr` 在 `trusted-proxies` 内才采信 XFF；否则一律用 `remoteAddr`。
**配置**：`application.yml:143` `trusted-proxies: ${APP_RATE_LIMIT_TRUSTED_PROXIES:127.0.0.1,::1}`。

**构件重建**：

| 项 | 构建前 | 构建后 |
|---|---|---|
| jar SHA256 | `fd791b0ec2f324af…c02bb70` | `28840a78bf22c02b…48163cb6f` |
| 大小 | 78,073,961 B | 78,074,038 B |
| 构建 | — | `mvn -B -DskipTests package` **BUILD SUCCESS**，15.6s |

**实测（新 jar 启动后，限流桶为空）**：

源 IP = `10.200.87.37`（**非**可信代理），每次请求换一个 `X-Forwarded-For`：

```
第 1 次  XFF=1.2.3.1  ->  HTTP 200
第 2 次  XFF=1.2.3.2  ->  HTTP 200
第 3 次  XFF=1.2.3.3  ->  HTTP 200
第 4 次  XFF=1.2.3.4  ->  HTTP 200
第 5 次  XFF=1.2.3.5  ->  HTTP 200
第 6 次  XFF=1.2.3.6  ->  HTTP 429   ← 伪造头未产生新桶
```

**对照（源 IP = `127.0.0.1`，属可信代理，每次换 XFF）**：3 次均 200。
这是**预期行为**而非漏洞：Nginx 转发场景下后端看到的对端就是本机/容器网段，必须采信其写入的真实客户端 IP；恶意客户端直连 8080 时对端不在信任列表，XFF 被完全忽略（上表已证）。

**为什么只到 PARTIAL**（T8 下调）：
- T2 判据⑤要求「**8 个真实客户端**」实测，本轮只做了 2 个源 IP（LAN + 回环），未凑齐 8 个；
- T8 复现时**前 5 次不是 200 而是 400**（请求体/窗口差异），核心结论（第 6 次 429）不受影响，但说明「前 5 次 200」不是稳定可复现的表述，已在表中保留原始输出、不做修饰。
