## 4. 已确认的三个事实（有实测支撑）

### 事实 1：`ftScore` 是「全文相关度原始分」，不是 0–1

`ChunkContext.java:21` 字段注释原文：`@param ftScore 全文相关度原始分（LIKE 降级时为 0）`。
→ ngram 路的 `ftScore` 是 BM25 量级（几十），向量路才是余弦（0–1）。**两路混在同一字段里**。

### 事实 2：`finalScore` 的归一化有「整段跳过」的出口

`VectorChunkMerger.java:88-91, 127-135`：

```java
double maxFt = ngramContexts.stream().mapToDouble(ChunkContext::ftScore).max().orElse(0.0);

double ftNorm = ctx.ftScore();
if (!dualHit && maxFt > 0 && ctx.sourceType() != null) {
    ftNorm = Math.min(1.0, ctx.ftScore() / maxFt);          // 归一化
} else if (dualHit && maxFt > 0) {
    ftNorm = (ftNorm + Math.min(1.0, ctx.ftScore() / maxFt)) / 2.0;
}
// 若 maxFt <= 0（ngram 侧 ftScore 全为 0，如 LIKE 降级 / 块被剔除干净）
// → 两个分支都不进 → ftNorm 保持原始 ftScore（几十）→ score = 几十 * 1.0
double score = ftNorm * r.getFulltextWeight()   // 1.0
        + titleHit * 0.30 + kpBoost * 0.25 + fresh * 0.15 + hotNorm * 0.10;
```

权重 `application.yml:303-307`：`fulltext-weight 1.0 / title 0.30 / knowledge 0.25 / fresh 0.15 / hot 0.10`，即 **正常 score 上限约 2.05**。**79 / 114 只能来自「未归一化的原始 ftScore」这一条路径**。

### 事实 3：`lexicalHasEvidence` 的 0.15 门在 `VECTOR_HYBRID` 下几乎恒真

`HybridRetriever.java:160-166`：

```java
boolean lexicalHasEvidence = !ngram.contexts().isEmpty()
        && ngram.bestScore() >= properties.getRetrieval().getRejectThreshold();   // 0.15
boolean semanticReject = applyGate && vectorEnabled && !lexicalHasEvidence
        && vectorBest > 0 && vectorBest < 0.58;
```

ngram 侧分数是几十量级 ⇒ `>= 0.15` 恒真 ⇒ **`semanticReject` 恒为 false ⇒ 语义闸门在双通道模式下永远不生效**。
`application.yml:289-291` 的注释自己写着「『区块链智能合约怎么写』这类…只有它拦得住」——**它被自己的 0.15 旁路条件关掉了**。

## 5. 待验证的根因（**假设，未证实，不得当结论**）

`maxFt <= 0` 是「跳过归一化」的触发条件之一，但本轮**没有直接观测到 `maxFt` 的值**（未加日志、未打断点）。可能的触发场景：

| 假设 | 依据 | 如何验证 |
|---|---|---|
| H1：`ngramContexts` 的 `ftScore` 全为 0（LIKE 降级）→ `maxFt=0` | `ChunkContext.java:21` 明写「LIKE 降级时为 0」；而 mode 仍是 `VECTOR_HYBRID`（向量非空即可为该 mode） | 加一行 `log.debug` 打 `maxFt` 与 top1 原始 `ftScore`，复跑同题 |
| H2：`maxOf(existing, ctx)` 选中的 ngram 块 `ftScore` 大于 `maxFt`（例如 `maxOf` 比较的是别的字段） | `VectorChunkMerger.java:113` | 单测直接构造两路输入断言归一化结果 |
| H3：某条路径绕过了 `merge`（如 `VECTOR_HYBRID` 但 `dualHit` 判定异常） | `:130-135` 两个分支都需要 `maxFt > 0` | 同上 |

> **三条都指向同一处代码**：归一化的**前置条件太脆弱**（依赖 `maxFt > 0` 与 `sourceType != null`），一旦不满足就静默退化到原始量纲，而下游 `reject-threshold` 仍按 0–1 语义使用。

## 6. 对「D07 该怎么修」的结论（按优先级，不含猜测）

| 优先级 | 动作 | 理由 |
|---|---|---|
| **P0** | **统一分数口径**：让 `finalScore` 恒在 0–1（归一化失败时取 0 或用向量分兜底，而不是保留原始分），并加一条单测锁住「任何模式下 `finalScore ∈ [0, 2.1]`」 | 量纲不统一时，`reject-threshold`、`semantic-reject-score`、`Recall@5` 三个指标互相不可比 |
| **P0** | **`lexicalHasEvidence` 改用归一化后的分**（或在 `VECTOR_HYBRID` 下改用 `vectorBest`），取消 `0.15` 对原始分的比较 | 现在等于把语义闸门永久关掉 |
| P1 | 修好后**固定条件重跑 D07**（语料/模型/promptVersion/时间戳四固定），拿真实基线 | 现有 6/10 是在量纲错误的链路上测的 |
| P1 | 再谈 `reject-threshold` / `semantic-reject-score` 标定，且必须用全量 214 条 | 10 条样本不足以标定（`application.yml:298` 记 0.58 来自全量实测） |
| P2 | 重标评测集（Q1 移出应拒集；Q4「大熊猫」待产品裁定） | 见 `任务_2026-11-15_D07误召回根因分析.md` 订正 3 |
