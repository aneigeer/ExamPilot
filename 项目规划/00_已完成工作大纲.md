## 四、第 3 周：训练环境稳定性

**主题**：证明「训练能跑完、能恢复、能复现」。

**关键决策：7B → 3B**

| 配置 | 显存峰值 | 结论 |
|---|---|---|
| 7B / 640 | 7.9 GB | 超限 |
| 7B / 512 | 7.9 GB | 无改善，且 42% 样本被截断 |
| 7B / 384 | 9.58 GB | 更差 |
| **3B / 640** | **4.36 GB** | **采用** |

结论：显存瓶颈不是序列长度，是 7B 权重 + CUDA 上下文 + 分页优化器的固定开销。

**交付物**
- `01_训练脚本步数口径核验.md` — 一步 16 条、50 步 = 37%、resume 必备文件
- `02_资源方案与停止条件.md` — 本地/云/小模型对比 + 11 条停止条件
- `03_短跑子集与加载完整性.md` — 200 条子集，确认无二次截断
- `05_验收方案.md` + `scripts/accept_week3.py`

**验收结果（A1–A6 全 PASS）**

| 项 | 结果 |
|---|---|
| A1 短跑完成 | 20/20 步，退出码 0 |
| A2 步数对账 | 20 步 = 320 ÷ 16，误差 0 |
| A3 检查点完整 | 四件齐全，optimizer/adapter = 1.02 |
| A4 恢复正确 | global_step 10→12，loss 跳变 7.6% |
| A5 显存步速 | 4.4 G，无共享内存回退 |
| A6 可复现 | 两次起跑前 10 步 loss 差 **0.000000** |

**顺带修掉的 4 个脚本缺陷**
1. `--smoke N` 会把数据截成 `N×4` 条（实际是 4 个 epoch）
2. `logging_steps=5` 硬编码（20 步以内的短跑不记 loss）
3. `eval_strategy` 未暴露（传了 eval_dataset 却从不评估）
4. 检查点保存非原子（卡死留下缺 `trainer_state.json` 的残件）

## 八、跨周沉淀的方法论

| 教训 | 出处 |
|---|---|
| 指标必须写清量法（子串/逐字/含标记三种结果） | 第 2 周 |
| 「跑完了」不等于「训练有效」（`--smoke` 陷阱、残检查点） | 第 3 周 |
| 显存不够时换模型比降长度有效 | 第 3 周 |
| 长训练必须「每 N 步存档 + 断点续跑」，不能指望一次跑完 | 第 4 周 |
| 基线必须与微调同量化档，否则比较无意义 | 第 4 周 |
| 训练日志必须回显完整参数，否则事后无法证明跑的是冻结配置 | 第 4 周 |
| 量化档会改变行为，安全项必须先对齐量化再比较 | 第 5 周 |
| 自动判据在抽取式答案上会失去区分力，必须保留人工终判 | 第 6 周 |
| summary 与 records 必须一致；判据变了要重判并保留旧版 | 第 6 周 |
| n=50 时 1 条=2pp，显著性要看不一致对与 CI，不能只比百分数 | 第 6 周 |

## 十一、协作规程（自 2026-11-07 起强制）

本项目所有任务按**三段式**执行，细则见 `项目规划/00_协作规程.md`：

```
① 拆解（主 agent）→ ② 分发执行（子 agent，一任务一 agent）
                    → ③ 独立验收（专职验收 agent，禁止执行者自查）
                    → ④ 汇总落盘（周记录 + 本大纲）
```

- **执行者与验收者必须是不同的 agent**；
- 验收输出 PASS / PARTIAL / FAIL 三档，**PARTIAL 不得写成 PASS**；
- 派活必须写全「任务 / 输入 / 产出 / 判据 / 禁止 / 回报」六项；
- 需要本机 GPU、Ollama 的动作由主 agent 执行，子 agent 只出方案与脚本。

已按此规程执行的任务见规程第 6 节。
