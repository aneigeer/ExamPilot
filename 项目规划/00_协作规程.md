# 协作规程（自 2026-11-07 起强制执行）

> 适用范围：本项目所有需要执行与交付的任务。
> 生效方式：用户明确要求「以后都要这样」，本文件为长期约定，不随单次任务失效。

---

## 1. 三段式流程

任何非平凡任务，一律按下面三段走，**不得由主 agent 一个人从头做到尾**：

```
① 拆解 → ② 分发执行（子 agent）→ ③ 独立验收（专职子 agent）→ 汇总落盘
```

### ① 拆解
主 agent 负责把任务拆成**互相独立、可并行**的子任务，每个子任务满足：
- 有明确的输入（文件路径、数据 sha、模型名）；
- 有明确的产出（文件路径 + 格式）；
- 有明确的完成判据（能被别人照着复核）。

拆解结果写进当周执行记录或计划文档，**先写清楚再派活**。

### ② 分发执行
- 每个子任务派给一个子 agent，**一个 agent 只负责一个子任务**；
- 派活时必须在消息里写全：背景、输入、产出路径、判据、禁止事项（如「不要跑推理」「不要改冻结数据」）；
- 有依赖关系的子任务串行，无依赖的并行；
- 子 agent 只负责「做」，不负责「判自己对」。

### ③ 独立验收（关键）
**执行者与验收者必须是不同的 agent。** 验收 agent 的职责是挑错，不是确认：

- 验收对象：所有子任务的产出（文件、数字、结论）；
- 验收方式：**独立复核**，不信注释、不信汇报，自己算一遍、自己读一遍；
- 输出：逐项 PASS / FAIL / PARTIAL + 证据（文件路径、行号、数字）；
- 有 FAIL 时，退回原执行 agent 修复，修完再验；
- **验收 agent 不得修改被执行的内容**，只能出判定。

### ④ 汇总落盘
主 agent 汇总验收结果，写入：
- 当周 `00_第N周执行记录.md`（结论、数字、遗留问题）；
- 总纲 `00_已完成工作大纲.md`（进展与关键结论）。

## 2. 角色分工（本项目固定）

| 角色 | 承担者 | 职责 |
|---|---|---|
| 主理人 | 主 agent | 拆解、派活、汇总、对外汇报；**不代写子 agent 的专业产出** |
| 数据 | data-audit | 数据构造、审计、口径核对 |
| 评测 | eval-harness | 评测方案、脚本、判分口径 |
| 导出/归档 | train-export | 合并、转换、登记表、SHA |
| 验收 | **qa-acceptance** | **独立验收所有产出，出 PASS/FAIL/PARTIAL** |
| 推理执行 | 主 agent | 需要本机 GPU/Ollama 的动作由主 agent 跑（子 agent 易与训练抢资源） |

---

## 3. 验收判据的三档

| 判定 | 含义 | 处置 |
|---|---|---|
| **PASS** | 判据全部满足，证据齐全 | 可进入下一阶段 |
| **PARTIAL** | 部分满足，或证据不全 | **不阻断流程，但阻断「完成」结论**；产物不得作为正式交付 |
| **FAIL** | 判据不满足 | 退回执行者修复，修完重验 |

**禁止把 PARTIAL 写成 PASS。** 第 4 周曾出现「训练只跑 100/135 步却按完成汇报」的风险，就是靠这一条拦下来的。

## 4. 派活模板（每次必须写全）

```
【任务】一句话说明要交付什么
【输入】文件路径 / 数据 sha / 模型名 / 上游产物
【产出】具体文件路径 + 格式要求
【判据】怎样算做完（可被第三方复核）
【禁止】不能碰什么（冻结数据、GPU、其他 agent 的目录）
【回报】≤10 行，含关键数字
```

---

## 5. 反例（明确禁止）

| 反例 | 为什么禁止 |
|---|---|
| 主 agent 自己写脚本、自己跑、自己宣布通过 | 没有独立验收，错误无人发现 |
| 让执行者顺便「自查一下」 | 自查不等于验收，执行者有确认偏误 |
| 验收 agent 只读汇报不读产物 | 汇报可能夸大，必须以文件为准 |
| 子任务没有明确判据就派活 | 无法验收，最后只能靠感觉 |
| 把 FAIL 说成「小问题，先过」 | 第 5 周就是靠 FAIL 才发现 Q4_0 破坏拒答 |
