## 3. 解码参数（A/B 完全一致）

| 参数 | 值 | 说明 |
|---|---|---|
| `temperature` | **0** | 贪心；但 GPU/批处理仍可能带来非确定性，所以 L1 不要求 100% |
| `top_p` | **1** | 与 temperature=0 一起构成"不改分布"的对照 |
| `num_predict` | **200** | 覆盖绝大多数答案（训练答案 P99=343 token，抽检只看前 200 足够判断一致性） |
| `num_ctx` | **4096** | 与 Modelfile 一致；输入 ≤640 token |
| `seed` | **7** | 与评测一致 |
| 调用方式 | **串行**，单条 `timeout=120s`，失败重试 **1** 次（间隔 2s/4s） | 并发会干扰显存与 KV cache，破坏可比性 |

> 两侧必须用同一份 `options`：脚本把 `DECODE` 硬编码在 payload 里，A/B 共用同一 dict，避免手误。

## 4. 三层判据与阈值

| 层 | 判据 | 计算方式 | 阈值 | 理由 |
|---|---|---|---|---|
| **L1 逐字一致** | `a.strip() == b.strip()` | 直接比对 | **≥ 30%**（6/20） | 量化必然改措辞（Q4_0 与 F16 权重不同），逐字一致只可能出现在短答案/拒答句上；30% 是「短样本+模板化输出」的合理下界，低于它要怀疑不是同一模型 |
| **L2 语义等价** | 去标点/空白后完全相同，**或** 引用序列（`[n]` 的顺序与个数）一致且归一化相似度 ≥ 0.9 | NFKC + 去标点 + `SequenceMatcher` | **≥ 90%**（18/20） | 量化只应带来用词/顺序微变，不应改变结论或引用编号；允许 2 条因措辞差异被判不等 |
| **L3 行为一致** | `mcq_acc / cite_rate / refusal_ok / planner_ok / injection_ok` 两侧差值 | 复用 `eval_v2.score_sample`（anchor 档） | **\|Δ\| ≤ 5pp** | 行为指标是交付真正关心的；5pp 是"可接受漂移"的经验线 |

**L3 的重要限制（必须写进报告）**：20 条清单里每类只有 4 条，`mcq_acc` 分母是 8（mcq+grounded），
**最小可分辨步长是 25pp / 12.5pp**，5pp 阈值在这个样本量下**无法分辨**。
因此 L3 在本清单上只作**方向性参考**（例如「引用率从 4/4 掉到 2/4」这种明显恶化能被抓到），
**权威结论以全量 250 条评测为准**；报告里会固定打印这条提醒。

### 4.1 判定组合（结论口径）

| L1 | L2 | L3 | 结论 |
|---|---|---|---|
| ≥30% | ≥90% | 全部 ≤5pp | **通过**：量化可交付 |
| ≥30% | ≥90% | 单项 10–25pp | **警告**：查 L3 差异是否集中在某一 kind；若集中在 planner/refusal，需人工看 10 条 |
| <30% | ≥90% | — | **可疑**：多半是采样/模板不一致（检查 `num_ctx`、Modelfile 的 SYSTEM 是否相同） |
| 任意 | **<90%** | — | **不通过**：量化已改坏输出，停止交付，回退 F16 |

## 5. 产物指纹（「评测的文件 = 交付的文件」）

脚本在正式运行时记录三样东西，缺一不可：

1. **本地 GGUF 文件 sha256**（`--file-a/--file-b`，流式计算，不占内存）；
2. **Ollama digest 与 size**（`/api/tags`，证明导入的 blob 与文件对应）；
3. **清单 sha256 + 两个数据文件 sha**（证明用的是哪版题）。

报告中以表格呈现，例如：

| 侧 | 模型 | digest | size | 文件 sha256 |
|---|---|---|---|---|
| A | `exam-3b-v1-f16` | `<digest 前 16>` | 6.17 GB | `<sha 前 16>` |
| B | `exam-3b-v1-q4_0` | `<digest 前 16>` | 1.74 GB | `<sha 前 16>` |

> 只要「文件 sha ↔ Ollama digest ↔ 评测命令里的模型名」三者能对上，就能证明评测用的就是交付物。
> 注意 Ollama 的 `quantization_level` 字段不可信（7B 曾把 Q4_0 显示成 F16），判定档位要用 GGUF 头
> `general.file_type == 2` 与张量数 435（见第 4 周 `02_3B基线方案.md` §2）。

## 7. 判读与处置

| 现象 | 可能原因 | 处置 |
|---|---|---|
| L1 很高（>70%） | 该 kind 输出高度模板化（refusal 整句固定） | 正常，不用处理 |
| L2 <90%，差异集中在 grounded/injection | 引用编号被改写（`[1]`→`[2]`）或答案被截断 | 查 `num_predict=200` 是否截断；查 Modelfile 是否一致 |
| L2 ≥90% 但 L3 里 `planner_ok` 掉 | 量化后 JSON 尾部被截断/多出文本 | 人工看 4 条 final；必要时提高 `num_predict` 重测 |
| 大量调用失败 | 模型未导入 / 显存不足 / 端口占用 | 先 `ollama list` 确认；错误会在 json 的 `failures` 里逐条列出 |
| 一侧全部输出为空 | Modelfile 缺 `stop` 或 system 冲突 | 对比两侧 Modelfile 的 SYSTEM 段 |

**不通过（L2<90%）的处置顺序**：① 复核两侧是否同一份 Modelfile 模板；② 复核 `num_ctx/num_predict`；
③ 用 `tools/check_gguf_quant.py` 确认 Q4_0 档位与张量数 435；④ 仍不过 → 交付 F16（体积 6.17 GB，
推理更慢但精度无损），并在交付说明里写明原因。

---

## 8. 限制

1. **20 条只能证明"没坏"，不能证明"没退化"**：行为指标的统计功效不足，全量评测仍是唯一权威；
2. `temperature=0` 不等于逐位确定性（GPU 归约顺序、KV cache 实现），L1 不高是正常的，不要当故障；
3. 抽检覆盖的是「短答案 + 五类代表题」，长答案、边界格式（超长 JSON）可能未被覆盖，
   这些靠全量评测与人工抽检补；
4. 清单不含 `citation` / `wiki` 类（holdout 里本来就没有），这两类不在本次抽检范围。
