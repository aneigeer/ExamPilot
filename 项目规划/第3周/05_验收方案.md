### 1.1 为什么 A3 必须是相对判据而不是绝对阈值

初版把门槛写成 `optimizer.pt ≥ 60MB`，这个数是从 7B 推出来的（40.37M 可训练参数 × 8bit 双状态 ≈ 82MB）。
换成 3B 后，可训练参数降到 29.93M，优化器状态本来就只有 58.6MB —— **同一根线会把正常的 3B 检查点判死**（实测就发生了）。

改成 `optimizer/adapter ≥ 0.5` 后两边都成立：

| 场景 | adapter | optimizer | 比值 | 判定 |
|---|---|---|---|---|
| 7B（r=16） | 77MB | 82MB | 1.07 | PASS |
| 3B（r=16） | 57MB | 58.6MB | 1.03 | PASS |
| 3B 残件（历史事故） | 77MB | 0.286MB | 0.004 | **FAIL** |

再叠一条 `> 10MB` 的绝对下限，防止"adapter 也很小"时比值失真放过残件。**286KB 在任何比例下都会被拦。**

## 1. 为什么需要这套验收

历史教训（本轮已确认的事实）：

- `checkpoint-10` 有 `adapter_model.safetensors`，但 **`optimizer.pt` 只有 286KB**、**没有 `trainer_state.json`** ——
  这种"有检查点"其实不可恢复：优化器状态丢了，恢复后等于重新起步，续训没有意义。
- 训练日志可能被 kill、可能停在 91/100 而无人察觉（v1 就是这样：`full_train.log` 停在 91/100，却按"已完成"报了 100 步）。
- Windows 单卡 8GB 会走**共享内存回退**：不报 OOM，但步速掉 5–10 倍，日志里只留一行 `Shared Usage`。

所以验收必须回答三件事：**跑完了吗？产物能恢复吗？恢复后的训练还连着吗？**

## 2. 六项验收（判据 / 证据来源 / 阈值 / FAIL 处置）

| 编号 | 项 | 判据 | 证据来源 | 阈值 | FAIL 处置 |
|---|---|---|---|---|---|
| **A1** | 短跑完成 | 达到预期步数 **且** 有正常结束证据 | 日志完成标记 `train_runtime` / `train_loss` / `[done]`；或 `--exit-code 0` | 步数 ≥ 预期，且（退出码=0 或 有完成标记） | 被 kill / 崩了：查日志尾部异常栈，重跑；连续两次崩则缩小 `--samples` 定位崩点 |
| **A2** | 步数对账 | `global_step == ceil(样本数 / (batch × accum))` | `trainer_state.json` 的 `global_step`（主）、日志最大 step（辅） | **误差必须为 0** | 口径错（如 dataloader 丢尾、`max_steps` 覆盖）：核对启动参数与 `--samples`，改 `train_qlora.py` 或改传入值后重跑 |
| **A3** | 检查点完整 | 目录内含 `adapter_model.safetensors` + `optimizer.pt` + `trainer_state.json` + `scheduler.pt` **四件齐全** | `ls -l` 文件清单与体积 | **相对判据**：`optimizer.pt ≥ 0.5 × adapter_model.safetensors` **且** `> 10MB`（绝对下限） | 检查 `save_only_model` / `save_optimizer=False` / 磁盘写满；改配置后**重跑并存检查点**，不接受"只有 adapter" |
| **A4** | 恢复正确 | ①最终 `global_step` > 存档步数（没回退、且确实继续训练）②恢复后日志有 >存档步的 loss ③恢复点前后 loss 相对跳变 ≤50% | `--saved-step` + `--resume-log` + `--resume-ckpt-dir` | 跳变 **>50% 判 FAIL**；无 `--resume-ckpt-dir` 时降为 **WARN**（日志能证明续训但缺 global_step 交叉验证） | 跳变 = 优化器状态没恢复或数据顺序重置 → 检查 `resume_from_checkpoint` 是否真的传入、`optimizer.pt` 是否完整（回到 A3） |
| **A5** | 显存与步速 | 记录峰值显存、步均耗时；识别共享内存回退与掉速 | 日志 `Shared Usage: N MB`、`max_memory_allocated`、`s/it` 或 `train_runtime/steps` | `Shared Usage > 512MB` 判 **WARN**；步速 **> 2× 基线**判 **WARN** | WARN 不阻断结项，但必须换配置（降 `max_length` / 减 `num_ctx` / 关其它占卡进程）后复测，否则 60s/步 的估算全部失效 |
| **A6** | 可复现 | 同配置连跑两次，前 N 步 loss 序列逐点一致 | 两次跑的 `trainer_state.log_history` 或日志 loss 行 | 绝对差 ≤ **0.01**（loss 量级 2.0–2.6，0.01 ≈ 0.4%；CUDA 非确定性算子正常抖动远小于此） | 不一致 → 固定 `seed` / 关 `dataloader_num_workers` 随机性 / 检查数据顺序；若仍不一致，说明配置里有未固定项，**不可用于结项** |

**判定汇总规则**：A1–A6 中任一 **FAIL** = 不可进入结项；**WARN / SKIP 不阻断**，但必须在报告里列明"未验证项"。

## 3. 脚本用法

```bash
# 基础：短跑完成 + 步数对账 + 检查点完整 + 显存步速
.venv-ai/Scripts/python.exe 项目规划/第3周/scripts/accept_week3.py \
  --log 项目规划/第3周/evidence/shortrun_a.log \
  --ckpt-dir training/output/<run-dir> \
  --samples 200 --batch 1 --accum 16 --exit-code 0 \
  --json-out 项目规划/第3周/evidence/accept_week3.json

# 加恢复（A4）与复现（A6）
.venv-ai/Scripts/python.exe 项目规划/第3周/scripts/accept_week3.py \
  --log ... --ckpt-dir ... --samples 200 --exit-code 0 \
  --resume-log 项目规划/第3周/evidence/shortrun_resume.log \
  --resume-ckpt-dir training/output/<run-dir> \
  --saved-step 4 \
  --run2-log 项目规划/第3周/evidence/shortrun_b.log \
  --baseline-step-seconds 60
```

**退出码**：0 = 无 FAIL（可结项）；1 = 有 FAIL。WARN/SKIP 不影响退出码。

### 3.1 关键参数

| 参数 | 说明 |
|---|---|
| `--samples` | 训练样本数，A2 的除数来源；传错会导致 A2 误判 |
| `--exit-code` | 训练进程退出码；不传则必须有完成标记，否则 A1 FAIL（防止"被 kill 也算跑完"） |
| `--saved-step` | 存档时的 global_step；不传则取 `trainer_state` 里最后一个 loss 点 |
| `--resume-ckpt-dir` | 恢复跑结束后的产物目录；**建议必传**，否则 A4 只能降级 WARN |
| `--baseline-step-seconds` | 基线步耗时（默认 60s/步），A5 用它判"是否 >2× 掉速" |
| `--loss-tol` | A6 逐点容差，默认 0.01 |

### 3.2 解析健壮性（已自测）

脚本不假设固定列，做了三层兜底：

1. 先去 ANSI 控制码，再把 tqdm 的 `\r` 刷新**折叠成最后一行**（否则进度条会刷出上万条垃圾行）；
2. loss 先按 `{...'loss'...}` 整体 `json.loads`，失败再逐字段正则提取（兼容 HF Trainer 不同版本的日志格式）；
3. 主证据取 `trainer_state.json` 的 `log_history`，日志只用来补"退出码 / 耗时 / 显存 / Shared Usage"。

**四个场景的自测结果**（假数据，验证判定方向正确）：

| 场景 | 构造 | 期望 | 实测 |
|---|---|---|---|
| 正常 | 4 步跑完 + 四件齐全 + 连续续训 | 全 PASS | ✅ A1–A6 全 PASS |
| 残检查点 | `checkpoint-10` 无 `trainer_state.json`/`scheduler.pt`，`optimizer.pt` 286KB | A1、A3 FAIL | ✅ A1 FAIL（无完成标记）、A3 FAIL（缺 2 件 + optimizer 仅 286KB） |
| 恢复跳变 | 恢复后 loss 2.25 → 4.50 | A4 FAIL | ✅ A4 FAIL（跳变 100% > 50%） |
| 共享内存 | `Shared Usage: 900 MB`、120s/步 | A5 WARN | ✅ A5 WARN（900MB > 512MB） |
