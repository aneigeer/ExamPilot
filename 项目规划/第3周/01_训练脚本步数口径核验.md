## 0. 结论先行

| 问题 | 答案 |
|---|---|
| 一个 optimizer step 吃多少条样本 | **16 条**（`1 × 16 × 1`） |
| 「50 步」覆盖多少样本 / 占比 | **800 条 / 37.1%**（一个 epoch 的 135 步里只跑了 37%） |
| 「50 步」定性 | **冒烟，不是「训练过一轮」**（未跑满一个 epoch，LR 也从未走完余弦调度） |
| 跑满 1 epoch | **135 step**；按 60 s/step ≈ **2h15m**（需实测确认步速） |
| `--resume` 恢复什么 | 模型权重 + optimizer + scheduler + `global_step`，**但必须有 `trainer_state.json`**；历史 `checkpoint-10` **无法恢复** |
| 历史 50 步为什么连 checkpoint 都没有 | `save_steps` 默认 **100**，50 步 < 100，一个都没存；必须显式 `--save-steps 10` |

## 2. 三个公式与结果

### 2.1 一个 optimizer step 的样本数

```
samples_per_optimizer_step
  = per_device_train_batch_size × gradient_accumulation_steps × n_gpu
  = 1 × 16 × 1
  = 16 条
```

依据：`TrainingArguments` 的步数计算用 `total_train_batch_size = per_device_batch × grad_accum × world_size`（`trainer.py` 内 `get_total_train_batch_size`），且 `global_step`（`trainer.state.global_step`，也就是 `save_steps` 与 `max_steps` 的单位）只在梯度累积完成后 +1。

### 2.2 「50 步」覆盖多少、占比多少

```
1 epoch 的总 step = ceil(N / 16)            # N = 2,156
                 = ceil(2,156 / 16)
                 = ceil(134.75)
                 = 135 step                # 前 134 步各 16 条（2,144 条）+ 最后 1 步 12 条
50 step 覆盖样本  = 50 × 16 = 800 条
占比              = 800 / 2,156 = 37.1%（= 50 / 135）
```

因为 `max_steps(50) < steps_per_epoch(135)`，**这 800 条互不重复**（sampler 一轮内不重复；`drop_last=False` 只在最后一步生效）。

### 2.3 「50 步」对 2,156 条意味着什么：**冒烟**

- 只覆盖 **37.1%** 的样本，**没有跑满一个 epoch**；
- `warmup_steps=30`，50 步里前 30 步都在预热（60%），LR 到第 30 步才达峰，再走 20 步余弦降到 0 —— 模型几乎没在「峰值 LR」下训练；
- `save_steps` 默认 100 > 50 → 一次都不会存盘（这也解释了「50 步跑完却没有任何 checkpoint」）；
- 与冻结数据 2,156 条的规模相比，50 步 = 800 个样本迭代 = **冒烟级验证**（只够证明「能跑起来、显存不炸、loss 在降」）。

**结论：50 步 = 冒烟。要算「训练过一轮」，至少 `max_steps ≥ 135`（1 epoch），建议 270–405 步（2–3 epoch）。**

### 2.4 跑满 1 epoch 的耗时

```
135 step × 60 s/step ≈ 8,100 s ≈ 135 min ≈ 2h15m
```

- 60 s/step 来自团队实测口径（640 token、8GB、batch1×accum16）；**需实测**：历史所有 run 都没跑满，没有可用的端到端计时。
- 敏感性：45 s/step → ≈1h41m；75 s/step → ≈2h49m。
- 3 epoch（405 step）按 60 s/step ≈ **6h45m**。

### 2.5 `--smoke N` 的真实语义（容易误读，单独标出）

```python
ds["train"] = ds["train"].select(range(min(N * 4, len(ds["train"]))))   # 数据变成 N*4 条
max_steps = N                                                            # 步数上限 N
```

→ `steps_per_epoch = ceil(N*4/16) = N/4`，而 `max_steps = N`，于是 `num_train_epochs = ceil(N / (N/4)) = 4`：

**`--smoke 50` 不是「在 2,156 条上跑 50 步」，而是「在 200 条上跑 50 步（重复 4 遍）」。** 这也是 20 步冒烟时代 `train_metrics.steps=5` 一类记录的来源（数据被截小后 epoch 反复）。

## 3. `max_steps` 与 `num_train_epochs` 的关系（代码实证）

`transformers 5.22.1`，`trainer.py:2481-2516`：

```python
max_steps = args.max_steps
epoch_based = max_steps < 0                     # max_steps<0 才看 epochs
...
num_update_steps_per_epoch = max(len_dataloader // grad_accum + int(len_dataloader % grad_accum > 0), 1)
if epoch_based:
    max_steps = ceil(args.num_train_epochs * num_update_steps_per_epoch)
...
if args.max_steps > 0:
    num_train_epochs = max_steps // num_update_steps_per_epoch + int(max_steps % num_update_steps_per_epoch > 0)
```

- **设了 `max_steps>0`（`--smoke` 或 `--max-steps`）后，`--epochs` 完全失效**：实际 epoch 数由 `max_steps` 反算。
- 例：`--max-steps 50` + 2,156 条 → `num_train_epochs = ceil(50/135) = 1`（跑到第 50 步停，不会真的跑完其余 85 步）。
- 例：不给 `--max-steps`（默认 -1）→ `max_steps = ceil(epochs × 135)`，`--epochs 1` → 135 步。

## 4. `--resume` 到底恢复什么（含历史 checkpoint-10 判定）

### 4.1 调用链

`train_qlora.py:168` → `trainer.train(resume_from_checkpoint=args.resume or None)`

`transformers/trainer.py`：

| 位置 | 行为 |
|---|---|
| `:1547` | `_load_from_checkpoint(<ckpt>)`：加载权重。5.22.1 支持 `adapter_model.safetensors`（`ADAPTER_SAFE_WEIGHTS_NAME`），**PEFT 适配器能被认出**；找不到任何权重文件则 `ValueError("Can't find a valid checkpoint")` |
| `:1548` | `TrainerState.load_from_json(<ckpt>/trainer_state.json)` —— **无条件执行**，文件缺失直接 `FileNotFoundError` |
| `:1832/1864` | `_load_rng_state(<ckpt>)`：读 `rng_state.pth` 恢复随机数状态 |
| `:3855-3870` | `_load_optimizer_and_scheduler`：**若存在** `optimizer.pt`（或 `optimizer.bin` / 分片）就 `load_state_dict`；**若存在** `scheduler.pt` 就恢复 LR 调度状态 |

结论：`--resume` 恢复的是 **权重 + 优化器动量 + 学习率调度进度 + global_step/epoch + RNG**。缺 `optimizer.pt` 时不报错，但优化器从零开始（8bit Adam 的动量全丢）；缺 `scheduler.pt` 则 LR 回到 warmup 起点。

### 4.2 恢复必需的目录内容（验收判据）

| 文件 | 必需性 | 缺了会怎样 |
|---|---|---|
| `adapter_model.safetensors` | **必需** | `ValueError: Can't find a valid checkpoint` |
| `adapter_config.json` | **必需** | 无法把权重装回 PeftModel（结构对不上） |
| `trainer_state.json` | **必需**（硬性） | `FileNotFoundError`，直接崩，不会“尽力恢复” |
| `optimizer.pt`（或 `optimizer.bin` + `_*` 分片） | 强烈建议 | 不崩，但优化器状态清零，等价于换个优化器继续 |
| `scheduler.pt` | 强烈建议 | 不崩，但 LR 重新从 warmup 起，会造成 loss 尖峰 |
| `rng_state.pth` | 可选 | 数据顺序/ dropout 不复现（结果可跑但不可严格复现） |
| `training_args.bin` | 可选 | 仅用于核对当时的超参，不参与恢复 |
| `tokenizer*.json` / `chat_template.jinja` | 可选 | 恢复不需要（脚本自己加载 tokenizer） |

### 4.3 历史 `checkpoint-10` 能否恢复：**不能**

实测该目录只有：`adapter_model.safetensors`、`adapter_config.json`、`tokenizer*`、`chat_template.jinja`、`training_args.bin`、`optimizer.pt`（**286,720 B，写到一半被 kill**；对照 `checkpoint-5` 的正常值 82,465,512 B）。

- **缺 `trainer_state.json`** → 在 `:1548` 就抛 `FileNotFoundError`，连优化器都走不到；
- **缺 `scheduler.pt`、`rng_state.pth`** → 即便补上 state 文件，LR 与 RNG 也回不到原位；
- `optimizer.pt` 只有 280KB → 即使前两项补上，`torch.load` 也会因文件截断报错（不是“部分恢复”，是失败）。

**判定：`checkpoint-10` 只能当「10 步权重」用（可合并导出），不能当续训点。** 续训要求检查点是「完整保存」——即 save 过程中进程不能被杀死。

## 5. 顺带核实的两件相关事实（影响正式训练配置）

1. **截断方向是保头切尾**：`SFTConfig.truncation_mode` 默认 `"keep_start"`。数据已压到 640，若把 `--max-length` 设成 512，会把每条样本的**尾部（assistant 答案与 `[1]`）切掉**——与第 2 周 `02_长度分布` 的结论一致（512 档会截 41.9%）。**正式训练请用 `--max-length 640` 或 768，不要用 512。**
2. **`eval_strategy` 默认 `"no"`**：脚本虽然传了 `eval_dataset`，但**不会自动评估**。要验证「恢复后 loss 连续」，必须显式加 `eval_strategy/steps`（脚本目前没暴露这两个参数，需加 CLI 或改 cfg）。

## 6. 建议的正式训练配置（供验收基准）

| 项 | 建议值 | 理由 |
|---|---|---|
| 数据 | `sft_train_behavior.jsonl`（2,156） | 行为优先配比，冻结 sha `1fb1510e` |
| `--max-length` | **640** | 与数据压缩上限一致；512 会切答案 |
| `batch × accum` | 1 × 16（不变） | 16 条/step，8GB 已验证可行 |
| `--max-steps` | **135（1 epoch）/ 270（2 epoch）/ 405（3 epoch）** | 135 = ceil(2156/16)，宁可显式写死步数也不要用 `--epochs`（避免被 `--smoke` 干扰语义） |
| `--save-steps` | **30**（≈480 条/次，4 次/epoch） | 50 步那种「默认 100 步」永远存不下来的坑；30 步一次，即使被杀也最多丢 30 步 |
| `warmup_steps` | **5–9**（≈5% max_steps） | 现在写死 30，对 135 步是 22%、对 50 步是 60%，短跑会很吃亏（需改代码或加 CLI） |
| `eval_strategy` | `steps` + `eval_steps=45` | 现默认 `no`；要证明「恢复后 loss 连续」必须有评估点 |
| 预计耗时 | 135 步 ≈ 2h15m / 405 步 ≈ 6h45m（60 s/step，**需实测**） | 历史无完整 run 的端到端计时 |

**验收判据建议（写进第 3 周验收表）**

1. 一次「完整」训练至少 `max_steps ≥ 135`（1 epoch），且 `train_metrics.steps` 与该值一致；
2. 检查点目录必须同时含 `trainer_state.json` + `optimizer.pt`（且大小 ≈ 82 MB，不是几百 KB）+ `scheduler.pt` 才算「可恢复」；
3. 恢复验证：从 `checkpoint-<k>` 续跑后，`trainer_state.json` 的 `global_step` 从 k 起算，且 `eval_loss` 与中断前最后一个评估点相差 < 0.05（需实测阈值）；
4. 报告里凡写「N 步」，必须同时写 `max_steps` 与 `--train` 用的数据文件（2,156 还是 4,751 决定占比），否则口径不成立。
