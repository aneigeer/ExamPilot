## 1. 本周最重要的一条结论：7B 在这台机器上不可用

原计划默认用 Qwen2.5-7B。实测显存峰值：

| 配置 | 显存峰值 | 结论 |
|---|---|---|
| 7B / 640 token / bf16 | 7.9 GB | 超 6.5 G 上限 |
| 7B / 512 token / bf16 | 7.9 GB | 无改善，且 42% 样本被截断 |
| 7B / 384 token / bf16 | **9.58 GB（保留）** | 触发保护停止 |
| 7B / 384 token / fp16 | 7.9 GB | 无改善 |
| **3B / 640 token / bf16** | **4.36 GB** | **满足 ≤6.5 G** |

**结论：显存瓶颈不是序列长度，而是 7B 权重 + CUDA 上下文 + 分页优化器的固定开销。** 原定「降到 512 换显存」的方案不成立（512 既不掉显存，又砍掉 41.9% 样本、323 条答案、492 条引用）。

用户拍板：换 Qwen2.5-3B-Instruct，显存硬上限 6.5 GB。

## 5. 本周挖出的四个脚本缺陷（都已修）

| 缺陷 | 后果 | 处理 |
|---|---|---|
| `--smoke N` 同时把数据截成 `N×4` 条 | 「跑 N 步」实际是在 4N 条上跑 N 步、过 4 个 epoch | 短跑一律用 `--max-steps` |
| `logging_steps=5` 硬编码 | 20 步以内的短跑**一条 loss 都不记** | 改为 `--logging-steps`，默认 1 |
| `eval_strategy` 未暴露 | 传了 eval_dataset 却从不评估 | 加 `--eval-strategy/--eval-steps` |
| checkpoint 保存无原子性 | 保存中途卡死会留下缺 `trainer_state.json` 的残件（与历史上 286KB 的 `optimizer.pt` 同一失败模式） | 记录为 R-06，第 4 周加保存超时与残件检测 |

## 6. 另外两个环境事实

1. **页文件不足**：两个训练进程重叠时出现 `OSError 1455 页面文件太小`，模型加载阶段直接失败。规则：同一时刻只允许一个训练进程。
2. **训练目标实为全文本**：每步 `num_tokens ≈ 444/条`（样本正文约 490），说明 loss 覆盖 system + user + assistant。这会让一半算力用于复述问题，第 4 周应改为 assistant-only loss。
