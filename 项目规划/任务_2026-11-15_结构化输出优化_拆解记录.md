## 2. 根因（有原始输出留痕，非推测）

`runtime/wiki_smoke_20261115.json` 的 `raws` 实读：

- `doc-1000636` raw0：`"content": ["智能IVR系统的应用效果与落地情况", …]` → **数组**
- `doc-1005315` raw0：`"content": {"要点1": "…", "要点2": "…"}` → **对象**
- `doc-1005071` raw0：`content` 是正常字符串，但内容是模型自由发挥的「适应性在职场中的重要性」，与六级听力原文不重合 → **接地率 0.077 被闸门正确拦下**

`ai-service/app/wiki/distiller.py:52-57` 的 `_clean()` 用 `str(text)` 把 list/dict 转成 **Python repr**（带 `[`、`]`、`'`、`": "`），造成两个后果：

1. 落进正文的不是资料文字，正文失真（第二段验收 #7）；
2. 这些引号/方括号/逗号与原文 bigram 几乎不重合，**直接压低接地率**，把本可救回的页推给抽取式兜底。

`SYSTEM_PROMPT`（:31-45）只写了字段名与示例，**没有声明字段类型**；`_retry_prompt`（:270-294）只点名缺失字段，不点名类型错误，还把上次输出原文回灌 800 字（可能强化复述）。

## 3. 可修 / 不可修边界（红线）

**可修（确定性补全，延续上一轮 wiki-fixer 的思路）**

- A1 新增 `_coerce_text()`：list → 逐项可读文本、dict → `键: 值` 逐行、str 原样、None → 空；**禁用 `str()` repr**。在 `_validate` 里对 `summary` / `content` 先归一化再 `_clean`。
- A2 `SYSTEM_PROMPT` 补字段类型硬约束：`content` 必须是 Markdown 字符串（不是数组/对象）、`source_chunk_ids` 必须是整数数组、`key_points` 必须是字符串数组、`summary` ≥20 字、`links` 无则空数组。
- A3 `_retry_prompt` 点名上次的类型错误（content 是数组/对象时必须改成字符串），不只列缺失字段。
- A4 补单测覆盖上述 4 类形态，断言输出**不含 Python repr 特征**。

**一律不动（7 条红线 + 在线一致性）**

- 接地率 `ratio < 0.10` 判编造、数组全非法 ID 抛错回退、摘要 20 字 / 正文 80 字下限、quality 公式、最多 2 次 LLM 调用、`_extractive` 的 0.30 / `extractive-fallback`、`_chat` 的 `response_format`、`MAX_CLUSTER_CHUNKS=6`、在线 worker 取数口径。
- **不写库、不跑全量 512 页、不做向量同步、不启停 8080/8000、不做 git 写操作。**

**明确不可修（能力/设计问题，不得包装成已解决）**

- 模型编造内容（如 `doc-1005071`）→ 接地率闸门就该拦，属正确行为，不是 bug。
- 超大文档只均匀抽 6 块 → 在线一致性设计限制，改动会影响在线链路，本轮不动。
