# 02 · 3B 评测基线方案（只写方案，未执行）

> 结论：**不要用 `ollama run qwen2.5:3b` 当基线**（官方档位是 Q4_K_M，与微调 Q4_0 不同档，比较无效；

## 1. 两种做法的对比

| 维度 | ① 直接导入现成 GGUF（`ollama run qwen2.5:3b` 或官方 q4_0 GGUF） | ② 自建：本地 safetensors → 同量化器出 Q4_0 → `ollama create`（**推荐**） |
|---|---|---|
| 量化档位 | 官方 Ollama 库通常给 **Q4_K_M**（≈4.8 bpw；以实际 pull 到的为准），与微调 Q4_0（≈4.5 bpw）不同档 | **与微调完全同档**：同一脚本、同一 Q4_0 块格式 |
| 比较有效性 | **无效**：位宽不同会引入 1–2 pp 的系统偏差，且方向不可控 | 有效：唯一变量是 LoRA 权重 |
| 本机可行性 | 无 `qwen2.5:3b` 本地缓存；`ollama pull` 走代理（历史记录：blob 域名被解析到 198.18.x.x 遭拒） | 全本地：只需 safetensors（已在盘上） + `tools/` 里的转换/量化脚本 |
| 耗时 | 拉取 2 GB（网络不通则卡死） | 转换 1–3 min + 量化 ~1 min + `ollama create` ~10 s |
| 磁盘 | 2 GB | F16 中间件 6.2 GB + Q4_0 1.7 GB（F16 可在导入后删） |
| 失败恢复 | 依赖外网 | 每步都有产物，失败可单步重跑 |
| 风险 | 拿到的可能是 q4_K_M/iq4_xs 等任意档位，且**事后难以证明档位一致** | 由 `general.file_type` 字段自证（见 §2） |

**结论：走 ②。** ①只适合「只想知道 3B 大概什么水平」的粗看，不能进正式对照表。

> 补充：Ollama 0.40.13 在本机还有两个已知限制（第 1 周踩过）：`FROM <safetensors 目录>` 会走 MLX
> 报 `unsupported MLX architecture: Qwen2ForCausalLM`；`--quantize` 只支持 int4/int8/nvfp4。
> 所以「`ollama create -q int4` 一步到位」也不可行，必须走后缀 GGUF 路线。

## 2. 量化同档怎么校验（三重，缺一不可）

| # | 校验 | 判据 | 命令/代码 |
|---|---|---|---|
| 1 | **GGUF 头 `general.file_type`** | **Q4_0 = 2**（两个模型必须相等） | 下方 Python 片段 |
| 2 | 文件体积 | 3B Q4_0 **1.6–1.9 GB**（参考：7B Q4_0 = 4.29 GB，比例 0.28 → 3B≈1.7 GB） | `dir` / `ls -l` |
| 3 | 张量类型抽样 | `blk.0.ffn_down.weight` 等 2D 权重为 `Q4_0`，norm 保持 F32 | 同一脚本打印张量 dtype |

**特别注意**：`ollama show` / `/api/tags` 里的 `quantization_level` **不可信**——本机 `exam-prep-7b`
明明是 Q4_0 GGUF（4.29 GB），接口却显示 `F16`（上游把 `general.file_type` 写成了别的值）。
**判定一律以 GGUF 头为准**，不要看 Ollama 的展示字段。

校验脚本（**需新建** `tools/check_gguf_quant.py`，源码如下，不启动 ollama）：

```python
# python tools/check_gguf_quant.py <a.gguf> [b.gguf]
import sys
from gguf import GGUFReader

FILE_TYPE = {0: "F32", 1: "F16", 2: "Q4_0", 3: "Q4_1", 7: "Q8_0", 15: "Q4_K_M"}

def probe(path: str) -> tuple[int, str, int]:
    r = GGUFReader(path, "r")
    ft = int(r.get_field("general.file_type").contents()) if "general.file_type" in r.fields else -1
    # 取一个 2D 权重看实际 dtype
    sample = ""
    for name, t in r.tensors.items():
        if name.endswith("ffn_down.weight"):
            sample = str(t.tensor_type.name)
            break
    return ft, sample, len(r.tensors)

for p in sys.argv[1:]:
    ft, sample, n = probe(p)
    print(f"{p}: file_type={ft}({FILE_TYPE.get(ft,'?')}) sample={sample} tensors={n}")
```

期望输出（两个模型一致）：

```
C:/models/base-3b-q4_0.gguf:   file_type=2(Q4_0) sample=Q4_0 tensors=435
C:/models/exam-3b-v1-q4_0.gguf: file_type=2(Q4_0) sample=Q4_0 tensors=435
```

> 张量数 435 = 36 层 × 12 + token_embd + output_norm + output（见 03 文档 §2）；
> 若张量数明显偏少（如 3xx），说明转换时分片没拼全，量化出来的模型是坏的。

## 5. 风险与回滚

| 风险 | 表现 | 处置 |
|---|---|---|
| 转换分片不全 | 张量数 < 435、加载报 `output_norm.weight not found`（第 1 周踩过） | 重跑 A1/B2，确认输入目录含 `model.safetensors.index.json` |
| 量化档位不一致 | 两个 `file_type` 不同（如 15 vs 2） | 用同一 `tools/quantize_gguf.py --qtype q4_0` 重做基线 |
| 显存不足 | 3B Q4_0 约 2 GB 权重 + KV cache，8G 卡足够；但训练同时跑会抢显存 | **必须等训练结束后**再 `ollama create` / 建索引 |
| 基线污染 | 误用 `exam-prep-*` 当基线 | 评测命令里 `--base` 显式写 `qwen2.5-3b-baseline`，报告首行会打印模型名 |
| 与 7B 混比 | 拿第 2 周 7B 分数当 3B 基线 | **禁止**：报告里凡引用 7B 数字必须标「7B，仅历史」 |

### 6.2 抽样清单能不能复用（重要：任务书描述已过期）

任务书写「300 条抽样来自 `sft_val.jsonl` 427 条」——**这是第 2 周之前的旧口径**。当前实测：

```
默认来源 ['eval_holdout.jsonl', 'eval_planner.jsonl']
候选 250（holdout 200 + planner 50）→ 去污染 0 剔除
--limit 300 实际抽样 250：grounded 50 / injection 50 / mcq 50 / planner 50 / refusal 50
```

- **`sft_val.jsonl` 已不在默认链路里**（它与训练同源，只作为可选补充源）；
- 规模是 **250 条（五类各 50）**，不是 300；`--limit 300` 只会取到 250；
- **可复用性 OK**：`stratified_sample()`（`522`）用 `seed=7` + 固定 kind 排序 + `random.Random(seed).shuffle`，
  同一数据池两次运行取样完全一致（已实测对象序列相同）；
- **配对前提**：基线/微调必须用同一份清单 → 两次运行都用同一条命令、同一 `--seed 7`、同一 pins；
  报告 JSON 的 `sample_manifest`（`1027`）已逐条记录 `kind/qid/source`，可直接当清单核对。

建议（第 6 周实现，约 15 行）：新增 `--manifest-out <path>` 与 `--manifest-in <path>`：
前者把 `sample_manifest` 落盘，后者按 qid/kind 还原抽样结果，彻底消除「两次抽样不一致」的可能。
当前不改代码也能保证一致，因为随机源已被 seed 固定。

### 6.3 3B 特有的两条注意

1. **上下文**：输入 ≤640 token、输出 ≤400 → 合计 <1100；Modelfile 里 `num_ctx 4096` 足够，不需要 8192；
2. **耗时**：3B Q4_0 比 7B 快约 2×，250 条 × 2 模型（约 500 次调用）预计 **10–20 分钟**（4 并发，8G 卡）；
   若同时有训练在跑，必须等训练结束，否则会抢显存导致双方都变慢甚至 OOM。

### 6.4 与 7B 数字的关系

**第 2 周所有 7B 分数（含 v1 验收的 -41pp 引用退化）只能作为「7B 时代」的历史记录**。
3B 基线重建后，所有对比必须在新基线上重跑；报告里引用 7B 数字必须显式标「7B，仅历史」，
不得与 3B 结果放在同一张对比表里。
