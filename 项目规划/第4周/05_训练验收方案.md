### 1.1 B3 为什么不能用固定 MB 数（两次踩坑）

初版写 `adapter ∈ [45,75]MB`，依据是"3B r=16 ≈ 59.9MB"——**这是按 fp16（2 字节/参数）算的，算错了**。
PEFT 的 `save_embedding_layers=False` 且 adapter 以 **fp32** 落盘：29,933,568 × **4** = 119,734,272 B ≈ **114.2MiB**，
实测文件 119,801,528 B（114.3MB），字节/参数正好 **4.00**。所以正确算法是：

```
期望字节 = 可训练参数量 × 4（fp32）
容差 ±10%   →  3B r=16 落在 [102.8, 125.6]MB
```

同理 7B（40.37M 参数 × 4 ≈ 154MB）也远超旧上限，旧阈值只是当时没卡到边界。
脚本现在直接读 safetensors 头算真实参数量（不加载权重），不再硬编码 MB。

**mtime 判据也修过一次**：原来拿"某个日志文件的创建时间"作参照，但同一轮训练会产出多个日志
（`train_formal_v1`、`chunk_90`、`chunk_100`…），随便拿一个比必然误判"早于日志"。
现在改为与**同目录的 `trainer_state.json` / `optimizer.pt` / `scheduler.pt`** 比（同一次 save 写入），
差值 >1 小时才判旧产物残留；同目录没有这些文件时跳过并标 WARN。

## 2. 「部分完成」的判定口径（PARTIAL）

这是本周最重要的口径，避免把"跑了一半"说成"跑完了"，也避免把"可恢复的中断"直接判死：

| 状态 | 触发条件 | 是否阻断结项 | 能否用于正式模型比较 | 对外表述 |
|---|---|---|---|---|
| **PASS** | 达到阈值 | 否 | ✅ 可以 | 「训练完成」 |
| **PARTIAL** | B1 步数 < 135 或 B2 覆盖 <99.9% | **不阻断流程**，但**阻断"完成"结论** | ❌ **不可以** | 「部分 epoch，覆盖 X%（N/135 步，消耗 M/2156 条）」 |
| **FAIL** | 产物缺失/体积异常/指标发散/加载失败 | 阻断 | ❌ 不可以 | 「训练失败，原因：…」 |
| **SKIP** | 证据不足（如 loss 点 <5、训练进行中） | 不阻断，但必须列明 | ❌ 不可以 | 「未验证：…」 |

**硬规则：PARTIAL 状态下的 adapter 不得进入正式模型评测**——
第2周已证明"用半成品模型跑评测"会得出无法解释的结论（v1 就是 5 步冒烟产物被当成正式模型）。

脚本退出码：**有 FAIL → 1；只有 PARTIAL → 0，但打印醒目警告**（便于 CI 区分"跑挂"与"没跑完"）。

## 3. 用法

```bash
# 训练跑完后（标准用法）
.venv-ai/Scripts/python.exe 项目规划/第4周/scripts/accept_week4.py \
  --log 项目规划/第4周/evidence/train_formal_v1.log \
  --ckpt-dir training/output/qwen2.5-3b-exam-lora-v1 \
  --expect-steps 135 --samples 2156 --batch 1 --accum 16 \
  --manifest 项目规划/第4周/evidence/artifacts_manifest.json \
  --json-out 项目规划/第4周/evidence/accept_week4.json

# 训练进行中看进度（产物类 FAIL 属预期，脚本会打印提示）
... --active-window 300

# 允许完整 PeftModel 加载（会读基座权重，训练在跑时自动跳过）
... --full-load
```

**退出码**：0 = 无 FAIL（可能是 PASS 或 PARTIAL）；1 = 有 FAIL。

### 3.1 参数说明

| 参数 | 作用 | 备注 |
|---|---|---|
| `--expect-steps 135` | B1 预期步数 | 2,156/(1×16) = 134.75 → 135 |
| `--samples 2156` | B2 分母 | 传错会让 B2 覆盖率失真 |
| `--adapter-mb 57` | B3 期望体积 | 换模型/rank 时要改 |
| `--active-window 300` | 日志 N 秒内更新过即视为训练中 | 影响 B5 是否跳过完整加载 |
| `--full-load` | 真做 `PeftModel.from_pretrained` | 默认只做配置+张量校验，不占显存 |

## 4. 解析健壮性（已自测）

复用第3周的三层兜底：去 ANSI → `\r` 折叠 → loss 先整体 `json.loads` 再逐字段正则。
本周新增两处坑，都已处理：

1. **loss 值是字符串**：正式日志是 `{'loss': '3.719', ...}`（带引号），不是数字字面量。解析时统一 `float()`。
2. **进度条分母相同会串**：数据集预处理也有 `2156/2156` 这种进度条，直接取 max 会把"2,156 条样本"误当成"2,156 步"（实测踩到，B1 一度报 2156/135）。现在只认**分母 == `--expect-steps`** 的进度条；找不到才退化并打印 warn。

**五个场景自测结果**（假数据）：

| 场景 | 构造 | 期望 | 实测 |
|---|---|---|---|
| 正常 | 10 步 loss 下降 + 四件齐全 + manifest 一致 | B1/B3/B4/B6 PASS | ✅ 符合 |
| 发散 | loss 3.00→3.72 单调上升 | B4 FAIL | ✅ 末 5 均值 3.56 > 首 5 均值 3.16 |
| adapter 过小 | 12MB（<45MB） | B3 FAIL | ✅ 报"体积 12.0MB 超出 [45,75]" |
| 真实 safetensors | 7 个 target_modules 的 lora_A/B 各 7 个 | B5 PASS | ✅ 张量 14 个、命中 7/7 |
| 训练进行中 | 日志 300s 内有更新 | B3/B5/B6 FAIL 但提示属预期 | ✅ 打印"产物要等存档后落盘" |

### 5.1 为什么是 100/135 而不是 135

本轮训练被环境反复强杀，先后在 14/35/40/47/70/75/95/100 步各断一次，**不是代码或显存问题**
（每段都能正常存档，loss 也一路下降）。要拿到 135/135，需要一次性跑满或从 checkpoint-100 续训 35 步。

### 5.2 仍未闭环的两点

1. **`train_metrics.json` 写的是 `steps: 90`**，但实际 global_step=100、checkpoint 到 100 —— 这两个数对不上，
   说明指标文件是中途某次写入的。**建议训练收尾时重写该文件**，否则 B3 里"用 train_metrics 证明步数"这条证据链是断的。
2. **无 eval_loss**（`log_history` 里没有 eval 记录），B4 的"eval 与 train 同量级"这条目前无法验证；
   若要用于正式比较，建议开 `eval_strategy="steps"` 至少跑一次验证集。
