  `total / elapsed_s / call_total / matched / ok_true / ok_false / tool_dist / rows`，
  **无语料版本、无模型名、无 `promptVersion`、无时间戳**（`C2_planner静态复核.md` §1.1 已复核）。
  它生成于**旧语料 65,511 块**、`promptVersion=v3`、非 7B 模型期，**不能当新基线**。
- 当前终态（`任务_2026-11-13_收尾执行记录.md` §11.5 / `任务_2026-11-14_本机执行记录.md` §4）：
  `ai_chunk` COURSEWARE **89,318**、模型 **`exam-prep-7b`**（后端启动带 `OLLAMA_MODEL`）、
  planner 源码 `PROMPT_VERSION = "agent-planner-v4"`。
- D07 的 F-11 拒答率历史极不稳定（**6/10 与 0/10 同日两次**），不写清条件就会被误用。
  修复记录 §6 还明确：`meta.promptVersion` 若仍是 v3，说明 **8000 未重启、跑的是旧代码**，
  本次重测即作废。

因此**两份输出 JSON 都必须带四个固定条件字段**，且语料版本必须**脚本内只读现查**，
不允许把 89,318 硬编码进结果。

### 四个固定条件字段（两份输出 JSON 顶层同名字段）

## 6. D08 脚本判据与字段字典

### 6.1 题面来源（关键设计决策，供验收核对）

`runtime/d08_planner_full_50.json` 的 `rows[].question` 是 **`stem[:80]` 的展示用截断串**：
已只读核对 50/50 —— 每条都是 `training/data/eval_planner.jsonl` 中
`messages[role=user].content` 的前缀（例：i=1 完整 90 字，v3 只留 80 字；
i=21 完整 121 字含 `【问题】` 段，v3 截断在 `【问题】\n` 处）。
若直接把 v3 的截断串当请求体，会改变原始 50 条 prompt，重跑不可比。

故：
* **默认题面源** = `training/data/eval_planner.jsonl`（50 条完整题面，长度 8–171 字，
  均 ≤ `AgentRequest.question` 的 200 字上限）；
* v3 文件仅作**格式参照、顺序对齐（50 条逐条前缀核对）、旧基线对照**；
* 如确需强制用 v3 截断串：`--questions runtime/d08_planner_full_50.json`，
  输出会标记 `questions.truncated=true` 并在控制台告警；
* 输出里记录 `questions.source` / `questions.sha256` / `questions.count` /
  `questions.alignmentWithV3`，使题面集合可复核、可固定。

### 6.2 请求 / 事件解析

* `POST /v1/agent/run`，头 `X-Internal-Token`，body `{"question": stem, "userId": 3}`；
  不传 `maxSteps`，沿用服务端默认 6（与 v3 的 `steps` 量级一致）。
* 事件顺序按 `meta → thought → tool_call → tool_result → … → final → done` 解析：
  * `meta.data.promptVersion` → 逐行取证，50 行一致且 `== agent-planner-v4` 才算条件合格；
  * `tool_call.data.arguments` → `args`；
  * `tool_result.data` 的 `ok / summary / elapsedMs / data` → 报告字段；
  * `thought` 文本含「大模型规划不可用」→ `llmPlannerFallback` 计数，
    用于对照修复记录 §4 的「旧基线 12 次，>12 应怀疑 +497 字符提示词挤占 4096 窗口」。

### 6.3 逐条配对（硬判据）

| 字段 | 口径 |
|---|---|
| `call_total` | 50 行 `tool_call` 事件总数 |
| `matched` | 按 `(step, tool)` 成功配对的次数 |
| **`matchedEqualsCallTotal`** | **要求 `matched == call_total`**；不满足则脚本返回退出码 2 |
| `unpairedCalls` / `unpairedResults` | 未配对的 call / result **如实列出，不丢弃、不补齐** |
| `rows[].tools[]` | 每条工具 `step / tool / args / ok / elapsedMs / summary / hits`（另加 `okMissing / dataType / recallCountFromSummary / hitsSource / paired`） |
| `ok_true` / `ok_false` / `okMissing` | 按 `ok` 严格布尔统计；**`ok=false` 如实保留**，不改成 true、不删除 |
| `okFalseDetails` | 每条 `ok=false` 的 `i / step / tool / args / summary`，便于逐条归因 |
| `hits` | `len(tool_result.data.data)`（list 时）否则 0；与 v3 口径一致。`SEARCH_KEEP=3` 会让「命中 5 条」仍显示 `hits=3`，故另存 `recallCountFromSummary` 区分召回数与裁剪数 |
| `tool_dist` | 工具名分布 |
| `focusCaseNumbers` / `focusCases` | **7 / 11 / 21 / 34**（修复记录 §6 P0 四题），逐题给出期望与本次实际工具链 |
| `v3Baseline` / `comparisonWithV3` | 旧 `call_total=54 / ok_false=5` 与本次对照；注明旧基线无四条件、语料 65,511、v3、非 7B |
| `llmPlannerFallback` | 回退次数 + 基线 12 + 风险说明 |

## 8. 边界声明（不粉饰）

1. 本轮**只产出 3 个文件**（2 脚本 + 1 方案）。**没有任何运行证据**：未执行两个脚本、
   未起停 8080/8000、未调 Ollama、未跑 pytest、未写库、未改审核状态、
   未改任何既有 runtime JSON 与 AI 服务源码、未提交未推送。
2. §4 的命令是**预案**；§5/§6 的字段名是**代码已实现的输出契约**，
   不是「已跑出的数值」。任何 `refusedCount` / `ok_false` / `corpusVersion` 的**实测值**
   都必须等主 agent 跑完由输出 JSON 提供。
3. 脚本不做质量判定：`meetsThreshold` / `matchedEqualsCallTotal` 只是记录与结构闸门，
   PASS / PARTIAL / FAIL 由 `qa-acceptance` 独立复核裁定；按 `00_协作规程.md` §3，
   PARTIAL 不得写成 PASS。
4. 已知风险（如实列出）：
   * LLM 非确定性 → 两次重跑工具调用数/耗时不会一致，只能比「固定条件 + 结构性判据」；
   * 单次拒答率不稳定（历史 6/10 与 0/10），单次结果不可当稳定基线；
   * `userId=3` 取自 v3 期 `[AgentAudit] user_id=3` 日志，若该用户错题本/画像已变化，
     `get_wrong_book` / `get_weak_knowledge` 的返回会不同，属条件差异，需在验收时说明；
   * 若已注入 `STUDENT_JWT` 但 token 已失效，脚本**不会**自动改用登录换取（避免悄悄改变
     「同一学生 JWT」条件），此时 10 条会如实记为 `http=401`（`httpOk<10`、退出码 2）；
     若既无 `STUDENT_JWT` 又无 `STUDENT_NO`/`STUDENT_PWD`，脚本直接中止并给出可读提示；
   * 静态 `PROMPT_VERSION` 兜底仅为「探针失败时的参考值」，输出会标
     `promptVersionRuntimeVerified=false`，**不得当作运行态版本证据**。
