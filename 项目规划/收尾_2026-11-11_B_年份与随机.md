## ② SQL 迁移文件摘要 + 预估影响行数 + 执行命令

**文件**：`sql/migration-question-year.sql`（新建，未执行）

### 2.1 内容结构（4 段 + 前置体检）

| 段 | 内容 | 幂等方式 |
|---|---|---|
| §0 执行前体检 | `SELECT COUNT(*) FROM question`、`SELECT COUNT(*) FROM question WHERE source REGEXP '^20[0-9]{2}年'` | 只读 |
| §1 加列 | `ALTER TABLE question ADD COLUMN year SMALLINT NULL DEFAULT NULL COMMENT '年份（真题年份，非真题为 NULL）' AFTER source` | `information_schema.COLUMNS` 判存在，存在则执行 `SELECT 1`（沿用 `sql/migration-perf.sql` 同款 `PREPARE/EXECUTE/DEALLOCATE` 动态 DDL 模式） |
| §2 加索引 | `ALTER TABLE question ADD INDEX idx_q_year (year)` | `information_schema.STATISTICS` 判存在 |
| §3 回填 | `UPDATE question SET year = CAST(SUBSTRING(source,1,4) AS UNSIGNED) WHERE source REGEXP '^20[0-9]{2}年' AND year IS NULL` | `AND year IS NULL` ⇒ 重跑只补新行，**不覆盖人工改过的 year** |
| §4 执行后核对 | 查列/索引是否就绪、`year IS NULL 但 source 可解析` 应为 0、subject_id=190 的年份分布 | 只读 |

**回填口径（写进文件头，不猜）**：只从 `source` 前 4 位取，且必须匹配 `^20[0-9]{2}年`；`SUBSTRING` 只取 4 位（防 `source='20223年…'` 被解析成 20223）；取不到 / 全角数字 / `source` 为 NULL / 形如 `'2016-2025合辑'` 一律留 `NULL`，**不推断、不按题干里的年份字样猜**。

### 2.2 预估影响行数

| 口径 | 行数 | 依据 |
|---|---|---|
| subject_id=190（实测基准科目） | **3027** | 已知运行库实测：2016:238 / 2017:240 / 2018:240 / 2019:242 / 2020:241 / 2021:119 / 2022:380 / 2023:353 / 2024:341 / 2025:352 / 2026:281，合计 3027，`source` 无一条为空 |
| 全表预估 | **约 3000~3400 行** | `sql/data-guokao.sql` 全文 `20xx年` 字样出现 **3356** 次（`sql/data.sql` 为 0 次），与 3027 同量级 ⇒ 年份数据基本只分布在国考这一科；其余科目题量远小于此 |
| 精确值 | **不猜，执行时由 §0 第二条 SELECT 得出** | 该 SELECT 的返回值就是真实回填行数 |

> 回填不会动 `is_deleted=1` 的历史行（逻辑删除只是标记，`UPDATE` 不区分），无害且后续恢复时年份已在。

### 2.4 回填后如何确认成功（三条 SQL 都在文件 §4 里）

1. `information_schema.COLUMNS` 查 `year` → 应返回 1 行，`COLUMN_TYPE = smallint`；
2. `information_schema.STATISTICS` 查 `idx_q_year` → 应返回 1 行；
3. `SELECT COUNT(*) ... WHERE year IS NULL AND source REGEXP '^20[0-9]{2}年'` → **必须是 0**；
4. `SELECT year, COUNT(*) FROM question WHERE subject_id = 190 GROUP BY year` → 应与 2.2 表里 11 个年份的数字一一对上（这是最强的端到端证据）。
