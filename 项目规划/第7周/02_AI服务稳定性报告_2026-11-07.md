# AI 服务稳定性报告（第7周框架线）

> 时间：2026-11-07
> 对象：`ai-service`（FastAPI + Uvicorn + ONNX Runtime + qdrant-client 本地模式）
> 现象：连续 `/v1/search` 约 300 次后进程崩溃，后端向量通道静默降级 ngram

---

Windows 应用程序错误日志：

|---|---|---|---|
| 2026-11-07 21:43:44 | `python312.dll` | `0xc0000005` | `0x896be` |
| 2026-11-07 22:14:04 | `python312.dll` | `0xc0000005` | `0x896be` |

- 崩溃进程：`D:\bigplan\tools\python3.12.10\python.exe`

  `向量通道不可用（未开启/熔断/健康检查未通过），静默降级到 ngram 通道`

**影响**：RAG 指标会突然从“向量+ngram 混合”退化为“纯 ngram”，外部看起来只是“检索变差”，不会报错。

## 3. 已尝试的修复

### 3.1 `read_meta()` 加锁

`qdrant_client.py` 的 `read_meta()` 访问本地 Qdrant 客户端时没有拿 `_op_lock`，而 `search()` 拿了。两个请求重叠会并发访问本地 Qdrant（文档写明“单进程独占”）。

修复：

```python
with self._op_lock:
    ...
```

**效果**：100 次连续检索压力测试通过（0 错误），但完整 214 条后又崩一次。说明并发只是诱因之一，不是全部根因。

### 3.2 并发限制

已用 `uvicorn --limit-concurrency 4` 启动；仍崩溃。不是单纯并发数问题。

### 3.3 未能根治的假设

1. **qn：qdrant-client 本地模式 native 泄漏/损坏**：连续几百次 `search` 后触发。
2. **ONNX Runtime / tokenizers 与 Python 3.12.10 组合问题**：崩溃模块是 `python312.dll`，偏移固定 `0x896be`，像固定代码路径。
3. **numpy 2.2.1 与 onnxruntime 1.20.1 兼容性**：需要进一步做最小复现（固定输入循环 encode）。

## 4. 当前缓解方案

### 4.1 已落盘

- `ai-service/run_watchdog.bat`：崩溃后自动重启（当前批处理重定向中文路径未生效，需改 PowerShell 版）。
- 后端已有熔断 + 静默降级：AI 服务短暂不可用时，问答仍返回 200，只是退回 ngram。

### 4.2 待做

1. **PowerShell watchdog**（推荐）：
   ```powershell
   while ($true) {
     & "..\.venv-ai\Scripts\python.exe" -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --limit-concurrency 4 *>> "..\项目规划\第7周\evidence\ai_service_watchdog.log"
     Start-Sleep -Seconds 2
   }
   ```
   或把 `run_watchdog.bat` 改成纯英文日志路径。
2. **定期重启**：每处理 N 次 `/v1/search` 主动重启（N 取 200，低于崩溃阈值 300）。
3. **Qdrant HTTP 模式**：启动 Docker/Qdrant 服务，AI 服务改用 `http://127.0.0.1:6333`，绕开本地模式 native 客户端。
4. **依赖升级/降级**：单独测试 `onnxruntime`、`qdrant-client`、`numpy` 组合；不要一次改多个。
5. **最小复现脚本**：固定一条 query 循环 500 次，记录 RSS 与崩溃计数，供官方 issue 使用。
