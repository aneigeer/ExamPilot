## 2. 误拒定位

### 2.1 修正前（0.62 语义线）

30 条中 8 条域内误拒：

| id | 问题 | 检索排名 |
|---|---|---|
| s02 | 32 位系统里一个整型变量占多大内存？ | 1 |
| s04 | C语言里哪些单词是保留关键字？ | 1 |
| s05 | 写代码时变量名不能用哪些词？ | 3 |
| s09 | 为什么访问数组时要从 0 开始计数？ | 1 |
| s14 | 为什么通过指针能修改函数外部的变量？ | 2 |
| s23 | 先进先出和后进先出分别对应哪种数据结构？ | 1 |
| s26 | 前序中序后序遍历分别怎么走？ | 1 |
| s27 | 层序遍历和深度优先遍历有什么区别？ | 2 |

**性质**：检索已经命中正确 chunk（rank 1–3），但最终语义闸门 0.62 把它们拒了。不是召回问题。

### 2.2 根因

`HybridRetriever` 的语义拒答条件：

```java
semanticReject = applyGate && vectorEnabled && vectorBest > 0
        && vectorBest < semanticRejectScore;   // 0.62
```

代码注释写的是“只在字面通道也没证据时否决”，但实现没有检查字面通道。s02 的正确 chunk 余弦 **0.6145**，被 0.62 拒掉；而 11 条域外最高 0.5606（r02 0.8066 除外）。0.62 与域内最低 0.6145 的余量只有 0.005，必然误杀。

### 2.3 修复

1. **加“字面通道有证据则跳过语义拒答”条件**：
   ```java
   lexicalHasEvidence = !ngram.contexts().isEmpty()
           && ngram.bestScore() >= rejectThreshold;
   semanticReject = ... && !lexicalHasEvidence && ...;
   ```
2. **语义线 0.62 → 0.60**（`application.yml` + `AiProperties` 同步）：
   - 域内 s02 0.6145 → 放行
   - 域外最高 0.5606 → 仍拒
   - 旧值 0.62 的注释已更新为本次标定

### 2.4 修复后

30 条误拒 **26.7% → 16.7%**；s02/s04/s26 已放行，剩余 5 条：

| id | 问题 | top1 余弦 |
|---|---|---|
| s05 | 写代码时变量名不能用哪些词？ | <0.60 |
| s09 | 为什么访问数组时要从 0 开始计数？ | <0.60 |
| s14 | 为什么通过指针能修改函数外部的变量？ | <0.60 |
| s23 | 先进先出和后进先出分别对应哪种数据结构？ | 0.5397 |
| s27 | 层序遍历和深度优先遍历有什么区别？ | 0.5173 |

**结论**：这 5 条是“语义相似度低但确实域内”的 hard case。继续降阈值会把 r05（0.5606）、r10（0.5564）放进来，拒答准确率下降；应先做 query rewrite/更好 embedding，而不是继续放宽。
