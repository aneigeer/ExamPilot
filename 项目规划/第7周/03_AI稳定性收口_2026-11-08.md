## 2. 任务 1：`run_watchdog.ps1` 为什么在 IDE 后台不生效

### 2.1 四个失效点

| # | 原因 | 证据 / 说明 |
|---|---|---|
| 1 | `*>> $log` 把 uvicorn 的 stderr 并入 PowerShell 错误流，日志行被包装成 `NativeCommandError`；若调用方（IDE 包装器）设置 `$ErrorActionPreference='Stop'`，循环在第一次日志输出时即终止 | `项目规划\第7周\evidence\ai_service_start6_20261107.log` 中明确出现：`python.exe : 2026-11-07 22:32:43 ... NativeCommandError`，`FullyQualifiedErrorId : NativeCommandError` |
| 2 | 依赖 `$PSScriptRoot`；若通过 `powershell -Command` 或 `Get-Content \| Invoke-Expression` 执行，该变量为空，`Set-Location -LiteralPath $PSScriptRoot` 直接报错退出 | 静态缺陷；v2 已做路径三级回退（`$PSScriptRoot` → `$MyInvocation.MyCommand.Path` → FATAL） |
| 3 | 无单实例/端口占用保护：重复运行会有两个 watchdog 抢 8000，uvicorn 绑定失败后“秒退-重启” | v2 使用命名互斥 + 启动前端口预检；端口被占用时退出码 3，重复实例退出码 2。历史上 14:39:38 出现过 `EXIT code=unknown uptime_s=12.6` 且无 Application Error 事件，疑为实例交接/端口竞争窗口，无法确认为 native 崩溃 |
| 4 | **IDE 后台终端会回收整个进程树**，watchdog 天然无法长驻 | 当前实例的父进程链为：IDE 命令包装器 `pid=13108`（命令行以 `-Command ... powershell -File run_watchdog_v2.ps1` 结尾）→ watchdog `pid=22352` → uvicorn 启动器 `pid=28252` → 实际服务 `pid=7956`。14:31 启动的 watchdog `pid=22080` 在 14:39 前已消失，随后由新实例 `pid=22352` 接管，说明 IDE 会话不可靠 |

### 2.2 采用的稳定版本

本次沿用已有的 `ai-service/run_watchdog_v2.ps1`（8707 字节，UTF-8 with BOM，PowerShell Parser 校验 0 错误），未改业务代码。关键机制：

1. `Start-Process -RedirectStandardOutput/-RedirectStandardError` 落盘，绕开 PowerShell 错误流；
2. 每轮拉起前把上一轮日志转存为 `*.prev`，保留崩溃现场；
3. 路径回退、`.venv-ai\Scripts\python.exe` 存在性校验；
4. `Global\ExamprepAiServiceWatchdogV2` 命名互斥 + 8000 启动前预检；
5. 每轮记录 `START / LAUNCH / STARTED / PORT_READY(ready_ms) / EXIT(code, uptime_s)`；
6. 200ms 监督轮询，默认 300ms 重启延迟（当前实例启动参数为 100ms）；
7. `.watchdog_stop` 文件或 Ctrl+C 优雅停止。

## 3. 任务 2：100 次连续 `/v1/search` 压力测试

### 3.1 方法

- 服务：`127.0.0.1:8000`，uvicorn 参数 `--host 127.0.0.1 --port 8000 --limit-concurrency 4`；
- 数据：`ai-service/eval/golden_set.jsonl` 的 214 条 `question` 循环取用；
- 参数：`top_k=10`，串行、无并发，每次间隔 15ms；
- 崩溃判定：请求异常 + 监听 8000 的 python PID 消失；随后每 100ms 轮询 `/v1/health`，记录恢复耗时；
- RSS：`netstat -ano -p tcp` 取 8000 监听 PID，读取该 python 子进程 `WorkingSet64`（排除约 3.6 MB 的 venv 启动器）；
- 时间：`System.Diagnostics.Stopwatch`；请求体按 UTF-8 字节发送，避免中文 query 被 ANSI 破坏。

核心命令（PowerShell 5.1，可复跑）：

```powershell
$qs = [IO.File]::ReadAllLines(
  'D:\大学生多考试备考知识库与题库系统\ai-service\eval\golden_set.jsonl',
  [Text.UTF8Encoding]::new($false)
) | Where-Object { $_.Trim() } | ForEach-Object { ($_ | ConvertFrom-Json).question }

for ($i = 1; $i -le 100; $i++) {
    $q = $qs[($i - 1) % $qs.Count]
    $bytes = [Text.Encoding]::UTF8.GetBytes((@{ query = $q; top_k = 10 } | ConvertTo-Json -Compress))
    $sw = [Diagnostics.Stopwatch]::StartNew()
    Invoke-RestMethod -Uri 'http://127.0.0.1:8000/v1/search' -Method Post `
        -ContentType 'application/json; charset=utf-8' -Body $bytes -TimeoutSec 20 | Out-Null
    $sw.Stop()
    # 每 20 次采样：PID / RSS / 崩溃 / 重启
}
```

## 5. 任务 3：watchdog 故障自愈验证

### 5.1 方法

```powershell
# 取真正监听 8000 的 python（venv 的 python.exe 是启动器，服务在其子进程）
$lp = (netstat -ano -p tcp | Select-String '127.0.0.1:8000' | Select-String 'LISTENING')
$old = [int](($lp.Line -split '\s+')[-1])
Stop-Process -Id $old -Force
# 每 100ms 探测：TCP 8000 可连接 + /v1/health 返回 200
```

### 5.2 结果

```text

KILLED pid=25564 at 14:43:19.699
RECOVERED new_pid=7956 recover_ms=2513 rss_mb=393.3
```

watchdog 日志（`evidence/ai_service_watchdog_v2.log`）：

```text

[2026-11-08 14:43:19.872] LAUNCH uvicorn port=8000 restart_no=2
[2026-11-08 14:43:19.884] STARTED pid=28252 restart_no=2
[2026-11-08 14:43:22.154] PORT_READY pid=28252 ready_ms=1037 health200=True
```

- 人工 kill 到 watchdog 记录 EXIT：49ms；
- 端口（TCP 8000）恢复：**1.037s**；

- 本次为**人工 kill**，计 1 次人工重启，不计入自然崩溃。

## 7. 剩余风险

| # | 风险 | 影响 | 现状 |
|---|---|---|---|
| R1 | native 崩溃根因未定位（历史 `python312.dll 0xC0000005`；2026-11-08 14:30:11 事件日志另有 `python.exe / ucrtbase.dll / 0xc0000409`，在本次压测窗口外） | 极端负载/长稳下仍可能崩；本次 1000+ 次未复现，不能证明根因已消除 | 未关闭 |
| R2 | watchdog 只看端口是否可连接（`Test-PortOpen`），不校验端口归新拉起的进程树所有 | 若存在孤儿 uvicorn 占用 8000，可能误报 `PORT_READY` 并进入重启循环；14:39:38 的 `EXIT code=unknown` 且无崩溃事件疑似此窗口 | 未命中本次 500 次窗口；建议按 PID 树归属校验 |
| R3 | `code=unknown` | watchdog 日志无法直接给出 native 退出码，需查 Windows 事件日志 | 已知限制 |
| R4 | 重启窗口 health 200 约 2.5s，首条检索冷加载 262ms | Java 侧熔断窗口内可能短暂降级到 ngram；评测需标注“向量可用/降级” | 已量化，未优化 |
| R5 | watchdog 依赖外部 PowerShell 会话 | IDE 会话结束即可能被回收；生产没有自动拉起 | 必须外部窗口/计划任务/服务 |
| R6 | 8080 后端由并行任务运行，请求节奏不受本测试控制 | “熔断-恢复”联动未做受控验证 | 未验证 |
| R7 | qdrant-client 仍为本地模式 | 本地客户端 native 路径仍是历史崩溃嫌疑点 | 建议迁 HTTP 模式（`QDRANT_URL=http://127.0.0.1:6333`） |

### 建议（未落地）

| 优先级 | 建议 |
|---|---|
| P0 | 把 watchdog 放到外部 PowerShell / 计划任务 / Windows 服务，开机自启并失败重启；IDE 终端只做临时调试 |
| P1 | `run_watchdog_v2.ps1` 的 `PORT_READY` 改为校验“8000 监听 PID 属于本次 `$proc` 的进程树”；发现外部占用时记录并退出，避免误报 |
| P1 | 迁移 Qdrant HTTP 模式，绕开本地模式 native 客户端；或给 `probe()` / `upsert_meta()` 同样加 `_op_lock`（仅建议，未改代码） |
| P2 | 压测脚本固定为可复跑脚本，并在每轮结束导出 CSV，便于回归对比 |
| P2 | 观测模型 RSS 基线（约 464 MB）；若后续版本超过 600 MB 再评估是否定期重启 |
