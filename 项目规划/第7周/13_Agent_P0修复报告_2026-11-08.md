## 2. T01 修复点（G-01：幻觉工具名必须在执行前硬拦截）

### 2.1 根因

`_agent_loop` 只要拿到 `decision.action == "tool"`，就直接：
1. `budget.try_consume()` 扣预算；
2. `attempt.tool_calls += 1`；
3. 发 `tool_call`；
4. `ToolRegistry.execute` 用 if/else 兜底返回 `ok=False, summary="未知工具"`，再发 `tool_result`。

于是幻觉工具名 `wiki_search_typo` 虽然没真的打 Java（`bridge.tools_called` 为空），但**预算被扣、错误事件照发**，用户端与统计都无法区分"模型胡说"和"工具失败"。

### 2.2 修复

在 `harness.py:284-301`，`action=final` 分支之后、预算闸门之前，插入白名单硬校验：

```python
# ---------- 工具白名单（执行前硬校验） ----------
# 未知工具（典型是本地小模型幻觉出的工具名）必须在执行前拦掉：
# 不发 tool_call/tool_result、不扣预算、不访问 Java，只留一条可解释的 thought。
if decision.tool not in TOOL_NAMES:
    logger.warning(
        "[Agent] 拦截未知工具：%s（不在工具白名单 %d 个内，未执行）",
        decision.tool, len(TOOL_NAMES),
    )
    yield event(
        EVENT_THOUGHT,
        {
            "step": step,
            "text": prefix
            + f"未知工具「{decision.tool}」已拦截：不在工具白名单内，"
            + "不执行、不消耗工具预算",
        },
    )
    continue
```

要点：

- 白名单直接复用 `planner.py` 的唯一事实来源 `TOOL_NAMES`（由 `TOOL_SPECS` 派生，与 `ToolRegistry` 可执行集合仍是同一份 7 个名字），**不新增第二份名单**，避免再次漂移；`harness.py:40-47` 只新增该导入。
- `continue` 而非 `break`：本轮不执行、不扣预算，把"下一步怎么走"交回规划器（T01 的脚本第二次规划即 `final`）。步数仍受 `max_steps` 约束，**不会死循环**。
- 放在预算闸门**之前**：顺序错了就会先扣预算再拦截，`final.tool_calls` 仍为 1。
- 选择"拦截 + thought"而不是在 `parse_decision` 抛 `PlannerError`：后者会让 `llm_available=False` 永久切规则规划器，规则规划器会改发 `search_knowledge`，**反而真的打 Java**，与 T01 的 `bridge.tools_called == []` 相冲突。

### 2.3 修复后该用例观测

- 事件序列：`meta → thought(查一下) → thought(未知工具已拦截) → thought(够了) → final → done`；
- 无任何 `tool_call` / `tool_result`，无 `wiki_search_typo` 字样的事件；
- `final.tool_calls == 0`、`step_count == 2`、`final`/`done` 齐全（HTTP 语义仍 200）。

## 3. T04 修复点（G-04：上游定稿 5xx 不得伪装成业务拒答）

### 3.1 根因

`_finalize` 的 `except JavaBridgeError` 返回 `answer=REFUSAL_TEXT("未找到相关资料")`、`generator="none"`、`refused=True`。Java 侧据此只能把终态记 `REFUSED`，上游 502 在 `errorTop5`/失败率里完全不可见。

### 3.2 修复

`harness.py:509-523`，把该兜底改成"显式上游失败"：

```python
except JavaBridgeError as exc:
    # 上游故障 ≠ 业务拒答：不得用「未找到相关资料」表达 5xx，
    # 否则 Java 侧会把终态记成 REFUSED，故障在 errorTop5/失败率里不可见。
    logger.warning("[Agent] Java 定稿失败（errorCode=%s）：%s", UPSTREAM_ERROR_CODE, exc)
    return {
        "answer": UPSTREAM_ERROR_TEXT,
        "generator": "upstream-error",
        "degraded": True,
        "refused": False,
        "sources": [],
        "errorCode": UPSTREAM_ERROR_CODE,
        "degradedReason": f"Java 定稿失败：{exc}",
    }
```

新增两个模块级常量（`harness.py:62-67`）：

- `UPSTREAM_ERROR_TEXT = "回答生成服务暂时不可用（上游故障），请稍后重试。"` —— 与 `REFUSAL_TEXT` 语义可分；
- `UPSTREAM_ERROR_CODE = "AGENT_UPSTREAM_ERROR"` —— `final.errorCode` 显式错误码。

`_emit_final`（`harness.py:183-189`）把 `errorCode` / `degradedReason` 透传到 `final` 顶层：

```python
if extra:
    data.update(extra)
# 上游失败要能被 Java 侧识别为 FAILED（而不是业务拒答 REFUSED）：
# 错误码/降级原因必须在 final 顶层可见，且不被 extra 覆盖。
for key in ("errorCode", "degradedReason"):
    if final.get(key) and key not in data:
        data[key] = final[key]
```

要点：

- `refused=False` + 显式 `errorCode`：测试只要二者之一，这里两者都给，Java 侧可按 `errorCode` 落 `FAILED`；
- `generator="upstream-error"` 与业务拒答/抽取式兜底（`extractive`、`agent-rule`）互不混淆；
- 透传写在 `extra.update` **之后**且用 `key not in data` 判断：subagent 回退路径的 `degradedReason` 优先，不破坏既有 `test_subagent.py` 断言；
- `errorCode`/`degradedReason` 只进 `final` 事件，`AgentRunResponse`（`schemas.py:630`）字段未变，`/v1/agent/run` 响应结构不受影响；
- 其它失败分支（工具失败、LLM 规划失败）语义未动，**没有顺手扩大改动面**。

### 3.3 修复后该用例观测

- `bridge.answer_calls == 1`（确实走了"有 contexts → Java 定稿"分支，不是被结构化答案短路）；
- `final.degraded=true`、`refused=false`、`errorCode=AGENT_UPSTREAM_ERROR`、`degradedReason="Java 定稿失败：Java 内部接口返回 502：Bad Gateway"`；
- `answer` 为上游失败文案，不等于 `REFUSAL_TEXT`；`generator="upstream-error"`。
