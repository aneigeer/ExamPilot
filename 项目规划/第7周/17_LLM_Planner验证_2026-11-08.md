# LLM Planner 验证报告（2026-11-08）

> 性质：**只读探测**。未改代码 / 配置 / 数据，未重启或停止 8000、8080，未训练、未提交。
> 目的：验证 `/v1/agent/run` 的 `generator=agent-rule` / `degraded=true` 到底是「LLM planner 失败回退」还是「结构化工具结果正常合成 / 答案侧降级」。
> 证据：`evidence/llm_planner_validation_20261108.json`（3 条完整 events + final + 耗时）。

---

## 0. 结论摘要

| 判定项 | 结论 |
|---|---|
| **LLM planner 是否可用** | **可用**（3/3 用例每一步规划都走 `LlmPlanner` → Java 代理，HTTP 200） |
| 是否发生 fallback | **否**。全程无 `LLM 规划不可用` 日志、无「大模型规划不可用，已切换规则规划器」thought 事件 |
| `generator=agent-rule` 的含义 | **不是** planner 回退，而是 `_finalize` 在「无检索 contexts + 结构化工具结果」时用本地规则合成答案（`harness.py:573-582`，该分支固定 `degraded=True`） |
| 用例 A 的 `degraded=true` | **答案侧**降级：Java L3 幻觉校验（正文无引用编号）丢弃 LLM 正文 → 切抽取式，与 planner 无关 |
| 用例 C 的 `generator=ollama/degraded=false` | planner 可用，但**决策质量弱**：Wiki 命中跨学科页面仍判「未找到」，重复调用同一工具 2 次（去重生效），最终答案退化为「未找到相关资料」 |

一句话：**LLM planner 已经在工作；上一轮报告里的 `generator=agent-rule` 是把「答案生成路径」误读成了「规划路径」。**

### 2.2 无 fallback 的负证据

对 `ai_service_v2_stderr.log`、`ai_service_v2_stdout.log`、`ai_service_v2_stdout.log.prev` 全量检索：

- `LLM 规划不可用` → **0 命中**
- `PlannerError` → **0 命中**
- `大模型规划不可用，已切换规则规划器` → **0 命中**（3 份 events 里也没有该 thought）
- `工具调用超时` / 会话 deadline 触发 → **0 命中**

`harness.py:296-305` 是唯一会把 planner 切到规则的地方（`except PlannerError` + 该条 thought）；两条信号都缺席，即 planner 未回退。

### 2.3 决策内容本身可区分两套规划器

| 判据 | 规则规划器（`RulePlanner`） | 实测 |
|---|---|---|
| 首次 thought | 固定文案「默认先检索站内资料」/「规则匹配到意图「x」」 | A「需要先确认值传递和地址传递的具体区别」、B「需要获取学生最近未掌握的错题信息」、C「需要查询函数专题的 Wiki 页面内容」 |
| 检索参数 | `search_knowledge` 恒为 `{query: 原问题, topK:5}`；`search_wiki`/`get_wrong_book` 恒为 `{}` | A 的 query 被压缩为「值传递和地址传递的区别」；C 的 `search_wiki` 显式 `topK=3` |

## 3. A / B 的降级来源（与 planner 无关）

### 3.1 用例 A：Java L3 引用校验拦截草稿（`backend_start6_20261108.log`）

```text
2026-11-08 16:12:55.173 [http-nio-8080-exec-8] INFO  [a9136db9043a4846] RetrievalService - [AI] 检索命中 4 块（模式 FULLTEXT_OR，最高分 1.2549，内容覆盖度 1.00，耗时 7 ms）：值传递和地址传递的区别
2026-11-08 16:12:58.740 [http-nio-8080-exec-3] WARN  [a9136db9043a4846] AnswerPostProcessor - [AI] L3 幻觉校验拦截：正文未给出任何引用编号，无法溯源。已丢弃大模型正文（165 字），切换抽取式
2026-11-08 16:12:58.740 [http-nio-8080-exec-3] INFO  [a9136db9043a4846] ExtractiveAnswerClient - [AI] 抽取式生成完成，引用 2 个来源，耗时 0 ms
```

即：planner 已正确 `search_knowledge` → 已用 LLM 给出 step2 final 草稿 → 草稿没写 `[n]` 引用 → 被 L3 丢弃 → `generator=extractive, degraded=true`。**降级点在定稿层，不在规划层。**

### 3.2 用例 B：结构化工具结果走本地合成

`harness.py:573-582`：`contexts` 为空且存在结构化 observation（计划/错题/薄弱/题目）时，直接返回 `generator="agent-rule"、degraded=True`。所以 B 的 `agent-rule + degraded=true` 是**设计如此**的合成路径；它的 step1/step2 规划仍是 LLM 决策（见 §2.1 两条 200）。


问题：`search_wiki` 未带 `subjectId`（请求里也没有 subjectId），命中 10 页全是跨学科页面（pageId 12「Prompting相关面试题」、17「分布式训练DeepSpeed面试题」、38「RAG关键痛点和解决方案面试题」），planner 判断「未找到函数专题」后转 `search_knowledge`；最终 `answer="未找到相关资料[1][2][3]。"` 而 `refused=false`、`degraded=false`，**语义自相矛盾**（这是答案质量/契约问题，不是 planner 不可用）。

## 4. 根因分类

| 维度 | 判定 | 依据 |
|---|---|---|
| 模型名 | 正常 | 后端启动日志 `Ollama 客户端已注册（http://127.0.0.1:11434/v1，模型 qwen2.5-7b-instruct-baseline，超时 90000ms）`；Ollama `/api/tags` 中存在该模型 |
| 路由（Python→Java `/internal/agent/llm`） | 正常 | 每条规划的 httpx 均 `HTTP/1.1 200`；Java 侧 `AgentInternalController#llm` 仅在全部客户端不可用时抛 503，本次未出现 |
| 超时 | 未触发 | Python `llm_timeout_seconds=15`；实测单次规划 1.0~1.5s，最长用例总耗时 7.9s |
| JSON 解析 | 未触发 | 无 `PlannerError`、无「模型输出 JSON 解析失败」、无切换 thought |
| Java LLM 接口 | 正常 | 无 `[Agent] LLM 客户端 xxx 不可用`、无 `AI_LLM_UNAVAILABLE`；`ollama 生成成功` 出现于 A/C 的定稿侧 |

**结论：LLM planner 可用（PASS），无 fallback。** 之前把 `generator=agent-rule` 当作 planner 失败判据是**观测口径错误**。

## 5. 修复建议（按优先级，均未实施）

1. **P0 观测口径**：把 `degraded` 拆成两个维度上报，例如 `plannerSource="llm|rule"` 与 `answerDegraded`，避免再用「`generator=agent-rule` + `degraded=true`」推断规划失败（当前会把 B 类完全正常的结构化路径误判为故障）。
2. **P0 语义一致性**：`refused=false` 却返回「未找到相关资料」（用例 C）应改为 `refused=true`，或由 Java 在 contexts 非空时按 contexts 重写而不是照抄 planner 的拒答草稿。
3. **P1 Wiki 检索域**：`search_wiki` 在请求无 `subjectId` 时未做学科过滤，导致「函数专题」命中 Prompting / DeepSpeed / RAG 页面；建议工具层缺省按用户/学科过滤，或 planner 提示词要求先确认学科。
4. **P1 planner 提示词**：C 在第 3、4 步重复完全相同的 `search_knowledge`（T05 去重兜住，但白烧 2 步）。system prompt 第 4 条已有「不要重复调用」，实测 7B 未遵守 → 建议在 observation 摘要里显式提示「该调用已执行过」，或在 planner 侧直接禁用同参重试。
5. **P2 引用格式**：A 的 LLM 草稿因无 `[n]` 被 L3 丢弃转抽取式。建议 planner system prompt 明确「最终 answer 必须带 [编号] 引用」，或在 `full_answer` 里让 Java 基于 contexts 重写无引用草稿，而不是直接降级抽取式。
6. **P2 回归固化**：把本报告 3 条请求加入 `eval/agent_tasks.jsonl`（当前只有 weak/explain/plan/wrong 四类，缺 Wiki 与地址传递类样本），并把 `plannerSource` 纳入评估指标，F-04 的关闭证据应以「planner 调用 200 + 决策内容命中工具」为准，而非 `generator`。
