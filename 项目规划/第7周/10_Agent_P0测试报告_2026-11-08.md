## 3. 逐条失败原因与建议（**未改生产代码**）

### P0-1 工具名白名单（G-01）— `planner.py:94-108`、`harness.py:265-279`、`tools.py:124-146`

- **失败断言**：幻觉工具 `wiki_search_typo` 仍发出 `tool_call` + `tool_result` 两条事件；`final.tool_calls=1`（预算被扣）；无任何提示。
- **根因**：`parse_decision` 只纠错 `action`，`action="tool"` 时 `tool` 字段不查 `TOOL_NAMES`；`_agent_loop` 先 `budget.try_consume()` 再执行，`ToolRegistry.execute` 用 if/else 兜底返回 `未知工具`。
- **建议**：在 `parse_decision`（或 `_agent_loop` 预算闸门之前）加 `tool not in TOOL_NAMES` 硬拦截 → 不扣预算、不发 `tool_call`、记一条 thought「未知工具已拦截：<name>」；同名常量复用 `planner.TOOL_NAMES`（与 `TOOL_SPECS` 同源，避免双份白名单）。

### P0-2 参数 Schema（G-02）— `tools.py:150-179`、`tools.py:224-228`、`tools.py:340-350`、`tools.py:353-358`

- **失败断言**：4/4 非法输入未统一为「参数错误」；其中两类**已打到 Java**（`query=123` 被 `str()` 强转成 `"123"` 正常检索；`questionId=-5` 拼出 `/internal/agent/tools/question/-5`）；`questionId="abc"` 泄漏 `工具执行异常：ValueError`。
- **根因**：无逐工具 `inputSchema`；只有 `_clamp_int` 兜 `topK/limit`；缺少"先校验后执行"的统一入口。
- **建议**：为 7 个工具补 `inputSchema`（对齐 `mcp_server/server.py` 口径：`query` 必须 `str` 且长度 1..200、`pageId/questionId` 必须正整数、`topK 1..10`、`limit 1..20`），在 `ToolRegistry.execute` 顶部统一校验，失败返回 `ToolResult(ok=False, summary="参数错误：<field> <reason>")` 且**不触网**；`_clamp_int` 只保留给显式越界值（用例已验证 `topK=99→10`、`limit=-1→1` 当前正确，需保留）。
- **顺带**：`get_question` 应先 `int()` 前判类型，禁止把原始字符串直接拼进 URL 路径。

### P0-3a 单次工具超时（G-03）— `harness.py:277-279`、`java_bridge.py:137-141`

- **失败断言**：`tool_timeout_seconds=0.2` 而桩桥睡 1.2s → 会话实耗 1.20s，`tool_result.ok=true`。用例刻意让桩**不实现超时**（模拟"Java 卡死但 TCP 未断"），验证 harness 侧是否兜住 wall-clock。
- **根因**：超时只在 `JavaBridge._post/_get` 交给 httpx；harness 对 `tools.execute` 无 `asyncio.wait_for`，一旦底层挂死整会话被拖住。
- **建议**：`result = await asyncio.wait_for(self.tools.execute(...), timeout=self.settings.tool_timeout_seconds + ε)`，`TimeoutError` → `ToolResult(ok=False, summary="工具超时：<tool> 超过 Ns")`，并写 `elapsedMs`。注明这是**纵深防御**（httpx 超时仍保留）。

### P0-3b 会话级 deadline（G-03）— `config.py:229-232`、`harness.py:217-299`、`AgentStreamService.java:309`/`application.yml:152-154`

- **失败断言**：`AgentSettings` 无 `session_timeout_seconds`；慢规划 6 步实测 1.81s（deadline 上限 1.2s）未截断；终态无「deadline 截止」标记；静态口径 `6×30s=180s ≥ Java SSE 120s`。
- **根因**：三处超时口径（Python 单次 30s×步数、Java SSE 120s、Java→Python 10s）互不约束。
- **建议**：新增 `AGENT_SESSION_TIMEOUT_SECONDS`（建议 ≤ 60，且 `max_steps × llm_timeout` 必须 < 120s 与 Java→Python 10s 可解释），`_agent_loop` 每步开始校验剩余预算，超时 → `final.degraded=true` + `degradedReason="session deadline exceeded"`（或新增 `errorCode`），不得跑满最坏步数。

### P0-4 Java 定稿失败 → REFUSED 失真（G-04）— `harness.py:467-479`、`AgentStreamService.java:244-255`

- **失败断言**：`full_answer` 抛 `JavaBridgeError("HTTP 502")` → `refused=true`、`generator="none"`、`answer="未找到相关资料"`，无任何 error 字段。
- **根因**：`_finalize` 的 `except JavaBridgeError` 只造拒答兜底；Java 侧按 `final.refused` 落 `REFUSED`。
- **建议**：区分「业务拒答（检索无资料）」与「上游故障」：后者返回 `refused=false` + `errorCode="UPSTREAM_FAILED"`/`error="Java 定稿 502"` + `generator="degraded-error"`（或 `status="FAILED"`）；Java 映射为 `FAILED` 并计入 `errorTop5`。注意 `_emit_final` 需要透传新字段（当前只白名单 answer/generator/degraded/refused/step_count/tool_calls/sources）。

### P0-5 重复调用去重（G-06）— `harness.py:265-299`

- **失败断言**：两次完全相同的 `search_knowledge{"query":"x","topK":5}` 被执行 2 次，`final.tool_calls=2`，thought 无「重复调用已跳过」。
- **根因**：仅靠 system prompt 第 4 条「不要重复调用」，代码层无 `(tool, canonical(arguments))` 去重集合。
- **建议**：`_agent_loop` 内维护会话级 `seen: set[(tool, json.dumps(arguments, sort_keys=True))]`；重复命中 → 不扣预算、不执行，发 thought「重复调用已跳过：<tool>」，并直接进入下一轮规划（避免死循环：连续 N 次重复后 break 到 final）。
- **备注**：用例的「重放幂等」子项当前**通过**（两次运行工具序列与答案一致），说明无跨请求状态，去重可安全实现为会话内状态。

### P0-6 审计日志（G-09）— `tools.py:141-146`、`harness.py`（无 audit）、`AgentStreamService.java:526-571`

- **失败断言**：3 次工具调用（2 成功 + 1 缺参失败）→ 按 `traceId=0123456789abcdef` 检索到 **0 条**日志；成功路径完全无痕。
- **根因**：Python 只在 `except` 分支 `logger.warning/exception`；成功调用零日志；Java checkpoint 只记 `event/tool/argKeys`，缺 `ok/elapsedMs/userId`。
- **建议**：在 `_agent_loop` 的 `tool_result` 处统一打一条结构化 INFO（`traceId/userId/step/tool/argKeys/ok/elapsedMs/errorCode`），**只记参数键名不记取值**（用例已断言 `query` 明文与错题题干不得出现）；Java checkpoint 同步补 `ok/elapsedMs/userId` 三字段以便成功率统计与归因。
