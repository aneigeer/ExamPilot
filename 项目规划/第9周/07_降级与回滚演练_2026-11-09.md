### 2.3 降级行为评价

**做对的地方**

1. **零 5xx**。4 次降级探测全部 HTTP 200，前端不需要任何改动即可继续使用。
2. **答案质量不塌**。域内问题由 wiki 通道（`WIKI_NGRAM`）接管，答案与基线**逐字相同**（`answer_len=343`），用户几乎无感。
3. **不放大幻觉**。域外问题 `refused=true`、`sources=[]`，没有因为主链路缺失而硬编一个答案——这是最容易被做坏的一点，本项目做对了。
4. **失败可见且收敛快**。3 次失败在 0.5s 内完成计数并开启 60s 熔断，避免每次请求都去撞一个死端口。

**做错/不足的地方**

1. **熔断状态对外不可观测**（R2 / P1）。日志说熔断已开 60000ms，但 `/api/ai/capability` 在 21:02:34、21:03:13、21:03:34 三次都返回 `circuitOpen=false`、`circuitRemainingMillis=0`。运维只能翻日志才知道熔断在起作用。
2. **`ask.degraded` 说「没降级」**（R4 / P2）。AI 服务明明不可达，`ask` 却返回 `degraded=false`，同时 `capability.degraded=true`。同一个系统两个字段给出相反答案，任何依赖 `ask.degraded` 做告警的规则都会漏报。
3. **文档让人看一个不存在的字段**（R3 / P1）。`docs/AI降级演练手册.md` 的排障速查表要求看 `capability.degradedReason`，实测响应里根本没有这个字段。照手册排障的人会当场卡住。
4. **自愈链路是断的**（R1 / P0）。看门狗脚本 26ms 就退出，等于没有看门狗；本次恢复完全靠人工，250s 里有相当一部分耗在排查脚本为什么起不来。

### 2.4 恢复过程的两点必须如实记录

**① 看门狗不可用（R1，P0）**

`ai-service/run_watchdog_v2.ps1` 在 21:04:04.573 启动，26ms 后退出：

```
[2026-11-09 21:04:04.593] LAUNCH uvicorn port=8000 restart_no=0
[2026-11-09 21:04:04.599] WATCHDOG_EXIT
Start-Process : 已添加项。字典中的关键字:"Path"所添加的关键字:"PATH"
所在位置 ...run_watchdog_v2.ps1:148 字符: 17
+ $proc = Start-Process -FilePath $Python ...
```

根因是 PowerShell 5.1 在 `Start-Process` 转换环境变量字典时，遇到同时存在 `Path` 与 `PATH` 两个键（大小写不敏感去重冲突）直接抛 `ArgumentException`。**这不是演练环境的问题，是脚本本身的兼容性缺陷**——只要是 Windows + 双 Path 变量的机器就必然复现。

**② 意外二次中断（如实披露）**

第一次恢复用的 uvicorn 是会话托管的后台任务拉起的，任务被回收时子进程一起被杀（存活 2m3s），导致 21:09:03 – 21:10:4x 出现约 100s 的**计划外二次中断**。最终改用 WMI `Win32_Process.Create` 创建脱离会话的独立进程才稳定下来。

**结论：看门狗修好之前，AI 服务的恢复能力依赖"有人手工拉起一个不会被回收的进程"——这在生产上等于不可恢复。**

关键错误行：

> **重要发现（R5 / P2）**：日志顺序是「**Tomcat 先起来 → 8s 后才因数据源失败退出**」。也就是说，错误发布在头 8 秒里**确实在监听 8081**。如果发布脚本用「端口监听」判断成功，会把一次失败发布判成成功。发布门禁必须用 `/api/actuator/health` 200 + 进程存活。


| Tomcat 就绪 | 21:07:42.221 | `Started ExamPrepApplication in 9.329 seconds` |

**从进程启动到 health 200 仅 8 秒** —— 这就是回滚 RTO 的实测基线。

| 检查 | 结果 |

**结论：全项目没有任何一份文档能在发布失败时被人照着执行一次回滚。** 这是 P1。

### 4.2 应补内容（可直接落成 `docs/部署文档.md` 的 §7）

1. **发布前置留档**：备份上一版 `exam-prep-backend-*.jar` 与 `application-local.yml`，文件名带版本号 + 时间戳，保留最近 3 份。
2. **发布门禁（硬信号，三者全满足才算成功）**：
   - 进程存活且未非 0 退出；
   - `/api/actuator/health` 返回 200；
   - 冒烟三项全绿：登录 + 一次 `/api/ai/ask` + 一次文件上传预览。
   - **明确禁止**用"端口已监听"判成功（本次实测错误发布能监听 8081 达 8s）。
3. **回滚判定阈值**：新版本 120s 内未返回 health 200，或关键接口出现 5xx → 立即回滚，不再观察。
4. **回滚操作（可复制）**：停新进程 → 用上一版 jar + 上一份配置启动 → 等 health 200 → 跑冒烟三项 → 记录 traceId 归档。
5. **隔离演练规范**：回滚预演固定用 `--server.port=8081`，禁止在 8080 上直接试错（本次按此执行，零影响）。
6. **数据库变更纪律**：只允许向前兼容迁移，禁止破坏性 DDL；不可回滚的变更必须先联机备份（现有 §3 的 mysqldump 可复用）。
7. **RTO 参考基线**：错误配置启动失败 13.7s、稳定版启动到 health 200 为 8s（本次实测，可直接写进文档作为验收值）。

## 7 R1 修复与复验

### 7.1 根因定位（比首轮判断更精确）

首轮只看到"`Start-Process` 抛 `ArgumentException`"，收口阶段进一步确认：**宿主环境里同时存在三份同名环境变量**。

```
PATH_KEYS = Path | PATH | path        COUNT = 3
  [Path] len=2527   C:\Users\15241\.workbuddy\binaries\node\versions\22.22.2-6;...
  [PATH] len=2368   C:\workboddy\WorkBuddy\resources\app.asar.unpacked\cli\vendor\shim\safe-bin;...
  [path] len=2527   C:\Users\15241\.workbuddy\binaries\node\versions\22.22.2-6;...
```

Windows 环境块**区分大小写存储**（所以三份能并存），而 `Start-Process` 构造 `ProcessStartInfo.EnvironmentVariables` 用的是**大小写不敏感**的 `StringDictionary`，逐个 `Add` 时第二个 `PATH` 就撞车 → `已添加项。字典中的关键字:"Path"所添加的关键字:"PATH"` → 脚本在 `LAUNCH` 之后 26ms 内 `WATCHDOG_EXIT`。

### 7.2 采用的方案

**方案 A（主）+ 方案 B（兜底）**，只改 `ai-service/run_watchdog_v2.ps1`，不动任何 Java / Python 源码。

| 改动 | 位置（行号） | 内容 |
|---|---|---|
| 新增 `-Port` 参数（默认 8000） | 39 | `[int]$Port = 8000`，删除原来写死的 `$Port = 8000` |
| 新增 `Repair-ProcessPath` 函数 | 118–134 | 取 `[Environment]::GetEnvironmentVariables()`，把所有 `-ieq 'Path'` 的键按 `;` 拆分去重合并，逐个 `SetEnvironmentVariable(key,$null,'Process')` 删除，再写回单份 `Path`，返回被合并的键数 |
| 互斥量按端口区分 | 138 | `Global\ExamprepAiServiceWatchdogV2_$Port`，使 8001 演练与 8000 互不阻塞 |
| 拉起前归一 + 落日志 | 159–162 | `$dupKeyCount = Repair-ProcessPath`，>1 时打 `ENV_NORMALIZED duplicate_path_keys=N` |
| `Start-Process` 包 try/catch + 兜底 | 187–206 | 首选仍是 `Start-Process`（保留文件级 stdout/stderr 重定向，崩溃现场可留档）；失败则打 `WARN` 并用 `System.Diagnostics.ProcessStartInfo`（`UseShellExecute=false`、`CreateNoWindow=true`）直接起进程，绕开环境字典构造；两条路都失败才 `FATAL ... break`，不再无声秒退 |
| 文档头补 v2.1 说明与 `-Port` 示例 | 18–33 | 便于后来人知道为什么有这段代码 |

> 选择"方案 A 为主"而不是直接全量换 `ProcessStartInfo`：`Start-Process` 的 `-RedirectStandardOutput/-RedirectStandardError` 能把 uvicorn 的 stdout/stderr 直接落文件，崩溃现场不会被丢；而 `ProcessStartInfo` 走管道重定向时若不读流会写满 4KB 缓冲把子进程堵死。所以保留 A 做主路、B 只做兜底。
