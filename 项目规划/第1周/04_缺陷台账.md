## D-04 【P2】Ollama 模型元数据自报量化等级与实际不符

| 项 | 内容 |
|---|---|
| **现象** | `POST /api/show {"model":"exam-prep-7b"}` 返回 `parameter_size=7.6B`、`quantization_level=F16`、`parent_model=exam-q4_0.gguf`。但模型实际体积 4.3GB（`C:/models/exam-q4_0.gguf` = 4,290,883,424 B），7.6B 参数对应约 4.5 bpw，**不可能是 F16**（F16 应为 ~15GB）。 |
| **复现步骤** | `curl -s -X POST http://127.0.0.1:11434/api/show -d '{"model":"exam-prep-7b"}'` → 查看 `details.quantization_level`；`ls -la C:/models/exam-q4_0.gguf` → 4.29GB |
| **影响范围** | 运维/选型误判：看到 "F16" 会认为显存需求 15GB，与实际 4.8GB 占用不符；也会误导"同量化对比"的口径判断（本轮验收曾因此反复确认）。不影响推理正确性。 |
| **证据** | `/api/show` 响应 + 文件大小；`ollama ps` 显示实际占用 4.8GB / 100% GPU |
| **根因判断** | GGUF 内部分张量保留 F16（如输出层），llama.cpp 取"首个/主导"张量类型作为展示值；导出脚本未统一量化元数据 |
| **建议责任方** | 训练导出（train-export） |
| **目标周次** | 第2周 |

## D-05 【P1】单卡 8GB 并发能力不足：并发 4 时交互请求超时/连接重置

| 项 | 内容 |
|---|---|
| **现象** | 在后台评测以 4 并发持续请求 `exam-prep-7b` 的同时，再发一条普通 `/api/chat` 请求：**120s 超时**；再发一条带【资料】的请求：**90.49s 后连接被重置（WinError 10054）**。同一时刻 `/v1/chat/completions` 在队列空档返回 200（7.26s）。 |
| **复现步骤** | 1. 后台起 4 并发推理：`python training/eval_v2.py --workers 4 ...`<br>2. 并行执行 `curl -X POST http://127.0.0.1:11434/api/chat -d '{"model":"exam-prep-7b","messages":[{"role":"user","content":"C 语言数组下标从几开始？"}],"stream":false,"options":{"num_predict":60}}'`<br>3. 观察：>120s 无响应；第二次请求 90s 后连接重置 |
| **影响范围** | 多用户场景下第 5 个并发请求会排队至超时；App 端表现为"转圈后报错"。**单次请求正常延迟 7–9s，问题只在并发**。 |
| **证据** | 实测记录：`POST /api/chat 基础 → ERR 120.42s timed out`；`POST /api/chat 带资料 → ERR 90.49s [WinError 10054]`；`POST /v1/chat/completions → 200 7.26s`；同期 `nvidia-smi` 显存 7,871/8,188 MiB，GPU 100% |
| **根因判断** | RTX 4060 Laptop 8GB 显存 + `num_ctx=8192` 下模型常驻 4.8GB，4 路并发 KV cache 已接近上限，Ollama 无排队上限保护，超时后连接被 runner 断开 |
| **建议责任方** | AI 服务（并发闸门/队列上限）+ 部署（限制 `OLLAMA_NUM_PARALLEL`、下调 `num_ctx`） |
| **目标周次** | 第2周（需在网关层加入并发限流与排队超时提示） |
| **备注** | 本轮接口层其余用例因服务未部署无法执行，**该并发结论来自 Ollama 层实测，可代表线上推理层瓶颈** |

## D-06 【P1】题库存在仅 2 个选项的单选题（听力/小样本类），选项完整性无强校验

| 项 | 内容 |
|---|---|
