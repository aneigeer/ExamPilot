# 故障处理手册（Troubleshooting Runbook）

> 项目：大学生多考试备考知识库与题库系统
> 版本：2026-11-10（第 10 周新增）
> 适用：AI 服务不可用、数据库连不上、上传失败、限流 429、端口占用等常见故障
> **本文不含任何明文口令/密钥/token**

---

## 0 故障处理总原则

1. **先看错误码，再猜原因。** 本项目所有响应统一格式 `{"code":..,"message":..,"traceId":..}`，`code` 与 HTTP 状态码可分离，**不要只看 HTTP**。
2. **先拿 traceId，再查日志。** 没有 traceId 的排查等于盲猜；拿到后 `grep -a <traceId> logs/*.log`。
3. **AI 相关故障几乎都不阻断主业务。** AI 全链路有降级（Wiki 热层 → RAG 冷层 → 抽取式兜底），**AI 挂了刷题/资料/管理端照常用**。所以不要因为 AI 报错就重启后端。
4. **不要用「重启一切」当第一手段。** 先按本文定位；重启会丢现场（尤其看门狗日志）。
5. **禁止在 8080 上直接试错。** 需要验证启动/回滚时用 `--server.port=8081`（第 9 周演练纪律）。

## 1 AI 服务不可用

### 1.1 典型症状

| 症状 | 位置 |
|---|---|
| 前端提示「服务暂不可用」 | AI 模拟面试页 |
| AI 问答答案变成「原文摘录」风格、`degraded=true`、`extractiveMode=true` | `/api/ai/ask` 响应 |
| `POST /api/ai/agent/stream` 返回 **503** | 这是**正常配置**，不是故障（见 §1.5） |
| `GET /api/ai/capability` 返回 `aiServiceStatus != "ok"` | 需登录 |

### 1.2 定位步骤（按序，每步都有明确判据）

```bash
# ① AI 服务进程在不在
netstat -ano | grep -a ':8000'
#   无监听 → 跳到 1.3 启动；有监听 → ②

# ② 服务自身健康
curl -s http://127.0.0.1:8000/v1/health
#   连接失败 → 进程僵死，杀进程后重启（1.3）
#   {"status":"ok"} → 服务活着，跳到 ③

# ③ embedding / 向量库子状态（看 /v1/health 的这两个字段）
#   embedding.ready=false 且 detail 提到模型缺失 → 1.4
#   qdrant.ready=false → Qdrant 本地持久化目录 ./data/ 损坏或无权限

# ④ Ollama 在不在、模型有没有
curl -s http://127.0.0.1:11434/api/tags
#   无 qwen2.5-7b-instruct-baseline → 见 docs/模型切换手册.md §2

# ⑤ 后端到 AI 服务的连通
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/v1/health
#   后端配置项：AI_SERVICE_URL（默认 http://127.0.0.1:8000，application.yml:317）

# ⑥ 后端侧降级判断（需登录 token）
curl -s http://127.0.0.1:8080/api/ai/capability -H "Authorization: Bearer <token>"
#   关注：available / degraded / circuitOpen / extractiveMode / chunkCount / vectorEnabled
```

### 1.3 启动 / 重启 AI 服务

```bash
# 前台（最简单，可见日志）
ai-service\run.bat

# 后台看门狗（推荐）
powershell -ExecutionPolicy Bypass -File ai-service\run_watchdog_v2.ps1 -Port 8000
```

`run.bat` 会做两件事：激活 `..\.venv-ai` 虚拟环境、从 `ai-service\.env` 读配置（读不到会提示修复路径）。**若提示找不到虚拟环境，先执行 `ai-service\install.bat`。**

### 1.4 embedding 模型缺失

- 表现：`/v1/health` 的 `embedding.ready=false`，`detail` 提到 `bge-small-zh-v1.5` 未找到。
- 处置：`ai-service\install-model.bat`（下载 bge-small-zh-v1.5 ONNX INT8，约 28 MB）。
- 注意：**正常状态下 `loaded=false` 是懒加载，不是故障**——首次 `/v1/embed` 调用会加载，约 0.2–1 s。判断依据是 `ready` 与 `detail`，不是 `loaded`。

### 1.5 看起来像故障但其实正常的三种情况

| 现象 | 真实原因 |
|---|---|
| `POST /api/ai/agent/stream` → **503** | `app.ai.agent.enabled=false`（默认关闭），Agent 功能整体关闭，`/ai/ask` 不受影响 |
| `POST /api/internal/agent/run` → **403** | `app.ai.internal-token` 为空时的**安全默认值**，不是配置错误 |
| AI 问答 0.4 秒就返回 | 命中了 **Wiki 热层**（`generator=wiki`, `retrievalMode=WIKI_NGRAM`），不是「模型没工作」 |
| AI 问答 20–45 秒 | 本地 7B 在 CPU 上生成的正常耗时（客户端超时 90 s，`ollama-timeout-millis: 90000`） |

### 1.6 熔断器已打开怎么办

```bash
curl -s http://127.0.0.1:8080/api/ai/capability -H "Authorization: Bearer <token>" | grep -o '"circuitOpen":[a-z]*'
```
- 打开原因：连续 **3** 次失败（`circuit-breaker-threshold: 3`）或单次超时（云端 `timeout-millis: 8000`）。
- 处置：先修根因（AI 服务/Ollama/网络），熔断器会按时窗自动半开；**不要靠重启后端强制关熔断**，那样下一次请求还是会失败。

## 2 数据库连不上

### 2.1 症状与判据

| 症状 | 含义 |
|---|---|
| 后端启动即退出，日志 `Communications link failure` / `Access denied for user 'root'` | 连不上或口令错 |
| 启动日志 `Could not resolve placeholder 'DB_PASSWORD'` 或直接数据源初始化失败 | **`DB_PASSWORD` 未注入**（本项目**故意不设弱口令兜底**，这是预期行为） |
| 运行中接口突然全部 500 | 连接池耗尽或 MySQL 挂了 |

### 2.2 定位步骤

```bash
# ① MySQL 服务在不在
net start | grep -i mysql
netstat -ano | grep -a ':3306'

# ② 用项目自带客户端配置连一下（免交互、凭据从 cnf 读，不会在命令行暴露）
mysql --defaults-file=config/mysql-client.local.cnf -N -B -e "SELECT 1;"
#   成功 → 跳到 ④
#   ERROR 1045 → 口令错（见 2.3）
#   ERROR 2003 → 服务没起或端口不通（跳到 ③）

# ③ 起服务
net stop mysql && net start mysql    # 需管理员权限

# ④ 确认库与表在
mysql --defaults-file=config/mysql-client.local.cnf -N -B -e \
  "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='exam_prep';"
#   期望 56；若为 0 → 库未初始化，见 docs/数据更新手册.md §1

# ⑤ 确认后端环境变量真的注入了（不要打印值，只看是否存在）
#   Windows PowerShell:
#   if ($env:DB_PASSWORD) { "DB_PASSWORD 已设置" } else { "DB_PASSWORD 缺失" }
```

### 2.3 口令错（ERROR 1045）

1. **不要**在命令行 `-p<口令>`。用 `--defaults-file=config/mysql-client.local.cnf`。
2. 确认口令来源只有一个：`config/secrets.local.yml`（已 gitignore）。若与实际库口令不一致 → 按 `docs/部署文档.md` §9.2 重新轮换。
3. 远程连接被拒（即使口令对）是**正常且期望**的：`root@'%'` 已删除，只剩 `root@localhost`。
4. **轮换口令后必须**：更新 `DB_PASSWORD` 环境变量 → 重启后端 → 复验 health 200。

### 2.4 为什么「口令错」不是弱口令兜底的锅

`application.yml:24` 是 `password: ${DB_PASSWORD:}`，默认空。**空口令不等于可以连**——MySQL 侧 root 已改强口令，两者不匹配必然 1045。这是**故意设计**：宁可启动失败，也不要静默回退到弱口令。

## 3 上传失败

### 3.1 先分清是哪个上传入口

| 入口 | 支持类型 | 限制 |
|---|---|---|
| **App / 学生端网页** | **仅图片**：`jpg,jpeg,png,webp,gif` | 单文件 ≤ **10 MiB**（`app.upload.image-max-size: 10485760`） |
| **管理端「文件上传」** | 文档类 `PDF/DOCX/ZIP` 等 | 文档 **200 MB**；nginx 侧兜底 `client_max_body_size 210m` |

> **「App 上传 PDF 报 415」不是 bug**：App 端只收图片，文档必须走管理端上传。见 `docs/用户手册.md` §5。

### 3.2 按错误码分流

| 错误码 | 原因 | 处置 |
|---|---|---|
| **415** | 类型不在白名单（如在 App 端传 PDF） | 换正确入口；或检查文件真实 MIME（改扩展名骗不过） |
| **413** | 超过大小上限 | 图片压到 10 MiB 内；文档压到 200 MB 内；同时确认 nginx `client_max_body_size 210m` 未被改小 |
| **401** | 未登录 / token 过期（7 天） | 重新登录 |
| **429** | 触发限流（注册 3 次/60s、登录 5 次/60s） | 等 60 秒；见 §4 |
| **500 且日志含磁盘/权限关键字** | `uploads/` 目录不可写或磁盘满 | 见 3.3 |
| **提交后一直「待审核」** | 不是故障，是正常审核流 | 管理端审核 |

### 3.3 存储侧排查

```bash
# 目录是否存在、可写
ls -la uploads/            # 期望存在 documents/ 与 preview/ 两个子目录
# 磁盘空间
df -h .                    # Linux；Windows 用：wmic logicaldisk get size,freespace,caption

# Docker 部署时确认数据卷挂载（uploads 必须持久化到宿主机）
docker compose config | grep -A3 uploads
```

**Docker 场景特有坑**：`./uploads` 必须挂到容器 `/data/uploads`（`docker-compose.yml`），否则容器重建后文件全丢，表现为「上传成功但预览 404」。

### 3.4 上传后预览/下载失败

| 症状 | 原因 |
|---|---|
| 预览只看到 3 页低清带水印 | 未登录（游客限制 `app.preview.guest-pages: 3`），属正常 |
| 下载链接点开 403/404 | **签名链接 10 分钟过期**，重新点下载获取新链接 |
| 图片 404 但文件在 | `uploads/` 与静态资源映射不一致；Docker 场景优先查数据卷 |

## 4 限流 429（请求过于频繁）

### 4.1 阈值（代码事实）

| 接口 | 阈值 | 窗口 | 证据 |
|---|---:|---:|---|
| 登录 `/api/auth/login` | **5 次** | 60 s | `backend/src/main/java/com/examprep/config/RateLimitFilter.java:29` |
| 注册 `/api/auth/register` | **3 次** | 60 s | 同上 `:30` |

- 窗口常量 `WINDOW_MS = 60_000L`（`:31`）。
- 超限响应体固定：`{"code":429,"message":"请求过于频繁，请稍后再试","data":null}`（`:68-71`）。
- 第 9 周实测：第 **6** 次登录开始 429，封禁 **60.28 秒**后自动恢复。

### 4.2 处置

1. **等 60 秒**。这是滑动窗口，不是永久封禁。
2. 确认不是「口令记错反复试」——连续失败会一直占桶。
3. 若是**批量测试**打出来的 429：测试脚本里加 `sleep`，或每个用例换合法账号（不要靠伪造 `X-Forwarded-For`，见 4.3）。
4. 桶上限 `MAX_BUCKETS = 10_000`（`:33`），超限后按实现会清理最旧桶；正常使用不会撞到。

### 4.3 ⚠ 限流分桶与 `X-Forwarded-For`：三种现象要分清

**先确认你跑的是哪个版本**：冻结的 jar（2026-11-10 17:55）内 `RateLimitFilter` 无条件采信 `X-Forwarded-For` 的第一个 IP，**换头即换桶、防护失效**（第 9 周实测「换 IP 后立刻从 429 变 200」）。源码已修（`ClientIpResolver` + `app.rate-limit.trusted-proxies`），但**未进入 jar**。先判断版本，再看对应现象：

```bash
# 判断修复是否在当前构件里（有输出 = 已含修复）
unzip -l backend/target/*.jar | grep ClientIpResolver
```

#### 现象 A：怎么试都不 429（可换头绕过）

- 版本：**旧 jar**，或 nginx 用回了 `$proxy_add_x_forwarded_for`。
- 判据：`grep -n "proxy_add_x_forwarded_for" nginx*.conf*` 有输出即中招。
- 处置：重建 jar；nginx 改 `proxy_set_header X-Forwarded-For $remote_addr;`（**覆盖**，不是追加）。

#### 现象 B：正常用户频繁互相 429（全站共用一个桶）

- 版本：**新 jar + 容器部署但没配白名单**。
- 根因：后端看到的 TCP 对端是 nginx 容器 IP，不在 `trusted-proxies`（默认 `127.0.0.1,::1`）内 → XFF 被忽略 → **所有客户端退回同一个 IP**。
- 判据：`grep -n -E "ipam|subnet|APP_RATE_LIMIT_TRUSTED_PROXIES" docker-compose.yml` **无输出**即中招。
- 处置：先钉死 subnet，再让白名单与之完全一致：
  ```yaml
  services:
    backend:
      environment:
        APP_RATE_LIMIT_TRUSTED_PROXIES: "172.28.0.0/16"   # 必须与下面 subnet 一致
  networks:
    default:
      ipam:
        config: [{subnet: 172.28.0.0/16}]
  ```
- **不要**图省事写 `172.16.0.0/12`：backend 端口一旦发布到局域网，攻击者真实 IP 就落在可信段内 → 伪造 XFF 直接生效，比不修更糟。

#### 现象 C：一切正常（本地直连形态）

- 本项目当前形态是 `java -jar` 直接监听 8080（无 nginx），后端看到的就是真实客户端 IP，XFF 一律被忽略 → **默认配置即正确**，无需额外配置。

#### 验收口径（别用「日志里看不到 IP」当判据）

`RateLimitFilter` **不打日志**（只有 `OperationLogService` 记操作日志，且其 IP 取值有同族信任问题，已登记为 P2）。因此可验收的口径是**行为**而非日志：

| # | 判据 | 期望 |
|---|---|---|
| 1 | 直连场景，每次请求换一个伪造 `X-Forwarded-For`，连续 6 次登录 | 第 6 次仍 **429**（而非 200） |
| 2 | 容器场景，8 个不同真实客户端各登录 1 次 | **全部放行**，互不干扰（不出现「第 6 个才开始 429」） |
| 3 | `trusted-proxies` 置空或配错 | 退化为「不信任任何代理」，取 `remoteAddr`（**不会**变成「信任所有人」） |
| 4 | `trusted-proxies` 留空串 | 同上，安全默认 |

- **禁止**：为了让压测跑通就在测试脚本里伪造 `X-Forwarded-For` —— 那等于把缺陷当功能用。

## 5 端口占用

### 5.1 定位

```bash
# 谁占了 8080
netstat -ano | grep -a ':8080'
# 取到 PID 后看是什么进程
tasklist | grep -a "<PID>"
# 或（PowerShell）
Get-Process -Id <PID> | Select-Object Id,ProcessName,Path
```

### 5.2 常见占用者

| 端口 | 常见占用者 | 处置 |
|---|---|---|
| 8080 | 上一次没退干净的后端进程 / 其他 IDE 调试实例 | `taskkill /PID <PID> /F`；切勿盲目 `taskkill /IM java.exe`（会杀掉 IDE 语言服务器） |
| 8000 | 上一次的 uvicorn / 看门狗拉起的实例 | 先停看门狗再杀 uvicorn，否则看门狗立刻又拉起一个 |
| 3306 | MySQL 服务（正常）；若被其他 MySQL 实例占用则冲突 | 只应有一个实例；`net start` 报错时查 `data/*.err` |
| 11434 | Ollama（正常） | 不要杀，杀了 AI 问答降级 |

### 5.3 换端口跑（推荐用于验证/回滚预演）

```bash
# 后端换 8081（第 9 周演练纪律：禁止在 8080 上直接试错）
java -jar backend/target/exam-prep-backend-1.0.0-SNAPSHOT.jar --server.port=8081
# 验证完立刻停掉，避免和 8080 实例共享数据库造成异步任务误伤
```

> **双实例警告**：两个后端实例共享同一 MySQL 会误伤运行中的异步任务（第 9 周实测 `Updates: 0` 未致损，但机制上未隔离）。验证窗口要避开有长任务的时段。

### 5.4 防火墙导致「端口在听但外部连不上」

- 后端监听 `0.0.0.0:8080` ≠ 外部可达。Windows 防火墙需放行（项目内 `放行8080端口(需管理员).bat`）。
- **但注意**：放行 8080 到公网 = 把无 TLS 的 HTTP 后端直接暴露。正式部署应走 nginx（`nginx-https.conf`）而不是裸放行。

## 6 其他高频故障速查

| 现象 | 最可能原因 | 处置 |
|---|---|---|
| 启动即失败，日志提到 `JwtUtil` / `secret` | `JWT_SECRET` 为空（**预期行为**） | 注入 `JWT_SECRET`，见 `docs/部署文档.md` §9.1 |
| 所有接口 401 | token 过期（7 天）/ 服务端换了 `JWT_SECRET` | 重新登录；密钥轮换会使全部 token 失效 |
| 所有接口 401 但刚登录成功 | 请求头格式不对：必须是 `Authorization: Bearer <token>`（含空格） | 见 `application.yml:98-99` |
| 浏览器跨域被拦 | `app.cors.allowed-origins` 默认只有 `http://localhost:8080` | 用 `APP_CORS_ALLOWED_ORIGINS` 覆盖 |
| 管理端页面白屏 | 同源访问路径错：应为 `/api/admin/index.html`（context-path=`/api`） | 补 `/api` 前缀 |
| App 登录提示网络错误 | APK 内置 BASE_URL 是打包时的 IP，换网络即失效 | 见 §7 |
| 静态资源/预览图片 404 | `uploads/` 丢失或 Docker 卷未挂 | 见 §3.3 |
| 页面显示「未找到相关资料」 | 语料里确实没有；不是故障 | 换问法或指定课程/章节 |
| 面试提示「会话已过期」 | 面试会话保留 30 分钟 | 重新开始 |

## 7 Android 端「连不上后端」专项（第 10 周实测）

### 7.1 根因不是网络，是构件失配

第 10 周复验：`备考知识库学生端-v1.9.1-真机版.apk` 的 `BASE_URL` 实测为 **`https://10.200.83.194/api/`**，而当轮本机局域网 IPv4 为 **`10.200.86.72`**（且历史任务书曾记为 `10.200.1.56`）——**三者互不相同，说明该机 IP 本身在漂移**。

因此「App 连不上」的正确表述是：**APK 里写死的 IP 与当轮实际 IP 不匹配**，不是手机/防火墙问题。

### 7.2 排查顺序（先排除构件问题，再查网络）

```bash
# ① 从 APK 里读出它到底指向哪（这是唯一权威来源）
unzip -p "备考知识库学生端-v1.9.1-真机版.apk" classes.dex | grep -a -o "https\?://10\.[0-9.]*/api/"

# ② 看本机当轮 IP
ipconfig | grep -a IPv4

# ③ 两者不一致 → 结论已定：必须重新打包（改 build.gradle 的 BASE_URL）
```

### 7.3 为什么改 IP 也未必能连（证书）

APK 走 HTTPS，且 `student-app/app/src/main/res/xml/network_security_config.xml:25` **只白名单 `10.200.83.194`**。把 BASE_URL 改成新 IP 后，自签证书 SAN 不覆盖新 IP → `SSLHandshakeException`。

### 7.4 本轮推荐替代方案

**直接用学生端网页版**：`http://<当轮本机IP>:8080/api/student/index.html`。零构建、零证书、功能面高度重合（`docs/用户手册.md` §3 描述的功能在网页版均有对应入口）。原生 App 需另开一轮重建 + 重算 SHA256。

## 8 故障升级路径

| 级别 | 判据 | 动作 |
|---|---|---|
| L1 自愈 | AI 服务掉线、端口占用、429 | 按本文处置，无需上报 |
| L2 需介入 | 数据库连不上 / 启动失败 / 上传全链路不可用 | 通知运维，记录 traceId 与时间点，保留日志现场 |
| L3 阻断 | 数据丢失 / 疑似越权 / 口令泄露 | **立即停止对外服务**，保留现场，按 `docs/部署文档.md` §9 轮换凭据，启动回滚（§7） |
| L4 事故 | 需要回滚版本 | 按 `docs/部署文档.md` §7「发布失败回滚」执行，全程记录时间线 |

**任何 L2 以上的故障，处理完必须留一份记录**到 `项目规划/第N周/evidence/`（现象、traceId、根因、处置、耗时、遗留）。
