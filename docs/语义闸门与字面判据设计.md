## 1. 问题定义

### 1.1 先厘清现有闸门的实际分工（读代码所得，非推测）

系统里其实有**四道**拒答判据，分散在两处，这是理解全部争议的前提：

| # | 判据 | 位置 | 判什么 | 阈值 |
|---|---|---|---|---|
| ① | 分数阈值 | `RetrievalService` ⑤ | `finalScore < 0.15` | `rejectThreshold=0.15` |
| ② | 词项覆盖率 | `RetrievalService` ②.5 | `expansionTerms` 命中率（**含虚词 bigram**） | `minTermCoverage`：**代码默认 0.25 / yml 配 0.5** ⚠️ |
| ③ | 内容覆盖度 | `RetrievalService` ⑤ | `contentTerms` 命中率（**仅实词**） | `minContentCoverage=0.45` |
| ④ | 越界词表 | `RetrievalService.outOfScopeHit` | 命中"天气/菜谱/汇率…"任一即拒 | 词表硬编码 |
| ⑤ | **语义闸门** | `HybridRetriever.java:101` | `0 < vectorBest < 0.62` 即拒 | `semanticRejectScore=0.62` |

> **①②③④ 是"字面侧"，⑤ 是"语义侧"。争议焦点是 ⑤ 与 ①②③ 的关系。**
> 作者在 `RefusalGateTest` 注释里写的「两道闸门各管各的、互不否决」是**目标**，但代码里 ⑤ **实际具有一票否决权** —— 这是矛盾点。

### 1.2 误拒长什么样（语义闸门伤害域内）

`HybridRetriever.java:101-105` 的现有逻辑：

```java
boolean semanticReject = applyGate
        && properties.getVector().isEnabled()
        && vectorBest > 0
        && vectorBest < properties.getRetrieval().getSemanticRejectScore();  // 0.62
```

**只要 top1 余弦 < 0.62 就直接 return refused，此时 ngram 已经召回的高相关块被整批丢弃。**

典型形态：**问题问得口语化、但字面高度匹配**。
- 语料里是「C 语言中 int 类型占几个字节」，用户问「32位系统int类型大小」
- bigram 全覆盖，ngram 分数很高；但 embedding 因为句式差异给出 0.58~0.61
- → 被 ⑤ 一票否决，用户问的是库里有答案的问题却得到"未找到"

**作者报告称这类情况在 214 题集上占 26.6%**（未复核，见第 5 章）。若属实，这是严重的产品缺陷——**误拒比漏拒更伤用户**，因为用户会认为"这个知识库没有我要的内容"而直接流失。

### 1.3 漏拒长什么样（字面闸门放过域外）

字面侧判据的根本弱点：**词重叠 ≠ 能回答**。

- 「量子力学波函数如何求解」共享 bigram「函数」→ 被 OR 召回（这是 `minTermCoverage` 存在的原因）
- 「红烧肉的做法是什么」只共享「做法」→ `contentCoverage` 约 0.2~0.33，**③ 拦得住**
- 「区块链智能合约怎么写」→ 覆盖度高、余弦 0.5957 → **只有 ⑤ 拦得住** ← 这是关键案例
- 「明天上海的天气怎么样」→ ④ 越界词「天气」直接拒 → **不受 ⑤ 影响**

### 1.4 ★ 关键发现：两个案例的根因不同（这决定了方案形状）

| 案例 | 字面覆盖 | 余弦 | 实际被谁拦住 | 若加 `&& ngram.isEmpty()` |
|---|---|---|---|---|
| `明天上海的天气怎么样` | 1.00 | — | **④ 越界词表**（`天气`） | **仍然拒答**（④ 在 ⑤ 之前生效，此时 ngram 已空） |
| `区块链智能合约怎么写` | 0.75 | 0.5957 | **⑤ 语义闸门（唯一防线）** | **放行 → 漏拒** ❌ |

**所以工程侧"两条都会重新放行"的预判只对了一半**——team-lead 的独立复跑也证实了这点：**新增漏拒只有 `区块链` 一条，天气没有漏**。

> **这个校正很重要**：真正的漏洞类别不是"所有域外问题"，而是
> **「不在越界词表内、但字面重叠很高」的一类** —— 即"词表覆盖不到的新领域实体"。
> 针对这一类，**继续往越界词表里加词是打地鼠**（今天加区块链，明天就有"元宇宙""NFT"）；需要的是**可判定的通用判据**（见 3.1 的判别性判据）。

## 2. 为什么 `&& ngram.contexts().isEmpty()` 是错的

### 2.1 逻辑形状：单调放宽（与阈值无关，纯布尔代数）

```java
refuse_new = (sim < 0.62) && ngram.isEmpty()      // 改动后
refuse_old = (sim < 0.62)                          // 改动前
```

对任意输入：`refuse_new ⊆ refuse_old`（新增条件只能**收窄**拒答集合）。

⟹ **拒答率只可能下降或持平，永不可能上升。**
⟹ `9/10 → 8/10` 是**逻辑必然**，不是"调参没调好"，也不是"数据波动"。

**推论**：任何以"降低误拒"为目标的改动，只要形状是"给拒答条件加 `&&`"，就**必然以漏拒为代价**。这不是实现问题，是表达式形状问题。

### 2.2 净贡献为 0 —— 决定性证据

team-lead 独立复跑（在线档与降级档）：

| 档位 | 语义闸门是否生效 | 拒答数 |
|---|---|---|
| 在线（向量可用） | 生效 | **8/10** |
| 降级（向量不可用，⑤ 自动失效） | 不生效 | **8/10** |

**两者完全一致 ⟹ 加上 `&& ngram.isEmpty()` 后，语义闸门对最终结果的净贡献 = 0。**

一个"净贡献为零、却损失一次拒答（且失去对 `区块链` 的唯一防线）"的改动，**没有合入价值**。回退成立。

### 2.3 它还顺带删掉了唯一防线

`区块链智能合约怎么写` 只被 ⑤ 拦住（1.4 已证）。改动后 ⑤ 对它失效，而 ①②③④ 都拦不住它（覆盖度高、非越界词）。**这是从"仅剩一道防线"变成"零道防线"。**

### 2.4 断言从 ≥9/10 放宽到 ≥8/10 —— 这是红线，不能做

- 把断言从 90% 降到 80%，等于**用放宽验收标准来让改动变绿**
- 这抹掉的正是"语义闸门在 `区块链` 上的唯一价值"
- **正确做法**：断言保持 `>=9`、`assertEquals(0, falseRefused)` 不动；如果新设计达不到，说明设计不合格，改设计而不是改断言

## 3. 正确形状的候选方案

### 3.1 方案甲（推荐）：语义闸门 + "判别性字面证据"豁免

**核心思想**：语义闸门**可以**被字面证据豁免，但"字面证据"必须是**判别性的**，不是"非空"。

```java
// 设计伪代码（不是业务代码）
boolean literalEvidenceIsDiscriminative =
       !outOfScopeHit(question)                      // ④ 越界词一票否决（已有）
    && contentCoverage(top1, contentTerms) >= 0.60    // ③ 实词覆盖（已有能力，阈值上调）
    && hasRareTermHit(question, top1);                // ★ 新增：判别性命中

boolean refuse = semanticLow && !literalEvidenceIsDiscriminative;
// 注意：是「豁免」，不是「AND 一个空判断」
```

**`hasRareTermHit` 的定义（这是本方案的新增件）：**

```
对 query 的每个 contentTerm t：
    df(t) = 语料中含 t 的 ACTIVE 块数        // 一次 GROUP BY 查询可得
判别性条件：存在 t 满足
    ① t 出现在 top1 块正文中（而不是"只出现在候选池某处"）
    ② df(t) ≤ dfCap（建议 dfCap = 50，即全库 11999 块中占比 < 0.5%）
    ③ t 不在泛词表（"怎么/什么/如何/有哪些/区别/作用/方法"…）
```

**为什么这个形状能同时解决两类错误：**

| 案例 | ④越界词 | contentCoverage | hasRareTermHit | 结果 |
|---|---|---|---|---|
| `C语言合法关键字有哪些` | — | 高 | `C语言`/`关键字` df 适中且**在 top1 里** → ✅ | **豁免 → 放行**（修掉误拒） |
| `区块链智能合约怎么写` | — | 高（智能/合约都在语料） | `区块链` 不在 top1 正文中（top1 靠 bigram 重叠命中）→ ❌ | **无豁免 → 拒答** ✅ |
| `明天上海的天气怎么样` | **命中「天气」** | — | — | **④ 直接拒答** ✅ |
| `红烧肉的做法是什么` | — | 0.2~0.33 < 0.60 | ❌ | **拒答** ✅ |
| `值传递和地址传递有什么区别` | — | 高 | `值传递`/`地址传递` 在 top1 → ✅ | **放行** ✅ |

> **为什么 `区块链` 会失败而 `值传递` 会成功**：这是本方案最精巧的地方。
> `区块链智能合约怎么写` 的 top1 是靠 **bigram「智能」「合约」** 撞上的课件段落，**段落里根本没有"区块链"三个字**。
> 而 `值传递和地址传递` 的 top1 里**真的写着"值传递/地址传递"**。
> **"用户问的关键实体是否真的出现在最佳证据里"**——这才是"可回答性"，而不是"字面重叠度"。

**代价与风险（必须诚实说明）：**
- 需要一次额外的 df 统计（可用 `SELECT content LIKE '%t%'` 或 MATCH 计数，11999 块规模下单次 < 20ms，**但需实测**）
- `dfCap=50` 是拍的值，**必须在 214 题集上标定**（见 4.4）
- 若 `区块链` 恰好出现在某块正文里（df>0 且在 top1），会退化为漏拒 → 需要第 4 章的验收集覆盖这类案例

### 3.2 方案乙：在 214 题 golden set 上重标 0.62

**核心思想**：不改进判据，只改阈值。

**标定流程（可复现）：**
```
1. 用 214 题（203 可回答 + 11 应拒答）跑纯召回模式（applyGate=false），
   导出每题 top1 余弦 → gold_cosines.csv
2. 域内 203 题：算 min、P1、P5、P10
   域外 11 题：算 max、P95
3. 若 域外max < 域内P1  → 存在空档，阈值取 空档中点（且留 ≥0.02 余量）
   若 域外max ≥ 域内P1  → **单阈值不可分**，方案乙单独不可行，必须配方案甲
4. 留出验证：把 214 题按来源分层抽样，80% 标定 / 20% 验证，
   验证集上要求 域内误拒 ≤5% 且 域外拒答 ≥90%
5. 阈值写入 yml（不要只留代码默认值，见 5.3）
```

> **重要预判**：我在 Router 设计里已经实测过**单一相似度阈值在域内/域外之间存在重叠**（域外最高 0.6317 > 域内最低 0.6136，见 `docs/Router与Skill架构设计.md` B.2）。**很可能会重演**。所以方案乙应预设"不可分"这一结论，不要把它当唯一方案。

**代价**：重标只是把错误在"误拒"与"漏拒"之间平移，**总错误量不变**。它不解决"语义与可回答性维度错配"的根本问题。

### 3.3 方案丙（可选）：二段判定 —— 语义只降权，不否决

```
第一段（可回答性）：① ② ③ ④ + 判别性命中  → 决定"能不能答"
第二段（置信度）：  ⑤ 语义分 → 只写 confidence / lowConfidence 标记，不单独拒答
输出：refused / answered_with_low_confidence / answered
```

**优点**：彻底消除"语义否决字面"的缺陷，语义信息不浪费。
**缺点**：引入第三态（低置信作答），需要前端配合展示"仅供参考"，**增加产品复杂度**；且 7B 在低置信下更容易幻觉（与"强制溯源"策略冲突）。

**建议**：本轮**不采用**，除非前端愿意做低置信 UI。记为后续演进。

### 3.4 方案对比与推荐

| 维度 | 甲：判别性豁免 | 乙：重标 0.62 | 丙：二段判定 |
|---|---|---|---|
| 修误拒 | ✅ 直接解决 | ⚠️ 部分是（若可分） | ✅ 解决 |
| 保漏拒 | ✅ `区块链` 仍拒 | ⚠️ 取决于空档 | ⚠️ 需上游策略 |
| 新增依赖 | 1 次 df 统计 | 无 | 前端改造 |
| 可解释性 | 强（"关键实体是否出现在证据里"） | 中（"阈值多少"） | 强 |
| 答辩价值 | **高**（能讲清"可回答性 ≠ 语义相似"） | 低（只是调参） | 中 |
| 风险 | dfCap 需标定 | **可能不可分** | 产品复杂度 |

**推荐组合：方案甲为主体 + 方案乙做参数标定。**
即：判据形状用甲，`contentCoverage` 阈值（0.60）、`dfCap`（50）、`semanticRejectScore`（0.62）**三个参数统一在 214 集上按乙的流程标定**。

## 4. 验收口径（先定后测，避免再"各跑各的样本"）

### 4.1 样本集：统一口径，不许换集

| 集合 | 规模 | 来源 | 用途 |
|---|---|---|---|
| **域内集** | **214 题**（203 可回答） | `ai-service/eval/golden_set.jsonl`（实测 214 行） | 测误拒率、Recall@5 |
| **域外集** | **≥30 题**（现有 10 题 + 新增 ≥20） | 现有 `HybridRetrieverTest` 10 题为基础扩充 | 测拒答率 |
| 冒烟集 | 12 域内 + 10 域外 | 现有单测内联列表 | 仅作单测护栏，**不作指标依据** |

**为什么域外必须扩到 ≥30**：
现有 10 题的最小可分辨差异是 1 题 = 10%。`9/10` 与 `8/10` 在统计上无法区分（同样，`10/10` 与 `9/10` 也不行）。
**rule of three**：n 次零失败时，真实失败率 95% 上界 ≈ 3/n。要证明"漏拒率 ≤10%"，至少需要 **n ≥ 30**（3/30=10%）。

> 这也是我要强调的：**上一轮"12 题 0 误拒"与"214 题 26.6%"之争，本质是样本量不可比，不是谁在说谎。**
> 0/12 的 95% 上界 ≈ 25%，完全容纳得下 26.6%。**双方可能都对。**

### 4.2 三条必须同时满足的指标（缺一不可，不许只报好的）

| # | 指标 | 门槛 | 理由 |
|---|---|---|---|
| **M1** | 域内误拒率（214 题） | **≤ 5%**（≤10 题） | 误拒是最伤用户的失败模式；5% 是产品可接受线 |
| **M2** | 域外拒答率（≥30 题） | **≥ 90%**（≥27/30） | 不低于现有生产基线 |
| **M3** | 高危漏拒率 | **= 0** | 定义：越界词命中 或 `hasRareTermHit=false` 的题，必须 100% 拒答。`区块链` 属此类 |

**M1 与 M2 是此消彼长的，必须同时报，禁止只报一个。M3 是硬约束（防"用放宽换指标"）。**

**基线对照（现有 HEAD 实测，用于判断改动是否真的变好）：**

| 指标 | 回退后 HEAD |
|---|---|
| 生产链路拒答 | 9/10 = 90% |
| 生产链路 Recall@5 | 11/12 = 91.7% |
| 词法通道拒答 | 8/10 = 80% |

> 注意：HEAD 的 9/10 与 11/12 是**12/10 题小样本**，只能作冒烟参考；**M1/M2 必须在 214/30 上重测**，不能拿小样本数字交付。

### 4.3 单测（护栏）与评测（测量）必须分开

| 层 | 载体 | 断言 | 是否可放宽 |
|---|---|---|---|
| 单测护栏 | `HybridRetrieverTest` | `refused >= 9`、`falseRefused == 0` | **不可放宽（红线）** |
| 评测报告 | `ai-service/eval/` 脚本 + `docs/` 报告 | M1/M2/M3 | 按 4.2 门槛 |

**规则**：单测负责"不许退化"，评测负责"是否变好"。**任何情况下都不改单测断言阈值来适配新行为。**

### 4.4 标定顺序（重要：先标后测）

```
① 导出 214 题逐条 top1 余弦 + contentCoverage + df 统计  →  CSV
② 按 3.2 流程确定 semanticRejectScore 与 contentCoverage 门槛（看是否有空档）
③ 按 3.1 标定 dfCap（在 214 集上扫 dfCap ∈ {10,20,50,100}，取 M1/M2 同时最优）
④ 20% 留出集验证
⑤ 三参数写入 application.yml（显式配置，不依赖代码默认值）
⑥ 全量跑 M1/M2/M3，写评测报告
```

> **禁止顺序**：先改代码 → 跑小样本 → 看到数字变好 → 补写文档。这是本次争议的成因，必须避免。
