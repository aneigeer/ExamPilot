# 模型切换手册（Ollama ↔ 在线 API）

> 项目：大学生多考试备考知识库与题库系统
> 版本：2026-11-10（第 10 周新增）
> 适用：本地 Ollama 与云端 API（阿里云百炼 / 智谱 GLM）之间的切换、降级、回滚
> **本文不含任何明文 Key**；Key 只通过环境变量注入

## 0 先读这一段（最容易踩的坑）

**`app.ai.llm.provider` 不控制路由。**

配置注释原文（`application.yml`）：
> ⚠️ 注意：`provider` 只影响日志与展示，**实际选路由 `@Order` + `available()` 决定**

真实选路逻辑在 `AiQaService`（`backend/src/main/java/com/examprep/service/ai/AiQaService.java:262-296`）：
按 `@Order` 升序遍历所有 `LlmClient` Bean，跳过 `ExtractiveAnswerClient`（第 296 行 `isProviderCandidate` 双重排除），**取第一个 `available()==true` 的**。

### 0.1 优先级实测（代码 `@Order` 原值）

| 顺序 | 客户端 | `@Order` | 端点 / 模型 | 何时 `available()` |
|---:|---|---:|---|---|
| 1（最高） | `OllamaLlmClient` | **5** | `http://127.0.0.1:11434/v1`，模型由 `ollama-model` 指定 | Ollama 可达且模型已拉取 |
| 2 | `DashScopeLlmClient` | **10** | `https://dashscope.aliyuncs.com/compatible-mode/v1`，`dashscope-model`（默认 `qwen-plus`） | `LLM_API_KEY` 非空 |
| 3 | `FastApiLlmClient` | **15** | 本机 AI 微服务 `AI_SERVICE_URL`（默认 `http://127.0.0.1:8000`） | AI 微服务 `/v1/health` 正常 |
| 4 | `ZhipuLlmClient` | **20** | `https://open.bigmodel.cn/api/paas/v4`，`zhipu-model`（默认 `glm-4-flash`） | 对应 Key 非空 |
| —（兜底） | `ExtractiveAnswerClient` | **30** | 纯本地抽取，零外部依赖 | 永远可用；**被排除出候选，只在全员失败时兜底** |

### 0.2 由此推出的三条硬结论

1. **只要 Ollama 活着且模型在，就永远走本地** → 想让云端生效，必须**先让 Ollama 不可用**（见 §2.2）。改 `provider` 一点用都没有。
2. **`LLM_API_KEY` 留空 = 云端永不参与**（`available()` 直接 false），此时若 Ollama 也挂 → 落到 AI 微服务（`@Order(15)`），再不行 → 抽取式兜底，**接口仍返回 200**。
3. **抽取式兜底不是异常路径**，是设计的一部分。`/ai/ask` 响应里可用 `extractiveMode=true` / `degraded=true` 识别。

## 2 切换场景与操作

### 2.1 场景 A：本地 Ollama ↔ 也是本地（换模型）

最简单的切换：**只改模型名**，不涉及外部依赖。

```bash
# 1) 看现有模型
curl -s http://127.0.0.1:11434/api/tags

# 2) 改配置（二选一）
#    a. application-local.yml（已 gitignore，属环境侧配置）
#       app.ai.llm.ollama-model: qwen2.5-7b-instruct-baseline
#    b. 环境变量（推荐，避免改文件）
export OLLAMA_MODEL=qwen2.5-7b-instruct-baseline

# 3) 重启后端（配置在启动期读取）
# 4) 验证生效
curl -s http://127.0.0.1:8080/api/ai/capability -H "Authorization: Bearer <token>"
#   期望 "generator":"ollama"、"llmConfigured":true、"degraded":false
```

**注意**：改模型不会改检索链路（embedding 仍是 `bge-small-zh-v1.5`，与生成模型解耦），因此**不需要重建向量**。

### 2.2 场景 B：本地 Ollama → 云端 API（真正切走）

**四步，缺一不可**（关键在第二步：只配 Key 不会切，因为 Ollama 优先级更高）：

```bash
# ① 注入云端 Key（不要写进任何文件/文档）
export LLM_API_KEY='<你的 Key>'

# ② 让 Ollama 不可用 —— 这一步是"真正切走"的关键
#    方式一（推荐，可逆）：停 Ollama 服务
#      任务管理器结束 ollama.exe，或（服务方式安装时）net stop ollama
#    方式二（不改运行环境）：把 base-url 指到不可达端口
#      export OLLAMA_BASE_URL=http://127.0.0.1:11434-DISABLED/v1
#    ⚠️ 不要靠"删模型"来切——会影响回滚速度

# ③ 声明展示用 provider（可选，仅影响日志）
export AI_LLM_PROVIDER=dashscope      # 或 zhipu

# ④ 重启后端 → 验证
curl -s http://127.0.0.1:8080/api/ai/capability -H "Authorization: Bearer <token>"
#   期望 "provider":"dashscope"（或 zhipu）、"generator":"dashscope"、无 degraded
```

**若 ② 没做会发生什么**：配置写 `provider: dashscope`、Key 也配了，但 `available()` 里 Ollama 排第一仍是 true → **请求还是打本地 7B**。这就是最常见的一次「切了但没切」。

### 2.3 场景 C：云端 → 回本地 Ollama（回滚，最常用）

```bash
# ① 拉起 Ollama（若之前停过），确认模型在
curl -s http://127.0.0.1:11434/api/tags | grep -o 'qwen2.5-7b-instruct-baseline'

# ② 移除/清空云端 Key —— 让云端 available()=false，避免误用云端产生费用
unset LLM_API_KEY

# ③ 恢复 provider 展示值
export AI_LLM_PROVIDER=ollama

# ④ 重启后端 → 验证
curl -s http://127.0.0.1:8080/api/ai/capability -H "Authorization: Bearer <token>"
#   期望 "generator":"ollama"、"extractiveMode":false、"circuitOpen":false
```

**回滚耗时**：后端重启到 health 200 约 **8 秒**（第 9 周实测基线，见 `项目规划/第9周/07_降级与回滚演练_2026-11-09.md` §3）。

### 2.4 场景 D：强制走抽取式（应急止血，零外部依赖）

当云端在烧钱、本地模型又慢到影响体验时，可强制降级：

```bash
# 方式：让所有 LlmClient 都不可用
#   ① 停 Ollama
#   ② unset LLM_API_KEY
#   ③ 停 AI 微服务（8000），使 FastApiLlmClient 不可用
# 结果：三路全不可用 → 落到 ExtractiveAnswerClient（@Order(30)）
curl -s http://127.0.0.1:8080/api/ai/capability -H "Authorization: Bearer <token>"
#   期望 "extractiveMode":true、"available":true（接口仍可用，只是答案偏原文摘录）
```

**这是设计内的行为，不是故障**。用户可见变化：答案变「原文摘录」风格、不再有流畅表述；引用仍真实。

## 3 切换判定与验证清单

每次切换后必须过这 6 条：

| # | 检查 | 期望 |
|---|---|---|
| 1 | `GET /api/actuator/health` | `200` |
| 2 | `GET /api/ai/capability` 的 `generator` | 与本次目标一致（`ollama`/`dashscope`/`zhipu`/空=抽取式） |
| 3 | `extractiveMode` | 目标为真模型时应为 `false` |
| 4 | `degraded` / `circuitOpen` | 均为 `false` |
| 5 | `POST /api/ai/ask` 实测一问 | `200`，`sources` 非空，有 `traceId` |
| 6 | 响应 `costMillis` | 本地 7B 通常 **数千毫秒**；Wiki 热层 **数百毫秒**；云端通常 **数百–一两千毫秒** |

> ⚠️ **第 6 条不能反推模型身份**：第 10 周实测「进程和线程的区别」0.409 s 返回，但走的是 **Wiki 热层**（`generator=wiki`），根本没调模型。要看 `generator` 字段，不要看耗时。

## 4 熔断与降级链（切换期间的行为）

```
请求 /ai/ask
  ↓
① Wiki 热层（app.wiki.enabled=true，hit-threshold=0.60）
  ├─ 命中 → 直接返回（generator=wiki，0.05–0.4 s）
  └─ 未命中 ↓
② RAG 冷层（recall-limit=50 → top-k=5，reject-threshold=0.15）
  ├─ 最高分 < 0.15 → 拒答（refused=true，不进生成）
  └─ 有证据 ↓
③ LlmClient 链（@Order）：Ollama(5) → DashScope(10) → FastApi(15) → Zhipu(20)
  ├─ 连续 3 次失败 → 熔断 60 s（circuitOpen=true，静默降级，用户无感）
  └─ 全部不可用 ↓
④ ExtractiveAnswerClient（extractiveMode=true，答案=原文摘录）
```

**切换时的关键推论**：
- 只要 Wiki 命中，**换模型对那部分问题完全无感**（这也是为什么实测 0.4 s 就返回了）。
- 熔断是**按客户端**计数的，切到云端后若云端连续失败 3 次，会静默降级到抽取式 60 秒，**不会自动回退到 Ollama**（因为 Ollama 的 `available()` 是独立的，若它已不可用就不会被选中）。因此切云端前务必确认 Ollama 状态符合预期。

## 5 成本与风险提示（切换前必读）

| 风险 | 说明 | 缓解 |
|---|---|---|
| **无费用闸门** | 项目**没有任何 token/金额/调用次数上限**（第 10 周检查表 T3 FAIL）。切到云端后费用无刹车 | 切换前先评估调用量；优先用 `glm-4-flash` / `qwen-plus` 这类低价模型；试点期手动限量 |
| **无成本计量** | `ai_agent_run` 表不含 token/计费字段，`costMillis` 是耗时不是钱（T4 FAIL） | 只能靠云端控制台看账单 |
| **Key 泄露面** | Key 只应来自环境变量；`config/secrets.local.yml` 已 gitignore | 轮换 Key 后立即 `unset` 旧值；禁止写进 `docs/`/`README.md` |
| **CORS / 网络** | 云端调用走公网，本机无出网代理时会超时 | 先用 `curl https://dashscope.aliyuncs.com` 验证出网 |
| **切换窗口的异步任务** | 双实例共享同一数据库会误伤异步任务（第 9 周实测） | 切换窗口避开有长任务的时段 |

## 6 「切了但没生效」的 5 个排查点

| # | 排查 | 命令 |
|---|---|---|
| 1 | `provider` 改了但没让 Ollama 不可用 → 路由仍走 Ollama | 见 §2.2 第 ② 步 |
| 2 | Key 没注入成功（`available()` 直接 false） | 只看存在性：`if ($env:LLM_API_KEY) {"set"} else {"missing"}` |
| 3 | 改了配置但**没重启后端**（配置在启动期读取） | 重启后查 `/api/ai/capability` |
| 4 | 命中熔断（刚切过去就连失败 3 次） | 看 `circuitOpen` 与 `circuitRemainingMillis`，等 60 s |
| 5 | 命中的是 Wiki 热层，模型压根没被调用 | 看响应 `generator` 字段是否为 `wiki` |
