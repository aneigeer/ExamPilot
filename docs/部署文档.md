# 部署文档

> 项目：大学生多考试备考知识库与题库系统 · v1.0
> 环境：开发为 Windows 本机；使用可 Windows/Linux + Docker Compose

## 1 方式一：本机直接运行（开发/日常使用）

### 1.1 前置条件
JDK 21、Maven 3.9、MySQL 8.0.46（本机均在 `D:\bigplan\tools\`）

### 1.2 步骤
```bash
# 1. 初始化数据库（可重复执行）
"D:/bigplan/tools/mysql-8.0.46/bin/mysql.exe" -u root -p < sql/schema.sql
"D:/bigplan/tools/mysql-8.0.46/bin/mysql.exe" -u root -p < sql/data.sql
# 增量迁移（P0-B / P1，可重复执行）
"D:/bigplan/tools/mysql-8.0.46/bin/mysql.exe" -u root -p < sql/migration-p0b.sql
"D:/bigplan/tools/mysql-8.0.46/bin/mysql.exe" -u root -p < sql/migration-p1.sql
"D:/bigplan/tools/mysql-8.0.46/bin/mysql.exe" -u root -p < sql/migration-p1b.sql

# 2. 启动后端（端口 8080，内嵌管理端页面）
cd backend && mvn spring-boot:run

# 3. 访问
#    管理端  http://localhost:8080/api/admin/index.html
#    接口文档 http://localhost:8080/api/swagger-ui.html
```

> **必需口令 `DB_PASSWORD`**：配置里不再有弱口令兜底（`${DB_PASSWORD:}`），**未提供时会因连不上 MySQL 导致启动失败——这是预期行为**，用于避免静默回退到弱口令。本机开发把口令写进 `backend/src/main/resources/application-local.yml`（已 gitignore，模板见 `application-local.yml.example`）；Docker 部署由 `docker-compose.yml` 从 `MYSQL_ROOT_PASSWORD` 注入（缺失即启动失败）。`DB_USERNAME` 仍默认 `root`（用户名不属秘密）。

### 1.3 学生端
- 模拟器：安装根目录 `ExamPilot学生端-v1.4-真机版.apk`（包内 BASE_URL 指向打包时的局域网 IP；模拟器联调请改 `build.gradle` 的 `BASE_URL` 为 `10.0.2.2` 后重新构建）
- 真机：修改 `student-app/app/build.gradle` 中 `BASE_URL` 为电脑局域网 IP（如 `http://192.168.1.100:8080/api/`）后重新构建：
```bash
cd student-app && JAVA_HOME="D:/bigplan/tools/jdk21" "D:/bigplan/tools/gradle-8.7/bin/gradle.bat" assembleDebug --no-daemon
# 产物 app/build/outputs/apk/debug/app-debug.apk，拖入手机安装
```
- 正式签名：在 Android Studio 中 Build → Generate Signed Bundle / APK（大纲 13.3：签名由人工完成）

## 2 方式二：Docker Compose 部署（Linux 使用）

```bash
# 1. 构建后端镜像依赖的 jar
cd backend && mvn -B package -DskipTests

# 2. 启动（MySQL + 后端 + Nginx）
cd .. && docker compose up -d --build

# 3. 访问（Nginx 80 反代后端）
#    http://服务器IP/            → 管理端（经 /api 转发）
#    http://服务器IP/api/swagger-ui.html → 接口文档
```

> **限流与反代（阻断项 B）· 改网段必须同步改白名单**：容器部署下后端看到的 TCP 对端是 nginx **容器 IP**，`docker-compose.yml` 已钉死 `networks.default.ipam.subnet = 172.28.0.0/16` 并同步注入 `APP_RATE_LIMIT_TRUSTED_PROXIES=172.28.0.0/16`。**修改 subnet 必须同步改该环境变量，否则后端不认 nginx 容器 IP → `X-Forwarded-For` 被忽略 → 全站共用一个限流桶**（正常用户互相 429；比被绕过更烦）。同理**不要给 backend 服务加 `ports:` 发布 8080**：一旦发布，局域网客户端的真实 IP 就落在可信段内，伪造 `X-Forwarded-For` 会重新生效。改完网络配置需 `docker compose -p examprep down` 再 `up -d`（旧网络不会自动改 subnet）。

### 2.1 组成（见 `docker-compose.yml`）
| 服务 | 镜像 | 说明 |
|---|---|---|
| mysql | mysql:8.0 | 数据库，首次启动自动执行 sql/ 初始化脚本 |
| backend | eclipse-temurin:21-jre + exam-prep-backend.jar | 后端，depends_on mysql |
| nginx | nginx:alpine | 80 端口入口，反代 /api → backend:8080 |

### 2.2 数据卷
- `mysql-data`：数据库持久化
- `./uploads` → 容器 `/data/uploads`：上传文件持久化

### 2.3 可选：AI 依赖栈（`docker-compose.ai.yml`）

`docker-compose.ai.yml` 提供 Qdrant（向量库）+ MinIO（对象存储）两个可选组件；不启动它们时后端自动降级（向量通道跳过、文件落本地磁盘），主业务不受影响。

启动前**必须**注入 MinIO 凭据（已移除出厂默认凭据兜底，未注入则容器直接启动失败）：

```bash
MINIO_ROOT_USER=<用户名> MINIO_ROOT_PASSWORD=<强口令> docker compose -f docker-compose.ai.yml up -d
```

> **未设置 `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` 时，compose 直接拒绝启动（`:?` 快速失败）——属预期行为**，用于避免用弱默认凭据把对象存储暴露出去。
>
> 两点注意：① Qdrant 默认**不**启用鉴权，且**不要**把 `QDRANT__SERVICE__API_KEY` 设为空串——该变量"一经声明即开启鉴权"，空串会让匿名请求也 401；确需开启时取消该行注释并与 `ai-service/.env` 的 `QDRANT_API_KEY` 保持一致。② 本文件把 9000/9001（MinIO）与 6333/6334（Qdrant）直接发布到宿主机，公网部署务必用防火墙或反代收紧到内网。

## 5 常见运维问题

| 现象 | 处理 |
|---|---|
| 端口 8080 被占用 | `netstat -ano \| findstr 8080` 找到 PID 后结束，或改 `--server.port` |
| 上传文件丢失 | 检查 `uploads/` 目录权限与数据卷挂载 |
| MySQL 连接失败 | 核对 `application-local.yml` 数据源配置与 MySQL 服务状态 |
| App 连不上后端 | 真机检查 BASE_URL 与电脑防火墙（放行 8080） |

## 6 内部令牌（AI 服务 ↔ Java 后端）

> 2026-10-31 新增：`/v1/agent/*` 已加 `X-Internal-Token` 鉴权（防直连 8000 伪造 userId）。

| 项 | 说明 |
|---|---|
| Java 配置 | `app.ai.internal.token`（或环境变量 `AI_INTERNAL_TOKEN`） |
| Python 配置 | `AI_INTERNAL_TOKEN`（`app.agent.internal_token`） |
| 传输头 | `X-Internal-Token` |
| 未配置时 | Python 侧**放行并打 WARNING**（本地开发约定）；Java 侧不发该头 |

**部署必须做**：两端配同一个值，且 Java 端 `AgentStreamService` 会带头发给 Python。
若只在一端配置，症状是 agent 接口 `401`（Java 侧已带、Python 未配则不校验；反之必 401）。

**上线检查**：`curl -X POST http://<ai>:8000/v1/agent/run -H 'Content-Type: application/json' -d '{}'`
应返回 `401`；带 `-H "X-Internal-Token: <值>"` 才进入业务校验（可能 400 参数错，但不该是 401）。

## 7 发布失败回滚（2026-11-10 新增，补第 9 周 P1 文档缺口）

> 背景：第 9 周 W9-7《降级与回滚演练》判定「全项目没有任何一份文档能在发布失败时被人照着执行一次回滚」，列为 **P1 未闭环**。本章即为该缺口的收口件。

### 7.1 回滚判定阈值（满足任一条即回滚，不再观察）

| # | 判据 | 观测方式 |
|---|---|---|
| 1 | 新版本启动后 **120 秒**内 `GET /api/actuator/health` 未返回 `200` | `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8080/api/actuator/health` |
| 2 | 关键接口出现 **5xx**（`/api/home`、`/api/questions`、`/api/auth/login`） | 逐条 `curl -w '%{http_code}'` |
| 3 | 错误率相对上一版本上升，或日志出现 `BeanCreationException` / `DataSource` 相关启动异常 | 后端启动日志 |
| 4 | 数据出现不可解释的写入（如异步任务误更新） | `operation_log` 与业务表时间戳 |

> **不要**因为「再等等可能就好了」而延长观察窗口。第 9 周实测：从进程启动到 health 200 仅需 **8 秒**，120 秒不健康基本等于确实坏了。

### 7.2 回滚操作（可直接复制执行）

```bash
# ── 0. 预演必须在隔离端口做，禁止在 8080 上直接试错 ──
#    第 9 周演练固定用 --server.port=8081，零影响

# ── 1. 停新进程 ──
netstat -ano | grep -a ':8080'          # 取 PID
taskkill /PID <新进程PID> /F

# ── 2. 恢复上一版构件（jar 必须来自 release 留档，不要现场重新构建）──
#    建议发布前把当次 jar 复制到 release/jar/exam-prep-backend-<版本>.jar 并记录 SHA256
cp release/jar/exam-prep-backend-<上一版>.jar backend/target/exam-prep-backend-1.0.0-SNAPSHOT.jar

# ── 3. 恢复上一版配置（application.yml 若本轮有改动，必须一并回滚）──
git --no-pager diff --stat backend/src/main/resources/application.yml
# 若有改动：git checkout -- backend/src/main/resources/application.yml
#   ⚠️ 仅在确认本轮未做必要配置变更时使用；否则手工逐项还原

# ── 4. 启动并等待 health ──
#    DB_PASSWORD 必须从环境变量注入（见 §1.2 说明）
cd backend && java -jar target/exam-prep-backend-1.0.0-SNAPSHOT.jar
#    或预演端口：java -jar target/....jar --server.port=8081

# ── 5. 等 health 200（实测约 8 秒）──
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/actuator/health

# ── 6. 跑冒烟三项 ──
curl -s -o /dev/null -w 'home=%{http_code}\n'      http://127.0.0.1:8080/api/home
curl -s -o /dev/null -w 'questions=%{http_code}\n' "http://127.0.0.1:8080/api/questions?page=1&size=1"
curl -s -o /dev/null -w 'admin=%{http_code}\n'     http://127.0.0.1:8080/api/admin/index.html

# ── 7. 记录 traceId 与回滚时间点，归档到 项目规划/第N周/evidence/ ──
```

### 7.3 数据库变更纪律（硬约束）

1. **只允许向前兼容迁移**，禁止破坏性 DDL（`DROP COLUMN` / `DROP TABLE` / 类型收窄）。
2. 不可回滚的变更，**必须先做一次联机备份**（复用 §3 的 `mysqldump --single-transaction`，实测 3 秒 / 23.7 MiB）。
3. 项目**无 Flyway/Liquibase、无 schema 版本号**（`information_schema` 无版本表），迁移靠人工按 `sql/*.sql` 顺序执行 → **每次执行后必须在 `项目规划/第N周/evidence/` 留一份「本次执行了哪些脚本」的记录**，否则无法回答「线上是第几版结构」。
4. 回滚时**不要**执行任何 `.sql` 的逆向操作（不存在 down-migration）；如结构必须退回，走「恢复备份」而非「反向改表」。

### 7.4 回滚演练纪律

- 预演端口固定 `--server.port=8081`，**禁止**在 8080 上直接试错。
- 灰度 / 回滚窗口应**避开有长任务的时段**：第 9 周实测双实例共享同一数据库会误伤运行中的异步任务（本次 `Updates: 0` 未致损，但机制上未隔离）。
- 每次演练后更新本文档与 `项目规划/第N周/` 下的演练记录。

## 8 编程题在线运行（code-run）默认关闭

> 2026-11-10 新增。这是第 9 周 P0-3 收口结果，**默认值不可随意改回 true**。

| 项 | 值 |
|---|---|
| 配置项 | `app.code-run.enabled`（`application.yml:121-122`） |
| **默认值** | **`false`** |
| 关闭时的行为 | `CodeRunController` 因 `@ConditionalOnProperty` **整体不注册为 Bean** → `POST /api/run` 返回 **`404`**（不是 403/500），也不出现在 `api-docs` 中 |
| 临时开启方式 | 启动参数 `--app.code-run.enabled=true` 或环境变量 `APP_CODE_RUN_ENABLED=true` |

**为什么默认关闭**：`CodeRunService` 用 `ProcessBuilder` 在本机裸跑 `gcc` / `java.exe`，**无 CPU/内存/网络/文件系统隔离**，且子进程继承后端全部环境变量（含 `JWT_SECRET`、`DB_PASSWORD`）。一旦录入 `PROGRAMMING` 题目，任意自助注册用户即可在后端宿主执行任意 Java → 等价于 **P0 远程命令执行面**（结论见 `项目规划/第9周/03_代码运行沙箱_2026-11-08.md`）。

**开启前置条件（缺一不可）**：在独立判题沙箱完成隔离验收 —— 容器 / nsjail + `--network=none` + 只读 rootfs + 非 root 用户 + CPU/内存/PID 配额 + 编译与运行分离各自超时 + 输出硬上限 + 全局并发上限。
**仅本机单人调试可临时开启，严禁在公网部署中开启。**

**验证关闭已生效**：
```bash
# 无 token → 401（鉴权先于路由，不能用来判断接口是否存在）
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:8080/api/run
# 带合法 token → 404 才算真关闭
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:8080/api/run \
  -H "Authorization: Bearer <token>" -H 'Content-Type: application/json' -d '{}'
# 对照基线：不存在的路径也应是 404
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/nonexistent-xyz \
  -H "Authorization: Bearer <token>"
```

## 9 口令与密钥轮换流程

> 2026-11-10 新增。**本文档不含任何明文口令**；实际值只在 `config/secrets.local.yml`（已 gitignore）与运行环境变量中。

### 9.1 必填/必配项清单

| 项 | 配置键 / 环境变量 | 默认值 | 缺失后果 |
|---|---|---|---|
| **数据库口令** | `DB_PASSWORD`（`application.yml:24` `password: ${DB_PASSWORD:}`） | **空** | **连不上 MySQL → 启动失败**（预期行为，故意不设弱口令兜底） |
| 数据库用户名 | `DB_USERNAME` | `root`（用户名不属秘密） | — |
| **JWT 密钥** | `JWT_SECRET`（`application.yml:96`） | **空** | **应用启动即失败**（`JwtUtil` 构造器校验） |
| AI 内部令牌 | `AI_INTERNAL_TOKEN`（`application.yml:156`） | **空** | `/internal/**` 一律 **403**（安全默认值）；只用 `/ai/ask` 时可不配 |
| 云端 LLM Key（可选） | `LLM_API_KEY` | **空** | 自动走抽取式兜底，接口仍返回 200 |
| CORS 白名单 | `APP_CORS_ALLOWED_ORIGINS` | `http://localhost:8080` | 正式域名下浏览器请求被拦 |

### 9.2 数据库口令轮换（四步，可照做）

```bash
# 1) 生成新口令（24 位，大小写+数字+符号），存到 config/secrets.local.yml，不要贴到聊天/文档
# 2) 改库（用旧口令连）
ALTER USER 'root'@'localhost' IDENTIFIED BY '<新口令>';
FLUSH PRIVILEGES;
# 3) 先验证新口令能连（旧口令应立刻 ERROR 1045）
mysql -u root -p -e "SELECT 1;"
# 4) 更新运行环境变量 DB_PASSWORD → 重启后端 → 复验 /api/actuator/health = 200
```

**轮换期间的坑（第 10 周实测）**：
- 轮换后**必须**同步更新所有读库脚本的凭据来源（本项目统一走 `config/mysql-client.local.cnf`，`mysql --defaults-file=...` 免交互）。
- 轮换后跑一次 `mvn -B clean package`，确认 Spring 上下文能连库（第 10 周在最终口令下取得 **371 用例 / 0 失败**）。
- 轮换后检查 MySQL **general_log**：若为 `1`，所有含 `IDENTIFIED BY` 的语句会写进 `mysql.log`（第 10 周曾因此产生 380 MB 含明文口令的日志）。**必须** `SET GLOBAL general_log=0;` 并清空该日志。

### 9.3 JWT 密钥轮换

1. 换 `JWT_SECRET` → **所有已签发 token 立即失效**，全部用户需重新登录（7 天有效期，`expire-minutes: 10080`）。
2. 因此**必须在低峰期**做，并提前公告。
3. 轮换后抽查：旧 token 请求应返回 `401`，新登录 token 请求应 `200`。

### 9.4 超管口令轮换

1. 用 Spring 自带的 BCrypt 生成新哈希（`spring-security-crypto`），写入 `user.password`。
2. 校验方式：旧口令 `MISMATCH`、新口令 `MATCH` 后再上线。
3. 明文只落 `config/secrets.local.yml`，**禁止**写进 `docs/`、`README.md`、`sql/data.sql`（第 10 周已把历史明文从上述三处清零）。
4. 轮换后立即用 HTTP 实测一次登录（`POST /api/auth/login`），避免「哈希写错但没人发现」。

### 9.5 禁止事项

- ❌ 把任何口令/密钥/token 写进 `docs/`、`README.md`、`sql/data.sql`、代码注释、提交信息。
- ❌ 在聊天记录、工单、截图中粘贴明文。
- ❌ 把 `config/secrets.local.yml`、`config/mysql-client.local.cnf` 加入版本控制（`.gitignore:123-130` 已覆盖，`git ls-files config/` 必须为空）。
- ❌ 依赖「弱口令兜底」——本项目已刻意移除所有兜底默认值。
