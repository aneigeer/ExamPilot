# 运维手册（Operations Manual）

> 项目：大学生多考试备考知识库与题库系统
> 版本：2026-11-10（第 10 周新增）
> 适用：部署后的日常运维、健康巡检、日志排查、看门狗使用
> **本文不含任何明文口令/密钥/token**；涉密项只写「位置」不写「值」

## 1 组件拓扑与端口

| 组件 | 监听 | 启动方式 | 端口性质 |
|---|---|---|---|
| 后端（Spring Boot 3.5.3） | `0.0.0.0:8080` | `java -jar backend/target/exam-prep-backend-1.0.0-SNAPSHOT.jar` 或 `启动后端.bat` | **全网卡**，context-path = `/api` |
| AI 微服务（FastAPI） | `127.0.0.1:8000` | `ai-service/run.bat` 或看门狗 `run_watchdog_v2.ps1` | 仅回环 ✔ |
| MySQL 8.0.46 | `0.0.0.0:3306` / X 协议 `0.0.0.0:33060` | Windows 服务名 `mysql` | 全网卡 ⚠ 见 §6.1 |
| Ollama | `127.0.0.1:11434` | 用户登录后自启 | 仅回环 ✔ |
| Redis（可选，当前未用） | 未监听 | `docker-compose.redis.yml` | 当前关闭，与 `app.ai.jobs.enabled=false` 一致 |
| Nginx（生产/Docker 模式） | `:80` / `:443` | `docker-compose.yml` | 反代 `/api` → backend:8080 |

> **路径前缀提醒**：`server.servlet.context-path=/api`，所以所有端点都是 `/api/...`。
> **健康检查不能用 `/api/ai/health`**（该路径不存在，返回 404）；AI 侧能力状态用 `/api/ai/capability`（需登录），AI 服务自身健康用 `http://127.0.0.1:8000/v1/health`。

## 2 健康检查（三层）

### 2.1 一层：进程/端口存活

```bash
netstat -ano | grep -a -E ':8080|:8000|:3306|:11434'
```
期望：8080 / 8000 / 3306 / 11434 四条均为 `LISTENING`；8000 与 11434 只应是 `127.0.0.1`。

### 2.2 二层：应用健康端点

```bash
# 后端（唯一权威健康端点）
curl -s -o /dev/null -w 'backend=%{http_code}\n' http://127.0.0.1:8080/api/actuator/health
# 期望 200（management 仅暴露 health,info，且 show-details=never，因此只返回 {"status":"UP"}）

# AI 服务（含 embedding / qdrant 子状态）
curl -s http://127.0.0.1:8000/v1/health
# 期望 {"status":"ok","embedding":{"ready":true,...,"dim":512,"model_id":"bge-small-zh-v1.5"},"qdrant":{"ready":true,...}}

# Ollama
curl -s http://127.0.0.1:11434/api/tags
```

### 2.3 三层：业务冒烟（4 条，全部应 200）

```bash
B=http://127.0.0.1:8080/api
curl -s -o /dev/null -w 'home=%{http_code}\n'          "$B/home"
curl -s -o /dev/null -w 'questions=%{http_code}\n'     "$B/questions?page=1&size=1"
curl -s -o /dev/null -w 'detail=%{http_code}\n'        "$B/questions/4022"
curl -s -o /dev/null -w 'admin=%{http_code}\n'         "$B/admin/index.html"
curl -s -o /dev/null -w 'student=%{http_code}\n'       "$B/student/index.html"
```

## 3 日志位置与检索

| 日志 | 位置 | 说明 |
|---|---|---|
| 后端运行日志 | 控制台输出 / `logs/` 目录下 `backend_*.log`（Spring Boot 标准 output） | 按启动批次编号，如 `backend_058_20261108.log` |
| AI 服务日志 | `ai-service/uvicorn.log` | uvicorn 访问 + 应用日志 |
| 看门狗日志 | `项目规划/第N周/evidence/ai_service_watchdog_v2.log` | 记录 `PORT_READY pid=… health200=True` |
| MySQL 错误日志 | `D:/bigplan/tools/mysql-8.0.46/data/*.err` | — |
| MySQL 通用查询日志 | `mysql.log` | **必须保持关闭**（`general_log=0`）；曾因开启产生 380 MB 含明文口令的日志 |
| 操作审计日志 | 管理端「操作日志」页（登录/审核/修改/删除，含 IP 与 UA） | 业务级审计，不落文件 |
| 备份产物 | `backup/<日期>/` | 已 gitignore，`git ls-files backup/` 必须为 0 |

### 3.1 按 traceId 定位

所有响应体都带 `traceId`（如 `{"code":400,"message":"…","traceId":"2ff3e8d9d86b1847"}`）。

```bash
# 从用户报错截图/响应里拿到 traceId，然后：
grep -a "2ff3e8d9d86b1847" logs/*.log
```

### 3.2 ⚠️ 日志隐私约束（务必知道）

- `app.observability.log-question: false` → **问题原文不进日志**，只输出 `qLen=<长度>` 与 `qHash=<sha256 前 8 位>`。
- 但**这不等于日志无 PII**：第 9 周审查确认运行日志仍可能含 **BCrypt 口令哈希、真实姓名、学号**（P1 未闭环）。
- 因此：**日志文件不得外发、不得贴到公开工单/聊天**；需要给外部看时先脱敏。

## 5 看门狗用法（AI 服务自愈）

### 5.1 为什么需要

第 9 周实测：AI 服务进程被杀后**不会自动恢复**，"依赖有人手工拉起一个不会被回收的进程"在生产上等于不可恢复。修好后的看门狗可在进程消失后自动拉回，**从启动到 health 200 约 8 秒**。

### 5.2 三个脚本的分工

| 脚本 | 用途 |
|---|---|
| `ai-service/run_watchdog.bat` | 最简版：循环检查并重启（早期版本，有进程被回收的问题） |
| `ai-service/run_watchdog.ps1` | PowerShell 版基础实现 |
| **`ai-service/run_watchdog_v2.ps1`** | **推荐**：修复了进程回收问题，日志写入 `evidence/ai_service_watchdog_v2.log`，输出 `PORT_READY pid=… health200=True` 作为可审计凭证 |

### 5.3 用法

```powershell
# 默认参数启动（内部固定 8000 端口）
powershell -ExecutionPolicy Bypass -File ai-service\run_watchdog_v2.ps1

# ⚠️ 指定端口：用 -Port 参数（不要在脚本内部改常量，避免多实例冲突）
powershell -ExecutionPolicy Bypass -File ai-service\run_watchdog_v2.ps1 -Port 8000
```

### 5.4 看门狗运维要点

1. **看门狗本身不是 Windows 服务**：终端关闭/用户注销它就停。要长期运行需注册计划任务或 NSSM（当前项目未做，属已知缺口）。
2. **验证它在工作**：杀掉 uvicorn 进程 → 等 10–20 秒 → 再查 `netstat` 是否重新 `127.0.0.1:8000 LISTENING`，并检查日志新增一行 `PORT_READY ... health200=True`。
3. **看门狗不做告警**：它只自愈不通知（第 9 周 W9-4 判「告警通道 部分/缺失」）。**服务反复重启不会被任何人发现**，需人工定时查日志。
4. **不要让两个看门狗同时守同一端口**，会互相干扰。

## 6 已知运行风险（运维必须知道的 5 条）

### 6.1 MySQL 仍监听全网卡（⚠ 最高优先）

- 现状：`my.ini:29` 已写 `bind-address=127.0.0.1`，但**服务未重启**，运行时变量仍是 `0.0.0.0`。
- 复验：`mysql --defaults-file=config/mysql-client.local.cnf -N -B -e "SHOW VARIABLES LIKE 'bind_address';"` → 若仍为 `0.0.0.0`，收口未生效。
- 处置：重启 MySQL 服务后复验，且 `netstat` 不应再出现 `0.0.0.0:3306`。
- 缓解现状：`root@'%'` 已删，远程连接会 `ERROR 1045`（双保险，但不是收口）。

### 6.2 限流分桶的 IP 来源（X-Forwarded-For 信任边界）

**判定基线说明**：冻结的 jar（2026-11-10 17:55）内 `RateLimitFilter` 无条件采信 `X-Forwarded-For` → 换头即换桶，**防护失效**。源码已有修复（`ClientIpResolver` + `app.rate-limit.trusted-proxies`），但**截至本文撰写未进入 jar**。下面按「修复后」的正确运维姿势写，重建 jar 后即适用。

**规则一句话**：只有 TCP 对端本身在 `app.rate-limit.trusted-proxies` 内，它写的 `X-Forwarded-For` 才被采信；否则完全忽略该头，退回 `getRemoteAddr()`。

#### 两种部署形态，配置完全不同

| 形态 | 后端看到的 TCP 对端 | 是否需要配 `trusted-proxies` | 结论 |
|---|---|---|---|
| **本机直连**（本项目当前形态：`java -jar` 直接监听 8080，无 nginx） | 真实客户端 IP | **不需要**（默认 `127.0.0.1,::1` 已够） | 行为正确，XFF 一律被忽略 ✔ |
| **Docker Compose / nginx 反代** | **nginx 容器 IP**（如 `172.28.0.3`） | **必须显式配置** | 不配 → XFF 被忽略 → **所有客户端退回同一个 nginx 容器 IP → 全站共用一个桶** |

#### ⚠️ 容器形态必须「钉死网段」，不能笼统写私有段

Docker 默认 bridge 网段是**自动分配**的（常见 `172.18.0.0/16`，但不保证），**无法静态写死一个能长期正确的值**。因此正解是**先钉死 subnet，再让白名单与它一致**：

```yaml
# docker-compose.yml
services:
  backend:
    environment:
      # 必须与下方 ipam.subnet 完全一致
      APP_RATE_LIMIT_TRUSTED_PROXIES: "172.28.0.0/16"
networks:
  default:
    ipam:
      config:
        - subnet: 172.28.0.0/16
```

**绝对不要**写成 `172.16.0.0/12` 这类笼统私有段：一旦 backend 的 8080 被发布到局域网，局域网攻击者的**真实源 IP 本身就落在「可信段」内** → 伪造 `X-Forwarded-For` 立刻生效，等于把修复作废。

**nginx 侧配套（已就位，勿改回）**：必须用 `$remote_addr` **覆盖**而不是 `$proxy_add_x_forwarded_for` **追加** —— 后者会把客户端自带的值拼在最前，后端采信第一段就被伪造。

```nginx
proxy_set_header X-Real-IP       $remote_addr;
proxy_set_header X-Forwarded-For $remote_addr;   # ★ 覆盖；禁用 proxy_add_x_forwarded_for
```

#### 三种配错的后果（从轻到重）

| 配错方式 | 后果 |
|---|---|
| 没配 `trusted-proxies`（容器形态） | XFF 被忽略，全站共用 nginx 一个桶 → **过严**：正常用户互相挤掉、频繁误报 429 |
| 白名单写了笼统私有段 | **过松**：局域网攻击者真实 IP 落在可信段 → 伪造 XFF 生效，防护失效 |
| nginx 用回 `$proxy_add_x_forwarded_for` | **过松**：无论后端怎么配，客户端自带值都会被采信 |

#### 机器校验（可直接贴进发布检查）

```bash
# ① nginx 未回退到"追加"写法（期望无输出）
grep -n "proxy_add_x_forwarded_for" nginx.conf nginx-https.conf nginx-https.conf.example

# ② compose 是否钉死了网段（期望有 subnet）
grep -n -E "ipam|subnet|APP_RATE_LIMIT_TRUSTED_PROXIES" docker-compose.yml

# ③ 重建 jar 后确认修复真的进包（两条都要过）
unzip -l backend/target/*.jar | grep ClientIpResolver
cd backend && javap -p -c -cp target/classes com.examprep.config.RateLimitFilter | grep -c resolve
```

> 代码修法本身属发布前阻断项，见第 10 周检查表 `S11` / `S11b` / `S18`。

### 6.3 无监控告警系统

- 能看状态（health 端点），**不能主动叫醒任何人**。
- 三大缺口：HTTP 5xx 错误率、AI 调用成本、队列积压/拒绝 —— **均无阈值告警**。
- 运维缓解：每日人工跑 §2.2 + §2.3；错误率靠查日志；成本靠人工估算调用量。

### 6.4 备份无节奏、无加密

- `backup/` 目录目前**只有 1 个历史转储**（`backup/2026-11-03/`），说明计划任务没在稳定跑。
- 转储为**明文 SQL**，含全部用户行（含 BCrypt 哈希、学号）→ 文件本身是高敏资产。
- 处置：①确认 `backup.bat` 已挂计划任务；②备份目录 ACL 收紧到仅运维账户；③禁止把 `backup/` 拷到个人 U 盘/网盘。

### 6.5 无 schema 版本管理

- 项目无 Flyway/Liquibase，无版本表，26 个 `sql/*.sql` 靠人工顺序执行。
- 后果：**无法回答「线上是第几版结构」**；回滚时也没有 down-migration。
- 纪律：每执行一个 `sql/*.sql`，就在 `项目规划/第N周/evidence/` 留一条记录（脚本名 + 执行时间 + 执行人 + 影响表）。
