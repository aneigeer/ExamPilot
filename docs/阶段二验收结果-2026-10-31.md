## 2. 最严重的三个问题（带原始证据）

### 问题 1（安全，最高优先级）：L3 引用校验在主力模型路径上整体失效，且模型答案被误标为降级

**证据（实测原始响应）**

```
POST /api/internal/agent/answer
{"question":"int 占几个字节","draftAnswer":"int 占 8 字节，这是常识 [9]。",
 "contexts":[3 条 …]}

→ HTTP 200
{"answer": "int 占 8 字节，这是常识 [9]。", "generator": "agent-llm",
 "degraded": true, "refused": true, "sources": []}
```

```
POST /api/ai/ask  {"question":"C语言 int 占几个字节"}
→ HTTP 200  generator=ollama  degraded=True  sources=1
  answer="在 32 位系统中，C 语言的 int 类型通常占用 4 字节 [1]。"
```

**根因（一处代码，两个后果）**

```java
// AnswerPostProcessor.verify() 第一行
if (!PromptBuilder.isLlmGenerator(answer.generator())) {
    return answer;                        // ← L3 四类规则全部跳过
}

// PromptBuilder.java:64-66
public static boolean isLlmGenerator(String generator) {
    return GENERATOR_DASHSCOPE.equals(generator) || GENERATOR_ZHIPU.equals(generator);
}
```

主模型是本地 `ollama`（`OllamaLlmClient` 传的 generator 就是 `"ollama"`），Agent 路径用 `"agent-llm"`，Python 代理是 `"fastapi"`——**三者都不在白名单里**。后果：

1. 伪造引用 `[9]`、无引用正文，都能原样返回给用户（A6 失败）；
2. `degraded` 被算成 `answer.degraded() || !isLlmGenerator(...)` ⇒ 只要是本地模型生成就恒为 `true`，管理端把"模型正常回答"和"降级/抽取式"混成一类（G 失败），**阶段二「模型网关」验收项不通过**。

**影响面**：答辩最可能被追问的两个点（伪造引用会不会被拦、这条答案是谁生成的）都答不好；且 `refused=true` 与 `answer` 里有内容自相矛盾，前端若按 `refused` 渲染"拒答"会展示出带 `[9]` 的正文。

**修复建议（1 处常量 + 1 处判定）**：把 `agent-llm` / `ollama` / `fastapi` 纳入 `isLlmGenerator`，或改成"白名单只排除 `extractive`/`none`/`wiki`"的反向判定；同时给 A6-a/A6-c 两个样本做回归（本轮已写成用例，修完直接复跑）。

**派给：software-engineer（Alex）**

### 问题 2（演示阻断）：Agent 工具链路当前完全不可用，答辩现场"AI 导学"会直接失败

**证据（`ai_agent_run` id=93，A 用户的真实会话轨迹）**

```
final: {"answer": "未找到相关资料", "generator": "none", "degraded": true,
        "refused": true, "step_count": 2, "tool_calls": 1, "sources": []}
tool_result: tool=get_wrong_book  ok=False
             summary=工具不可用：调用 Java 内部接口失败：ConnectError
```

**两个叠加原因**

1. Python 的 `java_base_url` 默认 `http://127.0.0.1:8080/api`，本轮 8080 未启动（约束：不得占用）→ `ConnectError`；
2. 即便 8080 起来，**Python 侧 `AI_INTERNAL_TOKEN` 为空**，而 Java 的 `InternalTokenFilter` 空令牌一律 403 → 工具调用仍会失败（`工具不可用：…403`）。两个方向都已核过：Java→Python 会带令牌（`AgentStreamService.java:265-267`），Python→Java 会带令牌（`java_bridge.py:29-30`），但**两侧令牌值目前对不上**（Java 有、Python 无）。

**影响**：`/ai/agent/stream` 能返回 200 + 终态（看起来"能用"），但实际所有身份类/检索类工具都失败，答案恒为「未找到相关资料」。答辩演示"查我的错题/薄弱点"会当场空转。

**最小修复**：两端同配 `AI_INTERNAL_TOKEN`（同一个值），并在 `docs/部署文档.md` 的上线自检里加一条 curl 自检（本轮已实测：Java 侧带正确令牌 `200`，无/错令牌 `403`，符合预期）。

**派给：software-engineer-py（配 .env）+ software-engineer（自检脚本/部署文档）**

### 问题 3（发布口径）：`/v1/agent/*` 运行态无鉴权，V1"名义已修、实际未生效"

**证据**

```
POST /v1/agent/run  （不带任何令牌）           → HTTP 200  ← 任何人都能指定 userId 读他人数据
POST /v1/agent/run  X-Internal-Token: 错误值   → HTTP 200  ← 错误令牌也放行
POST /v1/route                                → HTTP 200  ← 证明实例是最新代码（该接口 20:23 后才存在）
```

**根因**：`routers/agent.py` 的 `require_internal_token` 在 `AI_INTERNAL_TOKEN` 为空时**只告警不拦截**：

```python
expected = _internal_token()
if not expected:
    logger.warning("[Agent] 未配置 AI_INTERNAL_TOKEN，/v1/agent/* 处于无鉴权模式（仅限本地开发）")
    return          # ← fail-open
```

而 Java 侧是 fail-closed（`!StringUtils.hasText(expected)` 直接 403）。**同一套协议、两种失败策略**，结果就是"以为配了就好，其实默认全开"。

**验收口径建议**：要么把 Python 侧也改成 fail-closed（代价：所有未配令牌的本地环境 401，需要同步更新 `run.bat`），要么在启动日志里用 `ERROR` 级别 + 健康检查暴露 `internal_token_set=false`（`config.py:421` 已有该字段，但 `/v1/health` 未输出它）。二者择一，否则这条在高危项清单里会一直处于"看起来修了"的状态。

**派给：software-architect（定策略）+ software-engineer-py（实现）**

## 6. 给答辩的一句话口径（基于实测，不夸大）
